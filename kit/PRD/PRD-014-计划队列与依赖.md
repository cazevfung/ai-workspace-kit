## 1. 要解决什么问题

到 2026-11-21，库里 170 张单里有 166 张领过（含当天新开的 AW-095、AW-096）。把「排队」这一段按时间量一遍，结论是**这一段根本不存在**：所谓规划都在 `tasks/plan-*.md` 里，库里只有已经开工的单。

- **没有池子。** 164 张领过的单里 **140 张（85.4%）create 到首次 claim 不到 60 秒，中位数 0.027 分钟（1.6 秒）**（口径：`tickets.created_at` 到该单最早的 `attempts.created_at`，取 2026-11-21 11:49 之前建的单，即不含 AW-095、AW-096；全库算上这两张是 166 张里 142 张）。复算：

  ```bash
  python -m task_center --db {{WORKSPACE}}/.data/task-center.sqlite3 list_tickets --input '{}'
  ```

  这句话的实际含义不是「大家动作快」，而是**开单那一刻就等于开工了**：单子一旦进库，`ready` 就在等一个会话，而不是在等一个排期。于是「这一轮还欠哪几张单」只能拿 `tasks/plan-0NN-*.md` 当账本数——2026-11-21 当天现成的三个例子就是 `tasks/plan-030-工单机制的执行面.md`（计划四张，实开两张）、`tasks/plan-031-占用与作废语义.md`、`tasks/plan-032-计划队列.md`。

- **PRD 指纹冻在 create。** `tickets.prd_sha256` 是 `NOT NULL`（`task_center/db.py` 的 `SCHEMA`），`create_ticket` 当场写进去（`task_center/core.py:417`），之后 `_unchanged_prd()`（`task_center/core.py:472-473`）与 `answer_ticket`（`task_center/core.py:647`）都拿它比。所以一张单只要在库里排两天，PRD 一升版它就报 `STALE_PRD`——表达方式只有「本来就慢」和「已经过期」，没有「排着队、开工时再定依据」这一档。要排长队，先得让依据在**领取时**定格。

- **一个会话只能持一张单。** `task_center/db.py:44` 是 `CREATE UNIQUE INDEX active_session ON attempts(session_id) WHERE session_id IS NOT NULL AND state IN ('blocked','running','submitted')`——索引键只有 `session_id`，谓词只有三个活跃态。同一个会话要接着做第二张相关的单，只能先交完第一张，或者绕开正路（拿另一个会话顶一下）。「一次构建、一次资源占用、一次合并干掉三张相关的单」在库里无法表达。

- **排着不动的单会挡住收尾。** `tools/work_gate.py:44` 的 `CLOSING_BLOCKING_STATES` 含 `ready` 与 `rework`。**2026-11-21 收尾 R-015 时，正因 AW-094 留在 `ready`，收尾提交被钩子连拒三次，最后只能先 `cancel_ticket` 才收得了尾**（取消事件 `2026-11-21T11:13:11Z`，理由原文即「收尾闸门把 ready 也算在途」，随后才有收尾提交 `83d6189`）。而 `tools/close_gate.py:61` 的 `IN_FLIGHT` 只有 `dispatching` / `running` / `awaiting_review` / `blocked` 四个——两份定义不一致，同一件事两个答案。复算：

  ```bash
  grep -n "CLOSING_BLOCKING_STATES\|IN_FLIGHT =" tools/work_gate.py tools/close_gate.py
  ```

- **编号与 `request_id` 在并行下不可用。** 2026-11-21 当天，协调会话 `a7e4ca66` 想用 `AW-091`、`AW-093` 这两个号，两次都被另一个协调会话 `7ab2590d` 先建走（`AW-091` 建于 10:17:51、`AW-093` 建于 10:38:33，两张单的 `claim` 回执里 `coordinator_session_id` 都是 `7ab2590d`），本会话只能顺延到 `AW-092`、`AW-094`。同一时刻 `req-create-aw093` 这个 `request_id` 也撞车：10:52:33 的同号调用报 `REQUEST_CONFLICT`，`events` 里留了一行 `{"rejected":"REQUEST_CONFLICT","request_id":null}`（`requests.id` 是主键、全库共用，指纹不同就是冲突，见 `task_center/core.py:268-274`）。**自报编号在并行下不成立，这件事已经发生过两次。** 复算：

  ```bash
  python -m task_center --db {{WORKSPACE}}/.data/task-center.sqlite3 events --input '{"project_id":"ai-workspace","ticket_id":"AW-093"}'
  ```

- **schema 升版单证明不了自己的基座。** R-015 第 6 条留下的债：分支代码要 schema 10、正式库是 9 时，执行会话只能退回主检出的旧代码提交，于是那张单自己的 `submissions.base_sha` 必然是 `NULL`（`PRD-013` R7 的能力，用它自己的单证明不了）。排队更久 = 更多单跨着 schema 版本开工，这条债会更常撞。

这六条不是六件独立的小事，是同一条结构缺失的六个出口：**「还没开工」这件事在库里没有位置。** 它既不是 `ready`（那是等人领走），也不是 `blocked`（那是在等一句话），于是只能写在 Markdown 里；而写在 Markdown 里的东西，库推不动、闸门看不见、收尾还得替它让路。

### R1 `planned` 与收尾相容

**语义。** 新增 `planned`：还没开工、已经在库里排着的单。

1. `create_ticket` 收可选 `state`，只收 `planned` 与 `ready`（缺省仍是 `ready`，现有调用方行为一字不变）。`planned` 单不产生任何 attempt，不占 `active_session` 槽位，也不接受 `bind_session`。
2. `claim_ticket` 接受 `planned` 与 `ready`（`rework` 照旧），三者都进 `dispatching`。`planned → dispatching` 与 `ready → dispatching` 的区别只在进入时有几道校验（R2、R3）。
3. `cancel_ticket` 收 `planned`。`revise_ticket` 对 `planned` 单照常可改判据与依据。
4. **在途集合只有一份定义，写在 `docs/closing.md`：** 在途 = `dispatching` / `running` / `awaiting_review` / `blocked` / `ready` / `rework` 六个，**不含 `planned`**。`tools/work_gate.py` 的 `CLOSING_BLOCKING_STATES` 与 `tools/close_gate.py` 的 `IN_FLIGHT` 都从这一份取值（后者现在只有四个，要补齐到六个），两份不再各写一份。
5. 于是「这一轮还欠哪几张单」变成池子里看得见的行，而**收尾不再被排期挡住**：`planned` 单在场时 `close_gate --check` 与收尾提交都放行；`ready` / `rework` 的在场仍算「有活没干完」，照旧拦住收尾——它们是「等人领走」，不是「还没轮到」，两者的区别正是本条要落下的东西。

**验收条件。**

- AC-R1-1（命令类）：`python tools/close_gate.py --check` 退出 0，且此时库里至少有一张 `planned` 单没被取消；`grep -c "planned" docs/closing.md` 期望输出不小于 1，且该处句子写的是「不算在途」。
- AC-R1-2（命令类）：`python tools/work_gate.py --list` 在只有 `planned` 单在池子里时退出 0 并打印「在途 0 张」；把同一张单改成 `ready` 后同一条命令期望非零，并点名这张单。
- AC-R1-3（判断类）：`tools/work_gate.py` 与 `tools/close_gate.py` 的在途集合是否逐字同源、`planned` 是否只在「不算」一侧出现。反例：两份文件各留一份集合，改一处不改另一处。

### R2 PRD 指纹从 `create` 挪到 `claim`

**语义。**

1. `tickets.prd_sha256` 允许为空：`create_ticket` 只记 `prd_path`（并对路径是否存在做一次检查），`planned` 期间该列为 `NULL`。
2. `claim_ticket` 那一刻取 PRD 的 `sha256`，写进 `attempts.prd_path` / `attempts.prd_sha256`（两列 schema 10 已有），同时回写 `tickets.prd_sha256` 表示「这一次派发依据的是哪一版」。**取指纹的是 `claim_ticket` 自己**，不是任何定时任务，也不是执行会话。
3. 排队期间 PRD 升版不再让单变 `STALE_PRD`；`claim` 之后 PRD 再变，仍旧报 `STALE_PRD`（`_unchanged_prd()`、`answer_ticket` 的比较对象变成 attempt 上的那一份）。差异只落在「什么时候定格」，不落在「定格之后还算不算数」。
4. `revise_ticket` 显式更新 `prd_path` 时重取指纹（与现在一致），`planned` 单改了路径仍留 `NULL`。

**验收条件。**

- AC-R2-1（命令类）：`python tools/run_tests.py` 退出 0，且新增用例 `test_planned_ticket_survives_prd_bump_before_claim` 与 `test_prd_bump_after_claim_still_stale` 都 PASS。
- AC-R2-2（命令类）：`python -m task_center --db <副本库> get_ticket --input '{"project_id":"…","ticket_id":"…"}'` 在 `planned` 单上期望 `prd_sha256` 为 `null`，`claim` 之后同一字段为 64 位十六进制、且与工作树里那份 PRD 的 `sha256` 相等。
- AC-R2-3（判断类）：是否有第二条路径也在写 `tickets.prd_sha256`，以及它会不会让一张没领过的单带上指纹。反例：create 时顺手取一次「反正不费事」。

### R3 依赖三类

**语义。** 新表 `ticket_links(from_ticket, kind, to_ticket, created_at)`，`kind` 只收三个值：

| kind | 用途 | 拦不拦 |
| --- | --- | --- |
| `blocked_by` | 前置单：它没 `done`，下游不许开工 | 拦，`claim_ticket` 报 `BLOCKED_BY_DEPENDENCY` |
| `related` | 相关但可并行：同主题、会互看成果 | 不拦，只进 R6 的列与提示 |
| `rides_with` | 同一车次：按 R4 合并资源与合并动作 | 不单独拦，车次约束见 R4 |

1. `claim_ticket` 判 `blocked_by`：任一前置单不是 `done` 就报 `BLOCKED_BY_DEPENDENCY`，`message` 里点名是哪张单、它当前在什么状态；一行不写。
2. 依赖边在两个方向都答得出：`get_ticket` 回执增 `links`（出边与入边），R6 的 `list_tickets` 只显示未完成的 `blocked_by`。
3. 环检测在写边那一刻做：`create_ticket` / `revise_ticket` 收到 `blocked_by` 时跑一次可达性，成环报 `DEPENDENCY_CYCLE` 并点名环上的单号。
4. 前置单被 `cancel_ticket` 时下游不自动作废：`blocked_by` 只认 `done`，`cancelled` 的前置仍算未满足——取消不是完成，下游要不要撤由人决定。

**验收条件。**

- AC-R3-1（命令类）：`python tools/run_tests.py` 退出 0，且新增用例 `test_claim_blocked_by_pending_names_the_ticket`、`test_claim_blocked_by_done_ok`、`test_dependency_cycle_rejected` 都 PASS。
- AC-R3-2（命令类）：在副本库上对一张有未完成前置的单跑 `claim_ticket`，期望退出码非 0 且 stdout 含 `BLOCKED_BY_DEPENDENCY` 与那张前置单的单号。
- AC-R3-3（判断类）：三类链接是否各有一句用途且各自回答了「拦不拦、在哪个操作里拦」。反例：三类共用一句「用于表示关系」。

### R4 车次与 `active_session` 放宽

**语义。**

1. 新表 `batches(id, project_id, resource_key, owner_session_id, planned_at, closed_at)`，`tickets.batch_id` 可空。**一个车次 = 一次资源占用窗口 + 一次构建 + 一次合并**：车次内所有单共用同一个 `resource_key`（与 `PRD-012` 的 `资源:<类型>:<值>` 同形），一次 `run_tests`，最后只写一条合并记录。
2. 同一车次内允许一个会话持多张单：车次内每张单各自是一条活跃尝试，可以同时 `running`。**车次归属不靠 `attempts` 上的唯一键推，靠 `batches.owner_session_id`：** `claim_ticket` 领一张带车次的单时做一次运行期校验（与 R3 的 `BLOCKED_BY_DEPENDENCY` 同一类显式校验，不是索引兜底）——
   - 车次的 `owner_session_id` 为空 → 写入本会话，放行；
   - 等于本会话 → 放行（这就是「同车次内接着做下一张」）；
   - 是别的会话 → 报 `BATCH_OWNED_BY_OTHER`，`message` 里点名车次号、它与持有会话，一行不写。
3. `attempts` 侧的唯一索引只保留「无车次的单，一个会话一张」：`attempts` 增 `batch_key` 列（`claim` 时从 `tickets.batch_id` 抄一份，无车次为 `NULL`），索引收窄成

   ```sql
   CREATE UNIQUE INDEX active_session ON attempts(session_id)
    WHERE batch_key IS NULL AND state IN ('blocked','running','submitted');
   ```

   即：**没有车次的单行为与今天完全一致**（一会话一张）；**有车次的单根本不在这一条索引的范围内**，所以同一会话在同一个车次里可以同时持两张活跃单。`attempts.batch_key` 只用来回答「这条尝试属于哪个车次」，不承担唯一性。

   为什么车次归属不写成唯一键：唯一键表达不了「同一会话可以持多张、不同会话不可进同一车次」这条规则。同会话同车次的两张活跃单，任何 `(session_id, batch_key)` 或 `(batch_key)` 的唯一键都会重键——**2026-11-21 C5 验收在内存库里实测，两种写法分别报 `UNIQUE constraint failed: index 'active_session'` 与 `UNIQUE constraint failed: attempts.batch_key`**；而放开车次维度只留 `active_session(session_id)` 又会让「两个会话各持同车次一张」偷偷通过。所以这条规则只能落在 `claim_ticket` 的运行期校验上，索引只守住无车次的那一半。
4. 释放时机三种：

   | 情况 | 何时发生 | 怎么释放 |
   | --- | --- | --- |
   | 车次结束 | 车次内最后一张单写合并记录，`batches.closed_at` 落值 | 该车次的尝试早已 `done`，`closed_at` 之后车次不再接受新单；`owner_session_id` 随车次一起失效，不再拦人 |
   | 单子终结 | `done` / `cancelled`，或 `rejected` 回 `rework` | 未进车次的单：尝试状态离开 `blocked`/`running`/`submitted`，`active_session` 索引条件失效，槽位自动空出。进了车次的单本来就不占这条索引，它的「释放」是车次维度的事（见上一行） |
   | `recover_ticket` | 协调会话显式作废 | 旧尝试转 `superseded`（不在谓词里）：无车次的单槽位立刻释放；车次的 `owner_session_id` 不随 recover 改变，同一个会话重新 `claim` 时按新的 `batch_key` 重新进入校验 |

   未进车次的单不需要额外的「清理」操作：**释放不是一件事，是索引谓词的自然结果。** 有车次的单则多一步人看得见的东西——车次关不关由最后一张单的合并记录说明，`closed_at` 为空就还在占用。这也是没做租约表的原因：`PRD-013` 的 R8 才做租约，本条不抢它。
5. 车次内的合并：合并提交只认车次最后一张单（`batch_id` 相同、`closed_at` 为空、且没有其他未合并的同车次单）。`PRD-013` R10 的「合并唯一入口」仍在其后做，本条只把「一次合并」这层的目标写清。

**验收条件。**

- AC-R4-1（命令类）：`python tools/run_tests.py` 退出 0，且新增用例 `test_two_tickets_in_one_batch_both_active`（同一会话、同一车次的两张单**同时**处于 `running`）、`test_same_session_second_ticket_outside_batch_rejected`（无车次的第二张仍被 `CONFLICT`）、`test_second_session_on_a_batch_rejected`（另一会话领同车次报 `BATCH_OWNED_BY_OTHER`）都 PASS。
- AC-R4-2（命令类）：`grep -n "WHERE batch_key IS NULL" task_center/db.py` 期望命中一条建 `active_session` 的语句（索引只守无车次那一半）；`grep -c "active_batch" task_center/db.py` 期望输出 `0`（车次归属不再用唯一索引表达）；`grep -n "owner_session_id" task_center/db.py` 期望命中 `batches` 的建表行。
- AC-R4-3（判断类）：车次结束、单子终结、`recover_ticket` 三种释放时机是否各写清「什么时候发生」与「靠什么失效」，以及车次归属是否只有一个判据（`batches.owner_session_id` + `claim_ticket` 运行期校验），没有第二处靠唯一键推。反例：只写一句「用完会释放」，说不出谁触发；或既写运行期校验又保留一条车次维度的唯一索引。

### R5 库里发号

**语义。**

1. 每个项目一条顺序号：`projects.next_number`（或等价的 `ticket_numbers(project_id, next)`），**`create_ticket` 在同一个事务里取号并加一**——号在写 `tickets.id` 那一刻发出，它同时是主键、也是 `attempts` / `submissions` / `merges` / `notices` 引用的那个值，所以 `claim` 不再取号（re-claim / `rework` 重领沿用同一个号，换号就等于换主键）。展示形态 `<前缀>-<序号>`，前缀取项目登记时的短名（`ai-workspace` → `AW`）；**跨项目不共用一条序列**（`KIT-001` 与 `AW-001` 各自独立）。
2. `create_ticket` 不再接受调用方指定工单号：payload 里出现 `ticket_id` 报 `INVALID_INPUT` 并写明「号由库里发」。回执返回分配到的号，调用方以回执为准。
3. 迁移时按已有最大号初始化 `next_number`（`AW-096` → 下一次 `AW-097`），历史号一律不改、不重排、不复用。
4. **`request_id` 的命名空间**：`requests.id` 是主键、全库共用，不按项目、不按会话分区。所以规则是——同一条 `request_id` 只属于一次调用；指纹（`operation` + `payload` 的 `sha256`，`task_center/core.py:268`）相同才当幂等重放返回原回执，不同就报 `REQUEST_CONFLICT` 且一行不写。写法建议 `<发起方>-<操作>-<序号>`，发起方用会话短号或工单号。**撞了不自动改名**：改名会把「同一次调用」变成两次，两条都落库。R5 只把这件事写清，不把生成权收进库里——发号解决的是工单号，`request_id` 仍是调用方的责任，只是不再允许它「看着像唯一」。

**验收条件。**

- AC-R5-1（命令类）：`python tools/run_tests.py` 退出 0，且新增用例 `test_create_ticket_assigns_number`、`test_create_ticket_rejects_caller_id`、`test_number_sequence_per_project` 都 PASS。
- AC-R5-2（命令类）：在副本库上连开两张单，`python -m task_center --db <副本库> list_tickets --input '{}'` 期望两张单号连续；`grep -n "request_id" docs/protocol.md` 期望命中一段写明命名空间与 `REQUEST_CONFLICT` 判据的文字。
- AC-R5-3（判断类）：`docs/protocol.md` 是否写明 `request_id` 全库共用、以及「指纹相同 = 幂等重放、不同 = 冲突」两句话。反例：只写「注意 request_id 不要重复」。

### R6 规划期可见性

**语义。**

1. `list_tickets` 收 `planned` 布尔（CLI 糖 `--planned` 等价）：为真时只列 `planned` 单，**按依赖顺序**输出——先按 `blocked_by` 的层数升序（无前置为第 0 层），同层按 `created_at`。
2. `LIST_COLUMNS` 增两列，只在 `planned` 视图出现（其余视图的表头与现在逐字一致）：`claimable`（布尔）与 `blocked_by`（未 `done` 的前置单号数组，无前置为空数组）。
3. `claimable` 的定义写死：该单 `state` 在 `planned`/`ready`/`rework` 之内，且所有 `blocked_by` 已 `done`。**它不代表「现在就能领」**——同项目已有在途单时 `claim_ticket` 仍报 `DISPATCH_BUSY`，那是另一件事，不要在一列里混着答。
4. 具体命令与输出形状：

   ```bash
   python -m task_center --db {{WORKSPACE}}/.data/task-center.sqlite3 list_tickets --input '{"planned": true}'
   ```

   期望回执 `columns` 含 `id` / `project_id` / `title` / `state` / `claimable` / `blocked_by` / `created_at`，`items` 按上面的依赖顺序排；不传 `planned` 时 `columns` 与今天逐字相同（`PRD-013` R7 的 `behind` 列不丢）。

**验收条件。**

- AC-R6-1（命令类）：上面那条命令退出 0，且 `columns` 里含 `claimable` 与 `blocked_by` 两个键。
- AC-R6-2（命令类）：在副本库上造一条 A←B 的 `blocked_by` 边，同一条命令期望 B 排在 A 之后，且 A 的 `blocked_by` 含 B 的单号、`claimable` 为 `false`；把 B 置 `done` 后 `claimable` 期望变 `true`。
- AC-R6-3（判断类）：`claimable` 是否被写成了「现在就能领」的同义词。反例：把 `DISPATCH_BUSY` 的判定也塞进这一列。

## 7. 不在本 PRD 里做的事

- 不做自动排期、不做依赖变化时自动重排下游。
- 不做看板 UI，不做面板上的池子视图。
- 不把 `request_id` 的生成权收进库里（R5 只写清命名空间）。
- 不回溯历史单的编号、依赖与指纹。
- 不做车次内的会话移交（`transfer_batch`）：车次内一个会话做完，换人走 §6 的默认路。
