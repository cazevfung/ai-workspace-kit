# 计划 004：发一次版，把套件从 0.3.0 提到 0.4.0

## 依据

- `PRD-001-工作区使用与工单体系.md` v0.1（`kit/PRD/PRD-001-工作区使用与工单体系.md`）：闭环形状、版本可追、执行者不自验三条约束本计划；发版这件事本身不新增需求，只把已合入的 KIT-005、KIT-006 两轮成果变成一个能对着仓库复算的版本号。
- KIT-007 工单的 deliverable 与 C1–C7：VERSION 到 0.4.0、CHANGELOG 两条「未发布」并成一条 0.4.0 记录（日期 2026-11-21）、插件清单与套件同版本并重打包、文档里的旧数与旧包名同步、安装节的命令与仓库实际结构一致。
- `kit/AGENTS.md` 六条硬规则：第三条验收条件不许执行中改、第四条没有工单不许改文件、分支按工单走且执行会话不合并不推送。第三条决定了「判据与交付物口径冲突时不自行改判，写进未决」。

## 所用 skill

- `plan-gate`：它要求先记 PRD 编号与版本、按任务挑 skill 并真读、六节结构、过 `doc_gate` 才开工；本文件按它的四件事组织，依据段落因此写成「PRD-001 v0.1 + 工单判据」两条，而不是只抄工单。
- `ticket-dispatch`：它定 create → claim → bind → submit → review → merge 的字段与顺序；本单的绑定、提交与那一条回执按它走，回执正文只写工单号、状态与提交 sha。
- `verification-before-completion`：它要求说「做完了」之前贴出真跑过的命令与输出；本计划每个任务都把可复跑命令与期望输出写进验证，不写「已确认」。
- `writing-plans`：它要求每步写清「做到什么算完、拿什么当证据」；文档同步那一步因此按「文件 × 旧数 × 新数」列成可数的清单，而不是一句「同步文档」。

- **主题**：把套件发一次版。
  1. `VERSION` 改成 0.4.0；`CHANGELOG.md` 把「未发布（KIT-005）」「未发布（KIT-006）」并成一条 0.4.0 发布记录，日期 2026-11-21，全文不再出现「未发布」。

  3. 文档同步：`README.md`、`README.en.md`、`docs/`、`kit/README.md`、`plugin/README.md` 里的 0.3.0 与旧用例数、旧技能数、旧包名改成 0.4.0、491 项、26 个技能与 `dist/ai-workspace-kit-0.4.0.cindy`；安装节写的命令与包名跟仓库实际结构一致。
- **不覆盖**：不改任何闸门判定与核心逻辑（`kit/tools/*.py` 的判据、`kit/task_center/` 的校验与报错文案一行不动）；不加新功能、不改技能内容、不重写 README 的既有结构；不动 `D:/AI工作区`；不推送远端，提交只留在 `ticket/KIT-007` 分支上；不上架插件市场，不写 `releaseNotes`。
