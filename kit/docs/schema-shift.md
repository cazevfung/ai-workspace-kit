# 说明卡：两张单同时把 schema 推到同一级，后落地的那张顺延一级

这张卡只管一件事：**两个分支各自把 `SCHEMA_VERSION` 往上推了一级，先合并的那张已经把这一级占住了，后落地的那张怎么办。** 它不解释迁移怎么写、也不改版本判定逻辑——那些在 `docs/protocol.md` 的 `migrate` 一行与「改 schema 的落地顺序」里。

## 一、先判断：我这张单要不要顺延

```bash
git -C {{WORKSPACE}} show master:task_center/db.py | grep -n "^SCHEMA_VERSION = "
```

- 输出里的数**小于**你分支上写的那个 —— 不用顺延，按原样合。
- 输出里的数**等于**你分支上写的那个 —— **要顺延**：master 上那一级已经有人占了。
- 输出里的数**大于**你分支上写的那个 —— 你落后不止一级，先 `git rebase master`，再按 rebase 后的情况重看这一条。

判断依据只有这一条命令的输出，不要按「我记得我是第 14 版」来定。

## 二、规则一句话

**先合的那张保持原位；后落地的那张把自己的版本号 +1、把迁移语句的键 +1，先落地的那张一个字都不改。**

`SCHEMA_VERSION` 是等级不是水位：v15 的代码读 v14 的库报 `SCHEMA_MISMATCH`，v14 的代码读 v15 的库同样报。`MIGRATIONS` 又是拿版本号当键的字典，两个分支各自写 `MIGRATIONS[13]` 时，git 只会留下其中一份语句——先合的那份赢。所以后落地的那张如果不动键，它那两条 `ALTER TABLE` 就永远跑不到，而版本号照样往上走，库最后停在一个「版本对、缺列」的形状上。

## 三、顺序：谁先合

按**谁先被验收、谁先合并**定，不按谁先开工、谁的工单号小。已经合进 master 的那张不再改动——它是后来者的地基。

两张单都在路上的时候，先合的那张越小越好：后落地的那张要做的改动量，等于它自己那一级迁移再加一次 rebase 冲突，越小越省事。两张单改的是同一个文件的同一个字典，所以它们天然不能并行合并，也不该并行派发到最后一步。

## 四、后落地者的三件事

1. **版本号 +1。** `task_center/db.py` 的 `SCHEMA_VERSION` 从 N 改成 N+1。
2. **迁移键 +1。** 你自己的迁移语句从 `MIGRATIONS[N-1]` 挪到 `MIGRATIONS[N]`；`MIGRATIONS[N-1]` 留给先进 master 的那张，两条语句各自在自己的键里，不要叠在一个键上。
3. **冻结形状与用例名 +1。** 表示「上一级还没有这两列」的那个常量（例如 `V13_REQUIRED_COLUMNS` → `V14_REQUIRED_COLUMNS`）与迁移用例的名字（`test_13_to_14_…` → `test_14_to_15_…`）跟着挪一级。用例造库的方式也要跟着改：**上一级已经有对方加的那一列，造库时要把它留着**，否则你测的是「从更早的版本升上来」，而不是「从对方落地后的形状升上来」。

## 五、落地步骤（照抄）

在工单自己的工作树里：

```bash
cd {{WORKSPACE}}/.worktrees/<工单号>
git rebase master                 # 把自己挪到先落地者之上；冲突通常就在 db.py
# 解冲突：三件事按上一节做，两边的列与语句都保留，只有「键」和「版本号」往右挪一格
python tools/run_tests.py         # 必须末行「结果：全部通过」
```

解完冲突、测试绿了，再把合并交给协调会话：

```bash
python tools/auto_merge.py --ticket <工单号> --dry-run   # 冲突预演要过，看到「检查：…… 无冲突」而不是「第 3 步 · 冲突预演」
python tools/auto_merge.py --ticket <工单号>             # 真合并
```

`auto_merge` 不替你解冲突：源分支与目标分支撞在一起时它停在「第 3 步 · 冲突预演」并退出 1，把冲突文件列出来。这一步是设计如此，不是它坏了——它没有能力判断「两个键该留谁」，也不该猜。

## 六、库在哪一刻迁移

三句话，顺序不能换：

1. **执行会话一步都不碰正式库。** 要试迁移，只在副本上试：`python -m task_center --db <副本库> migrate`，看回执里的 `from_version` / `migrated` / `schema_version`，再 `list_tickets` 确认原有记录都在。
2. **代码先进 master，再迁库。** 合并窗口就在这一刻：合并成功之后，用合入后的 master 代码对正式库跑一次 `migrate`，把 N → N+1 那一级补上。这两步在同一个窗口里做完，不留过夜，中间不派新的执行会话。理由是等号校验：代码合了、库没迁的那段时间，`work_gate.py --list`、`list_projects`、`backup` 全都读不了库。
3. **迁完校验，通过再删快照。** `migrated: true` 且 `schema_version` 是新版本、`list_projects` / `list_tickets` 看得到原有记录、`backup` 能成功、`work_gate.py --list` 列得出来。全过才删升级前那份副本。

完整五步（副本验证 → 代码先进 master → 合完迁库 → 校验 → 删快照）写在 `docs/protocol.md` 的「改 schema 的落地顺序」；这张卡只补它没讲的那一格：**同一级被两张单同时占的时候，谁让路、让到哪一格。**

## 七、三条反例（每种都能当场变红）

- **两边都写 N、都写 `MIGRATIONS[N-1]`，合并时随手取了一边。** 另一边的列永远加不上：版本号到了 N+1，`PRAGMA table_info(tickets)` 里却没有对方的列，代码一读就报缺列。检测：迁完之后逐列对一遍两边的 `ALTER TABLE`，少一列就不算迁完。
- **只改版本号、不改迁移键。** 迁移从 N-1 直接跑到 N，跳过的正是后落地那张的两条语句；同样的检测命令会红。反过来的形状也会被拒：版本号停在 N-1、键却已经是 N 的语句（`already_applied` 命中）时报 `SCHEMA_MISMATCH`，文件一个字节都不改。
- **在自己的分支上先把正式库迁了。** 主检出停在旧版本的代码上，`python tools/work_gate.py --list` 当场报 `SCHEMA_MISMATCH`——「开工前先查有没有人在做」那条命令先失灵，后面所有人都在一个读不了库的状态里干活。

## 八、这件事的真实发生过一次，演练过一次

- 真实顺序（2026-11-22，正式库）：AW-106 先落地、占住 13 → 14 那一级（合并提交 `e31445e`），AW-114 后落地，在 `69e8466` 里把版本顺延到 15、把 owner 那两条语句放到 `MIGRATIONS[14]`，随后由 `f4b8749` 合进 master。之后 AW-116 又把这一级推到 16（`merges` 四列）。
- 演练：`tasks/drill-AW-118-schema-shift.md` 在副本仓库与副本库上把「两边都是 14」重演了一遍——先证明不顺延就停在冲突预演，再解冲突、跑全量测试、把副本库 14 → 15、用 `--record-only` 写下合并记录；演练前后主检出与正式库都没有变动。
