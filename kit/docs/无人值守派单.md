# 无人值守派单：三个动作、什么时候不许动、怎么停

这份文档写给两拨人：要把这条循环做成定时任务的人，和接手时想知道「它为什么没干活」的人。
它同时是 `tools/next_action.py` 的说明书——那个脚本只负责**算**下一步，不负责**做**。

依据：`PRD/PRD-014-计划队列与依赖.md` v0.2（R1 `planned` 与收尾相容、R3 依赖三类、R6 池子视图）、
`PRD/PRD-013-工单机制的执行面.md` v0.3（R10 合并唯一入口）、`PRD/PRD-005-决策通道.md`（`blocked` 与提问）、
`PRD/PRD-001-Cindy会话工作体系.md` v0.12（owner 与 origin 的分工、回执的收件人、`answer_ticket` 与回执同一把尺）、
`docs/closing.md`（在途集合只有一份定义）。

## 1. 这条循环在做什么

每隔一段时间问一次「现在该做什么」，只做一件，然后结束：

```bash
python tools/next_action.py            # 一句人话
python tools/next_action.py --json     # 同一份结论的结构化形态
```

五个结果，一次只给一个：`dispatch_execute`（派执行）、`dispatch_review`（派验收）、`merge`（合并）、
`fix_pool`（池子里只剩领不走的单，点名它；报过之后按窗口退避、到第 N 轮升级，见 §3.2）、
`nothing`（不动）。**退出码就是判据**，
不要去读输出里有没有某个词：

| 退出码 | 含义 | 调度侧该做什么 |
| --- | --- | --- |
| `0` | 有活，`action` 是四个动作之一 | 按 `dispatch` / `ticket` 里的指向开一个会话或跑一次合并；`fix_pool` 是「去补判据或取消单」 |
| `2` | 没活：暂停中、有在途单挡着、池子空、或只有需要人看的行 | **不开会话**，本次醒来就结束 |
| `1` | 出错：库不存在/读不开/版本不对/缺表、项目归属查不出、参数写错 | 报给人，**不许**当成「没活」静默跳过 |

`1` 与 `2` 分开是这份说明书里最要紧的一处约定：库读不开的时候，脚本不知道有没有活；
把它报成 `2`，调度侧就会安安静静地不干活，而现场是坏的。这种静默失败比报错难发现得多。

**它不做的事**：不 claim、不 bind、不 submit、不合并、不发消息、不建定时任务。库里一行都不写
（`mode=ro` + `PRAGMA query_only=ON`）。动作由协调会话按结论去调对应的命令与工具。

## 2. 四个动作的先后：验收 > 合并 > 派执行 > 补池子

不是偏好，是各自挡不挡别人的差别：

- **验收排第一。** `awaiting_review` 在 `DISPATCH_BUSY` 的口径里算在途（`task_center/core.py` 的
  `ACTIVE_TICKET_STATES`）。它不被挪走，池子里的单一张也领不出来——它是唯一会卡住整条链的动作。
- **合并排第二。** 合并不挡任何派发，晚一轮没关系；但先把已验收的合进 master，后面的分支就少积一层冲突。
- **派执行排第三。** 池子排着的时候它才有意义。
- **补池子排最后。** `fix_pool` 是兜底：真实活一样也没有、而池子里躺着永远领不走的单时，
  才把这一档给他（§3.1）。把兜底排到真活前面，就会用「去补判据」把真活抢掉。
- **有在途单就一个都不给。** 见下一节。

`--json` 的 `candidates` 会把四类候选的单号都列出来（各是一个数组），但 `action` **只有一个**。
这就是「互斥」的落地方式：想看后面排着什么可以看 `candidates`，但只能照着 `action` 做一件事。

## 3. `nothing` 的四种来路，`reason_code` 分得开

| `reason_code` | 什么时候 | 话怎么说 |
| --- | --- | --- |
| `paused` | 暂停标记存在 | 「暂停中——<标记路径> 存在，一个动作都不给」 |
| `in_flight` | 同项目有在途单挡着 | 点名单号 + 停在哪一步，`in_flight` 数组带 `state` / `attempt_id` / `session_id` |
| `needs_human` | 一个能自动做的动作都没有，但库里有不自洽的行 | `stop` 数组逐条写清哪张单怎么了 |
| `review_in_flight` | 唯一的待办是「验收已经派出去、结论还没落库」 | `review_in_flight` 数组带单号、提交、已等几分钟；不再派第二个验收人，30 分钟没有 `reviews` 行自动回落成可派 |
| `idle` | 真没活 | 池子空、没有待验收、没有待合并 |
| `blank_criteria_backoff` | 空判据单报过、还在退避窗口里 | `fix_pool` 数组里仍带单号、轮次与还剩多久；到点之前不点名，退出码 `2`（§3.2） |

**挡住派发的是三个状态，不是四个。** `dispatching` / `running` / `blocked` 这三个占着「这一轮有人在做」：
分别对应「已领取、还没绑定执行会话」「执行会话在跑」「开了工在等一句话」。
`awaiting_review` **不在**这一组里——它自己的下一步就是派验收，把它算成「忙」，这个循环永远转不动。
这不是把在途集合改小：`DISPATCH_BUSY` 一行没改，收尾闸门的在途集合（`docs/closing.md`）也一行没改；
这里只回答「这一轮我自己还能不能往前走」。

`ready` / `rework` 也不算「在途挡着」：它们是没被领走的活，正是 `dispatch_execute` 的目标。

## 3.1 第四档：`fix_pool`，池子里只剩领不走的单（AW-138）

`planned` 允许 0 条验收条件（`PRD-014` R1：那是「已经知道要补什么、还写不出验收条件」的念头），
但 `claim_ticket` 读到空列表就报 `CRITERIA_NOT_JUDGEABLE`，所以**这种单永远领不走**。
在 AW-138 之前，它只是 `skipped` 里的一行 `no_criteria`、`action` 仍是 `nothing`——
池子里明明有单、只是没人能领，而循环每轮醒来都说「没活」。两张空判据单就这样在池子里
躺了一整天，直到有人自己去翻池子才发现。

**现在的判据：** 池子里存在状态可领（`planned` / `ready` / `rework`）且验收条件为空、
建单时间已经超过 `BLANK_CRITERIA_GRACE_SECONDS` 的单，且这一轮没有验收 / 合并 / 派执行
可做时，`action` 给 `fix_pool`、退出码 `0`，`dispatch` 里点名全部单号。**它属于「有活」，
不属于「没活」**：调度侧该开一轮去看，而不是把这一次醒来静默结束。

**阈值只有一个来源。** `tools/next_action.py` 的 `BLANK_CRITERIA_GRACE_SECONDS`，当前是
**24 小时**。为什么是这个数：建单与补判据本来就可能是两次动作（先记下来、再想清楚），
给它一天不会把正常流程报成故障；而「躺了一整天」正是这次被漏掉的现场——一天还没补上，
就不该再假定「有人正在补」。要调就改那一个常量，本文件不跟着改数；
`tools/next_action.py` 里也只有它一处，不写第二个数。

**两条出路，都要人或协调会话动手：**

- `revise_ticket` 补上至少一条**可判定**条件——写完它就从 `fix_pool` 里消失，下一轮按
  正常的池子顺序被派出去；
- `cancel_ticket` 承认这张单不做了——落库、带理由，事后查得到是谁为什么取消的。

**它只报不改。** `next_action.py` 不写判据、不取消单、不改状态：库仍是
`mode=ro` + `PRAGMA query_only=ON`，一行都不写。替人做决定会让「这张单为什么没了」无迹可查，
而「人忘记补判据」恰恰是这个档要暴露的事实，不是它要抹掉的事实。有一条用例守着这条
（`tools/test_next_action.py` 的 `test_next_action_never_writes_to_the_pool`：跑完一轮，
库里每张单的 `state` / `criteria` / `criteria_version` / `revision` 一个字节也不变）。

两个边界写在这里，免得读的人以为它只在一种现场出现：

- **期限之内的空判据单不点**，只留在 `skipped` 的 `no_criteria` 里（`reason_code=idle`）；
- **有别的动作可做时先做那个**（真活优先），但空判据单已经躺过期限时，人读那一行末尾仍会
  缀一句「另有 N 张空判据的单已经躺过一天」。

这一档在 AW-140 里多了一层节流：**报过之后不每轮重报**，按 2h→6h→24h 退避，报到第 3 轮
改喊「升级」。台账、阈值与落记录的命令写在下一节。

## 3.2 报过之后要退避，报到第 N 轮要升级（AW-140）

§3.1 只解决了「看不见」：池子里只剩空判据单时，`action` 给 `fix_pool`、退出码 `0`，
调度侧开一轮去看。代价是**没人处理就每轮再报一次**——同一张单、同一句话，一天下来烧掉
几十轮，输出一字不变。这一节补的就是那层节流：既不把它藏起来，也不每轮叫一遍。

### 台账：一条事件 = 一次点名

「已经报过几次」只有一个落库位置：`events` 表里 `operation=record_pool_report` 的行
（`task_center.core.POOL_REPORT`，写操作也叫这个名字）。写它的是 `task_center`，
读它的是 `tools/next_action.py`；**两边都不靠会话记忆**——换一个会话、换一台机器读同一个库，
算出的轮次与下一次时间一模一样。这条事件不改工单状态、不写判据、不取消单。

点名之后要落一条，一轮一张单一次：

```bash
python tools/pool_report.py --project ai-workspace --ticket AW-990 --request-id pool-AW-990-1
```

不落，下一轮就还是「第 1 轮」：没有退避，也没有升级。`--request-id` 是幂等的单位——同一轮
重试请重用同一个编号（回执原样返回，不会多记一轮）；省掉它脚本直接拒绝（退出码 `2`），
因为一次重试就会把同一轮记成两轮。

### 三条判据，都只看台账

| 台账情况 | 这一轮给什么 | `reason_code` | 退出码 |
| --- | --- | --- | --- |
| 还没有记录（第 1 轮） | 原样点名，人话带「还没报过」，并提示落一条记录 | `blank_criteria` | `0` |
| 报过，还没到下一次的时间 | 不点名：`fix_pool` 数组里仍带单号、轮次、还剩多久 | `blank_criteria_backoff` | `2` |
| 已到点，这一轮就是第 N 轮 | 升级：人话换成「建一张 planned 单 / `ask_ticket`」 | `blank_criteria_escalate` | `0` |
| 已到点，还没到第 N 轮 | 原样点名，人话带「已报过 k 轮」 | `blank_criteria` | `0` |

退避窗口从**最后一次**那条事件算起：第 1 次之后 2 小时、第 2 次之后 6 小时、第 3 次之后
24 小时，此后一直 24 小时。升级点 N 与这条阶梯对得上：1 次原价 + 两次退避之后再叫一次，
正好是第 3 轮（`POOL_REPORT_ESCALATE_AFTER`）。**升级只喊一次**：喊过之后要等 24 小时，
这期间再喊「请升级」就是同一句噪音——那正是这一档要消掉的东西。

退避窗口里退出码是 `2`，这不是 AW-138 之前的「静默」：每张单都已经点名过至少一次，
名字、轮次与下一次时间都在 `fix_pool` 数组里，人跑一次 `--json` 就看得到。真正会变成静默
的是「没落记录」——那就永远停在第 1 轮，每轮重报。

### 阈值只有一个来源，怎么调

`tools/next_action.py` 里三个常量，本文件不跟着改数：

- `BLANK_CRITERIA_GRACE_SECONDS`（24 小时）：一张空判据单躺多久之后才进这一档（AW-138，本单不动）；
- `POOL_REPORT_BACKOFF_SECONDS`（`2 小时, 6 小时, 24 小时`）：第 i 次点名之后等多久再点下一次；
- `POOL_REPORT_ESCALATE_AFTER`（`3`）：报到第几轮改喊升级。

要调就改这几个常量，`next_action.py` 里也只有它们一处；`--json` 的 `pool_report` 一节会把
当前值打印出来（`backoff_seconds` / `escalate_after`），核对时看那一份。

### 升级是两条路，仍然是「只报不改」

`next_action.py` 不建单、不写判据、不取消单——它只把这一轮的话换成升级：

- **建一张 `planned` 单**（推荐）：`create_ticket` 带 `state: "planned"`，把「补判据 / 取消
  这几张空判据单」写成可验收的条件。它进池子、会被正常派出去，比一句「请升级」有用。
- **`ask_ticket`**：只在读它的会话本身持有一条 `running` 尝试时可用（`ask_ticket` 要
  `attempt_id` 与 `session_id`）。它是落库的问题，不是同步提问卡，不在这儿开卡片。

两条老出路（`revise_ticket` / `cancel_ticket`）随时可用，而且是最短的：补上判据那张单立刻
离开这一档，下一轮按正常池子顺序被派出去；取消它连池子都不用再看见。

## 4. 动作一：派执行（`dispatch_execute`）

### 前置条件（全部成立才给这个动作）

1. 同项目没有 `dispatching` / `running` / `blocked` 的单。
2. 池子里至少有一张**可领**的单，定义与 `list_tickets --planned` 的 `claimable` 列逐字同源
   （`task_center/core.py`：状态在 `planned` / `ready` / `rework` 之内，且 `blocked_by` 全部 `done`）：
   - 只有 `done` 算满足，`cancelled` 的前置仍算没满足（`PRD-014` R3.4）——取消不是完成。
   - 挑哪一张：依赖层数升序，同层按 `created_at`，与池子视图同一个顺序。层数按**边**算，
     不按前置单的状态算——前置完成之后顺序不会重排。
3. `dispatch` 里给出 `prd_path` 与 `prd_sha256` 作为依据。`planned` 单的 `prd_sha256` 是 `null`，
   这是对的：指纹在 `claim_ticket` 那一刻才取（`PRD-014` R2）。

### 拒绝条件（下面任一条成立，就不许派这张单）

- **依赖没满足。** `claim_ticket` 报 `BLOCKED_BY_DEPENDENCY` 并点名前置单。`next_action` 已经把这类
  单排除在候选之外，列在 `skipped` 的 `blocked_by_pending` 里；**不要**替它改依赖边开路。
- **项目忙。** 别人刚领走一张：`claim_ticket` 报 `DISPATCH_BUSY`，点名那张单与它停在哪一步。
  这时候这一轮就结束，等下一轮——**不要**传 `allow_parallel` 绕开。
- **PRD 已变。** `claim` 之后 PRD 再改是 `STALE_PRD`；需要改判据就走 `revise_ticket`，由人决定。
- **车次在别人手里。** `BATCH_OWNED_BY_OTHER`（`PRD-014` R4）。

派执行的做法是「新开一个项目会话」：`cindy_helper` 的 `send_to_session` **不传** `target_session_id`，
指定 `project_path` 与 `title`。派单消息里带工单号、一句「以 `get_ticket` 的当前 attempt 为准」，
以及 `get_ticket` 回执里 `sessions` 那几项的 `session_url`（请求方 / 协调 / 执行 / 验收 / 回执收件人，
见 `docs/protocol.md` 的「一张单牵扯到哪些会话、哪条消息」）——链接是给人，让执行会话或接手的人
一眼能走到该看的那条会话；不写 attempt/sha——那些几小时就过期。`sessions` 里 `stale` 为 true 的
链接照给但注明是旧会话，`device` 为 null 时链接不带 device 参数，不自行补一个。

### 派单消息照这份写

派单消息分两段，一段机器写、一段人写。**整条消息不交给机器**：库里只有标题、交付物、判据，
生成不出「上一轮抠出来的 icon 不能用、这次不要贴 PSD」这种现场；把整条交给机器，等于把执行
会话的上下文抽干，那比回执漏发更贵。

- **骨架段（机器写）**：五块——工单与项目根 / 协调会话 id（取 `tickets.owner_session_id`）/
  开工第一步 / 开工方式（git 或 non_git）/ 回执怎么发。
- **现场段（人写）**：黄金圈 Why / How / What + 「最容易做歪的地方」，由协调会话写成一份文件，
  用 `--context` 传进去，工具原样接在骨架段后面（中间一条分隔线），一个字都不改。

```bash
python tools/dispatch_payload.py --ticket AW-111 --context <现场段文件>
```

现场段文件放这个工单的落点（`.data/untracked/<工单号>/context.md`），按四个标签各占一节。
2026-11-25 在 AW-168 上跑出来的真实输出（现场段原文照贴）：

```text
工单：AW-168（project_id=ai-workspace，项目根 d:/ai工作区）
协调会话 id：<session-id>（tickets.owner_session_id 的原值，缺了执行会话没处回执）
开工第一步：用 get_ticket 取当前 attempt 与判据（criteria 已到 v3，以库为准）；再 bind_session（project_root 写 d:/ai工作区）
开工方式：项目根是 git 仓库 → git worktree add .worktrees/AW-168 -b ticket/AW-168 master，之后只在这棵树里改
回执怎么发：python tools/receipt_payload.py --ticket AW-168 打印 send_to_session 的完整 args；target_session_id 不能省，send_to_session 要经 cindy_helper 的 call_tool 调
--- 现场段（派单人写的，不是库里的字段） ---
Why：2026-11-25 的 NC-007 做完了却没回执——协调会话派单只写一句「做完回我一声」，执行会话把回执写在自己会话里，`notices` 为空，合并会被 `NO_NOTICE` 拒；同一套模板派出的 NC-006 是执行会话自己摸到 `send_to_session` 才成的。通道只要还靠记性，就一定会漏。
How：机器只负责它知道的那几行，以及「三行圈在不在」；现场那一段仍由人写，缺了就不许把消息发出去。
What：`tools/dispatch_payload.py`（骨架 + `--context` 校验）、`tools/test_dispatch_payload.py`、三处文档收敛。
最容易做歪的地方：
1. **又抄一遍散文**——三处各写一份新的模板。
2. **打印到一半再报错**——半条消息被贴出去。
```

分隔线是给人看的：上面五行来自库里，下面几节是派单人这次写的。两段混排，事后就分不出
哪句话是库里的字段、哪句话是派单人的判断。

**三圈各管什么。**

- **Why**：这一单为什么这么做，1–2 句，**必须能改变执行中的判断**——不这么做会怎样，
  而不是复述工单标题。整段只写指向（「见 PRD」「详见工单」「参考 docs/x.md」）等于没写，
  因为它给不了执行会话任何一条可用的取舍。
- **How**：已定的路径与不许重新决定的事（改哪几个文件、哪些语义一个字不动）。执行会话
  不重新设计路线，改路线走 `revise_ticket` 或 `steer`。
- **What**：交付物，什么东西、什么形状、给谁看。
- **最容易做歪的地方**：派单前三条质询（哪里最可能被照字面做歪 / 一个有想法的工程师会先问
  什么 / 哪条判据在成果很浅时仍会通过）的落点。

**工单的 Why 在派单时定格**：之后意图演化走 `revise_ticket` 或 `steer`，执行会话不追新版。

**机器只判三件事：在不在、空不空、是不是纯指针。** 缺 `--context`、文件不存在、内容为空、
缺 Why / How / What / 最容易做歪的地方 任一节、某节正文为空、Why 是纯指针，都非零退出、
stdout 一个字节都不打印、stderr 点名缺哪一节——半条派单消息被贴出去，比没有更贵。
**Why 写得好不好机器判不了**，那是验收会话逐条判的事（它不判「这条合理吗」，只判
「可执行」与「你已经明说这是判断类」）。所以文档里不许把这件事写成「生成器保证 Why 有效」，
那会让人以为圈的质量已经被校验过。

为什么骨架段可以照发：它和回执方向是**同一套取数**——同一个库、同一张单、收件人取同一列
`tickets.owner_session_id`（`record_notice` 的授权与 target 读的也是它），不是自己读环境变量、
也不猜一个字符串。取不到就一行都不给：owner 为空、这张单没有尝试、状态不在 `dispatching` /
`running` 之内时同样非零退出。所以**不要手写骨架、也不要改输出里的值**；要改工单本身
（补 owner、重派）就回去改库，再打印一次。

这五行里有两行不是措辞，是两次事故：

- **「协调会话 id」这一行不能省。** 派单消息先于会话存在：执行会话要到 `bind_session`
  才有自己的标识，而「派我的人是谁」它无法自取。少了它，执行会话要么猜一个字符串填进去
  （AW-027 的现场：格式像、长度对，`list_sessions` 里却没有这条），要么干脆不发；
  两种都要等事后查 `notices` 才发现。现在这一行由命令从 `tickets.owner_session_id` 取。
- **「回执怎么发」这一行不能省，而且要写成能直接敲的命令。** `send_to_session` 在工具列表里
  可能看不到（按名字搜会返回空或 `UNKNOWN_TOOL`），要经 `cindy_helper` 的 `call_tool` 调，
  args 传 `name` 与 `target_session_id`（省略 `target_session_id` 的语义是新建任务，回执就落到
  一条没人认领的会话里）。不知道这一点的执行会话会写成「结果我写在提交里了」，回执于是
  没有送达（NC-007 现场：158 次工具调用里 `send_to_session` 出现 0 次）。

### 回执的收件人是谁、他不在时怎么办、谁有权收尾（AW-122）

这一节回答三件事，每件一句可判的话。起因是同一天三个现场：派单器 claim 完就被宿主归档，
于是 `answer_ticket` 对任何人都是 `NOT_COORDINATOR`（AW-118 在 `blocked` 里挂了 7 个多小时）；
一个会话在 owner 还活着的时候把它接替到了自己身上，结果两个会话都以为自己该写合并记录
（AWK-103，靠 `ALREADY_MERGED` 才没写成两条）；同一时刻回执在队列里堆了三条。

**一、收件人是现在负责收尾的那条会话，不是「谁派的」。** 回执发给
`tickets.owner_session_id`；`attempts.coordinator_session_id`（origin）只用于事后追查谁派的单，
不再参与投递。判据：`python tools/receipt_payload.py --ticket <单号>` 与
`python tools/notice_payload.py --ticket <单号>` 打印出来的 `target_session_id` 都等于该单的
`owner_session_id`；两处不相等就是有工具还在读 origin。

**二、派单器 `claim` 之后、发派单消息之前，必须把 owner 接替到一条活着的常驻会话。**
由派单器自己（那条刚 `claim` 的会话）做，一步搞定：

```bash
python tools/handover_owner.py --ticket <工单号> --to <常驻会话 id> \
    --reason "无人值守：派单器 <id> 本轮结束即归档，接替到值班会话"
```

它先只读核四件事，四条都过才写库：当前 owner 已经在宿主里**不在**（`archived` 或查不到）、
目标会话**活着**、这张单**还有收尾动作可做**（`done` 且已有合并记录或已有回执就拒绝——
合并根本不认会话）、目标不是这条尝试的执行会话。退出码三档：0 接替成功（`HANDOVER_DONE`）、
1 拒绝（`REFUSED` 并点名哪一条）、2 查不出（`UNKNOWN`，**「不知道」不许长得像「可以接」**）。
**这不改变 `take_over_ticket` 的四字段语义，也不是自动接替**：目标会话由人指名，工具只负责
拒绝那些后来会变成死锁或双重收尾的接法。判据：接替之后 `python tools/coordinator_state.py
--ticket <单号>` 退出 0 且打印 `verdict: OWNER_ACTIVE`。

**三、他不在时：回执落 `failed`，推进靠下一轮 `next_action`。** 派单器没指名常驻会话、或接替的
那条后来也归档了，执行会话的做法是固定的：回执发不出去就 `python tools/receipt_payload.py`
先看收件人，再走 `report_notice_failure` 落一条 `failed`，`detail` 写宿主原话（
例如「send_to_session 返回 ARCHIVED」）与目标已经归档这件事；`merge_ticket` 的 `NO_NOTICE` 因此
过得去（`failed` 也算走过回执）。**不要**换一个会话接着写、**不要**冒充已归档会话的 id、
**不要**在这一轮里反复重试。推进由下一轮 `next_action` 负责（`nothing` / `merge` /
`dispatch_review`），巡检由 `python tools/wait_audit.py` 报出「`done` 但 `merges` 无行」这类悬空。
判据：这张单的 `notices` 里有一行写清去向（一条 `sent`，或若干条 `failed` 带原因），
且那一轮里没有第二张单因为同一原因被重试。

**谁有权收尾，一句话一条：**

| 动作 | 读什么 | 判据 |
| --- | --- | --- |
| 记回执（`record_notice`） | 当前 owner | `session_id` 与 `target_session_id` 都等于 `tickets.owner_session_id`，否则 `NOT_COORDINATOR` / `NOT_TARGET` |
| 代答一个问题（`answer_ticket`） | 当前 owner | `answered_by_session_id` 等于当前 owner（AW-122 起与回执同一把尺）；origin 不再能答 |
| 合并（`merge_ticket`） | 不认会话，只看 `done` + `notices` 非空 | 因此等价于「谁有权写回执谁就能合」；已有的合并记录报 `ALREADY_MERGED` |
| 改判据（`revise_ticket`） | 不绑会话，认 `expected_revision` | 由协调会话做；改判据要带 `must_wake` 把在飞的执行会话叫起来 |

**无人值守时不要求回执的 `wake_kind` 落在某个值上。** 没有另一条活会话可读投递回执、可核队列、
可插话，所以「`wake_kind` 必须是 `queued` / `already-active`」「回执要 `delivery=steered`」这类条
在无人值守下是做不到的。改成可满足的写法：**要求的是 `notices` 里那一行写清去向与原因**
（`sent` 一条，或 `failed` 带宿主原话），`wake_kind` 有就照宿主原值记、没有就记 `unknown` 并在
`detail` 里注明是占位。

## 5. 动作二：派验收（`dispatch_review`）

### 前置条件

1. 有单的状态是 `awaiting_review`。
2. 该单**最新提交**存在，且那份提交还没有 `reviews` 行。
3. `dispatch` 里给出 `submission_id` 与 `head_sha`——验收要的就是这两个：验的是哪一份成果、哪一棵树。
   另带 `get_ticket` 回执里 `sessions` 那几项的 `session_url`：验收人要能在同一条会话链里回看执行会话
   与协调会话，而不是只凭提交文字下结论（口径同上，见 `docs/protocol.md` 的那一节）。
4. 这张单**没有在飞的验收**：30 分钟内没有指向这份提交的 `review_dispatched` 事件。
   有就轮到下一张，或者（没有别的活时）这一轮什么都不派。

### 派完之后先落一条事实再建会话

派验收与派执行不一样：派执行有 `claim_ticket` 把状态改成 `dispatching`，下一轮一眼看得出「已经有人在跑」；
派验收不改任何状态，工单还是 `awaiting_review`、提交还是没有 `reviews` 行，所以下一轮醒来看到的现场与
派之前**一模一样**。不记这一笔，同一张单会被连着几轮派第二个、第三个验收人。

```bash
# 先落事实（submission_id 用 dispatch 里给的那一条），再新建验收会话
echo '{"project_id":"ai-workspace","ticket_id":"AW-0xx","submission_id":"<dispatch.submission_id>","reviewer_session_id":"<新建会话 id>","note":"派给新开的验收会话"}'   | python -m task_center --db {{WORKSPACE}}/.data/task-center.sqlite3 review_dispatched
```

它只落一条事件，不改状态、不碰 `reviews`：窗口 30 分钟（`task_center.core.REVIEW_IN_FLIGHT_SECONDS`），
超时还没有验收结论就自动回落成可派。**先落事件、再建会话**：反了就是「会话已经在跑、库里还没有这一笔」，
那正是要补的窗口；落错了（验收会话没建起来）等 30 分钟自动回落，不用手工清。

### 拒绝条件与「不给动作」的两种情形

- **取不到提交**：`awaiting_review` 但库里没有任何提交。验收没有可依据的东西，**停下等人**，
  进 `stop`，不给动作。
- **已经有验收结论**：提交有 `reviews` 行、工单状态还停在 `awaiting_review`。这是状态机慢一步，
  不是没人看——再派一次验收会让第二个人重复判同一份成果。进 `stop`，等人把状态走完。
- **已经派出去、还没回落**：30 分钟内有一条指向这份提交的 `review_dispatched` 事件，说明已经有人在看。
  它不是 `stop`（没出错），也不是候选——这一轮跳过这张单，没有别的活就报 `review_in_flight`。
  事件指向的是旧提交（返工后的新提交还没人看过）时照旧派：那份成果确实没人看。
- **验收人不能是执行会话**：`review_result` 会拒（`PRD-001` §9）。派验收时新开会话，不复用执行会话。
- **判据变了**：`criteria_changed` 不为空时，验收会话要按当前 `criteria_version` 判，
  不能按派单时的旧判据。

验收结论只有两个：`accept` → `done`（下一轮会走到合并），`reject` → `rework`（下一轮会派执行）。
结论由验收会话自己 `submit_result` 之后的 `review_result` 落库，**协调会话不代判**。

## 6. 动作三：合并（`merge`）

### 前置条件

1. 单的状态是 `done`，且 `merges` 表里没有它的行。
2. 它的最新提交记了分支头（`submissions.head_sha` 非空）——合并要合的是一棵树，
   没有分支头就没有可合的东西。
3. 当前检出在目标分支（`master`）上、工作区干净、`git branch -d` 之后没留下残留分支。
   这一条不靠 `next_action` 判，由 `tools/auto_merge.py` 自己查，见下一节。

### 拒绝条件

- **回执没落库。** `auto_merge.py` 第 2 步要求这张单走过回执（`notices` 非空），`failed` 也算走过。
  为空就一步不动地拒。`next_action` 在遇到这种单时会在 `stop` 里写明「先 `record_notice` 再合并」。
- **合并记录已存在。** 直接 `ALREADY_MERGED`，不重复合。
- **合并断在半路。** 已经 `git merge` 成功、只差记录时用 `--record-only` 收口；真失败走 `--ticket`。
  两条路都只走 `tools/auto_merge.py`，不手工补记录（`PRD-013` R10：合并只有一个入口）。
- **测试红、冲突、分支领先目标为 0。** 工具自己回滚到 `pre-merge-<工单号>` 并以非零退出，
  目标分支一动未动。**下一次醒来仍然会给同一个 `merge`**——所以这时必须走「停下来等人」，见 §7。

### 合并流程之前直接做在 master 上的单

库里有一批 `done` 且没有合并记录的早期单：它们是合并流程建立之前直接做在 master 上的，
提交里没有分支头，库里没有可合的东西（`AGENTS.md` 与 `tools/auto_merge.py --list` 都写着
不要替它们补记录）。`next_action` 把它们**列在 `skipped` 的 `no_branch_head` 里并带全部单号**，人读那一行末尾也会
缀一句「另有 N 张……」，不给 `merge`：这一条不派动作，但也不隐瞒——要补记录、要作废、
要就让它躺着，由人决定。

宁可多一行 `skipped`，也不要让这条循环每 15 分钟去撞一次同一张合不了的单。

### 没有可合的树：仓库无改动（`no_repo_change`）

同一个「`done` 但没有 `merges` 行」里还挤着另一种现场（AW-147）：这张单**只改仓库之外的
东西**（本机一条调度的 prompt、一份库里的配置），提交时记下的 `head_sha` 与 `base_sha`
是同一个提交（说明这次尝试根本没造出提交），也从来没有 `ticket/<单号>` 分支。它没有
可合的树，`auto_merge --ticket` 第 2 步必然停（源分支不存在），所以给它 `merge` 就是
每轮派一件永远做不成的事——后面排着的单全被它挡住。

判据是两个事实，**两条同时成立才算**：提交的 `head_sha` 等于 `base_sha`（这次尝试没
造出提交），且仓库里没有 `ticket/<单号>` 分支。任一条不成立、`base_sha` 为空（老提交）、
或者 git 读不动，就归回 `merge`（宁可多列一行，不把单藏起来）。判定只跑 `git rev-parse`，
不写库、不动分支。

**不拿目标分支的 head 当参照（AW-148）。** 以前用「`head_sha` 等于 master 的 head」，那个值
随每一张单合并往前走：AW-146 提交时 `head_sha = base_sha = 2e911e84`，与当时的 master head
相等，判得对；AW-147 一合进 master（head 变 5aa136d），它就退回「真待合并」，`next_action`
又开始派那个走不通的动作。换成 `head_sha == base_sha` 之后，这两个 sha 都是这条提交自己的
事，master 怎么动都不影响结论。不能放宽成「只要没有分支就算仓库无改动」：一张真提交过、
分支又被误删的单会被当成「仓库没改」，真失败从此看不见。

这类单：**不派 `merge`，不写合并记录，也不进 `archived`**。不写合并记录是因为那会变成一条
指向别人合并提交的假记录；不进 `archived` 是因为它的账是清楚的，`archived` 的语义是
「做完了但账对不上」。`next_action` 把它列在 `skipped` 的 `reason=no_repo_change` 里（带单号
与每张单的依据），人读那一行也缀一句「另有 N 张……不派合并、也不该进 archived」；
`tools/auto_merge.py --list` 把它单独列成「仓库无改动」一栏，依据写在同一行。

## 7. 必须停下来等人的三种情况

无人值守的意思是「没人回话时它也能往前走完一步」，不是「任何情况都不叫人」。下面三种必须停：
**不重试、不换路、不改判据、不替人做决定**，落一条消息或一个问题，然后结束本轮。

### 第一种：有在途单挡着（`reason_code=in_flight`）

`dispatching` / `running` / `blocked` 三个状态里有任何一张，就不派下一张。库里默认一次只跑一张单，
这是 `PRD-014` R1 与 `DISPATCH_BUSY` 一起定下的节奏。
**这时要看的不是下一张单，而是这一张**：`in_flight` 里的 `state` 说明它停在哪一步——

- `dispatching`：领了还没绑定会话。要么由派发的会话去 `bind_session`，要么 `recover_ticket`。
  **不许换一个会话接着写**。
- `running`：执行会话在跑。超过阈值没活动由 `python tools/wait_audit.py` 报出，
  不是靠这一轮里 `sleep` 等——轮内 sleep 会押住一条活轮，期间不能纠错、不能响应消息。
- `blocked`：开了工在等一句话。答案是人的事（`answer_ticket`），协调会话只能代记、不能发明答案。
  答完把答案落库、再发一条带 `question_id` 的消息把执行会话叫起来。

### 第二种：工单在等一句话（`blocked` 且问题开放）

`blocked` 不是「还在干」，也不是「要改」——它是「开了工，卡在一个只有人能回答的问题上」。
这张单占着 `active_session` 槽位，所以在它等到答案之前，同项目别的单也领不动。
**这条链上没有自动解**：要么人答，要么 `recover_ticket` 作废这次尝试并让位。
尤其不要用 `send_to_session` 去「催一下」——催不出答案，只会多一次唤醒。

### 第三种：要做的动作被拒（`claim` / `review` / `merge` 报错）

派下去之后收到 `BLOCKED_BY_DEPENDENCY` / `DISPATCH_BUSY` / `STALE_PRD` / `BATCH_OWNED_BY_OTHER`，
或者合并时测试红、冲突、分支领先为 0、`notices` 为空：**这一轮就停在这里**，把原始错误码与那句话写给人看。

- **不许**为了绕过它去改库（改状态、改依赖边、改 `blocked_by`）。
- **不许**改用 `--no-verify`、临时换库、或另开一个会话来绕。
- **不许**下一轮原样再撞一次：同一个动作连续被同一个错误码拒两次，就已经是「等人」的信号，
  不是「再试一次」的信号。

同时这类拒绝要落成可查的记录（`record_notice` / `ask_ticket`），而不是散在一段对话里——
事后查「它为什么停在那儿」时，只有库里的行算数。

## 8. 怎么暂停

**暂停就是让这条循环醒来也算不出动作。** 做法只有一个：建一个标记文件。

```bash
# 暂停整条无人值守循环（默认位置：工单库旁边的 .data/dispatch-paused）
touch {{WORKSPACE}}/.data/dispatch-paused

# 恢复
rm {{WORKSPACE}}/.data/dispatch-paused
```

标记存在时 `next_action.py` 一律退出 `2`、`reason_code=paused`，`human` 里带上标记路径，
**一个动作都不给**。所以：调度侧不需要「暂停」这个功能，它只要照退出码办事；
人也不需要去改配置或停掉库里任何一行，改的是一个文件的有无。

三条补充：

- 标记默认放在**工单库旁边**（`.data/dispatch-paused`），跟着库走，不跟着脚本走——
  在 `.worktrees/<工单号>/` 里跑也能认到同一个位置。要放别处就传 `--pause-file <路径>`。
- **暂停不等于收尾。** 在途单还在库里，`close_gate --check` 照旧拦；暂停只停「派新动作」这一件事。
- **要停某一张单，别用暂停。** 暂停是整条循环的开关；单张单的去留走 `cancel_ticket`（不做了）
  或 `revise_ticket`（改判据），两者都落库、都能事后查到是谁为什么。

## 9. 不在本单范围

- **不启定时任务。** 调度由协调会话在 `tools/next_action.py` 通过验收之后单独建；
  本单只交付「算得准」与「算不出就退 2」。
- **不改 schema、不改 `claim`/`submit`/`review`/`merge` 的既有语义、不改收尾闸门的在途集合。**
- **不自动建会话、不发消息。** 它只输出结论，动作由协调会话照 `dispatch` 里的指向去做。
- **不判断「这张单值不值得做」。** 值不值得是规划期的事（`PRD-014` 的池子与依赖边）；
  到了这里，池子里排着的就是该做的。
