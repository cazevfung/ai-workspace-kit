# 收尾包（closing）

这是「一轮做完之后，怎么算说完了」的唯一正文，与 `docs/intake.md`（一轮怎么算开始了）对称：入口有六节交接包，出口有七节收尾包。两边同一套写法——标题固定、顺序固定、缺一节就由闸门当场失败。

收尾包给要收尾的协调会话看，写在**轮**这一层，不写在工单里。工单的收尾是「验收 + 合并」，一轮的收尾是「目标达成到哪儿、还欠谁一句话」。

## 1. 本轮原话目标

把 `tasks/round.md` 的「本轮目标」原样搬进来，不改写、不摘要。**为什么要搬一遍**：收尾时最容易发生的事是目标被悄悄换成了更好达成的那个；原话与「这一轮实际做了什么」并排放着，换了才看得出来。

## 2. 已完成及证据

一条目标至少一条证据，每条证据写**跑过的命令与输出**，或**可点的落点**（提交 sha、文件绝对路径、验收编号）。写「已完成」不算证据。

## 3. 未做到或偏离

没做到的、做到一半的、做了但和原话目标不一致的，都写在这里。**这一节禁止只写一个「无」**：真为零就要写「无，因为每条目标都有对应证据，见第 2 节」——这句话把「我确认过」与「我没想」分开，闸门按这个形状判（裸「无」「暂无」「待补充」一律非零）。

## 4. 决定不做及原因

原本在范围内、这次明确放弃的，逐条写「做了什么决定 + 为什么 + 谁同意」。和第 3 节的区别是：第 3 节是「没做到」，这一节是「决定不做」——前者是债，后者是取舍。

**发现的问题也算在这里。** 干活时撞见一个不属于本单的缺口，判定它不值一张单，就把「不做 + 为什么」写在这一节；写在这里就是处置过了，第 5 节不必再为它编一条落点。要给它一张单，就按 N31 当场 `create_ticket`（`state=planned`），把单号写进第 5 节。

## 5. 欠 AI 的下一步

下一轮要接手的、已经知道怎么做但这一轮没做的，写成一条条可执行的下一步。写给下一个会话看，所以要有落点（文件、工单、命令），不写「继续优化」。

**这一条由闸门按「每条」判，不再是散文要求。** `python tools/close_gate.py` 会把第 5 节切成一条条，每条至少要有下面三者之一，否则非零退出并点名第 5 节：

| 落点 | 例 |
| --- | --- |
| 工单或 PRD 号 | `AW-108`、`PRD-004` |
| 文件路径 | `tools/close_gate.py`、`docs/closing.md` |
| 反引号里的命令或标识 | `python tools/run_tests.py`、`auto_merge` |

一条都没有（整节空着）同样非零：要么写一条带落点的下一步，要么把「决定不做」写进第 4 节并给原因——两节的分工就是这一条闸门的两半，「补进第二张单」这种既没单号也没路径的写法过不去。

## 6. 欠人的一条可执行动作

**只写一条，而且必须是能做完的动作**：打开哪个文件改哪一行、跑哪条命令、在哪个页面点哪个按钮。写「需要你确认」「请评估一下」不算——那不是动作，是把判断又推回去。

真要人拍板的决策不进这一节，走 `ask_ticket` 落进工单，第 7 节结论写「等一句答复」，把那一句原话写在这里。

## 7. 结论

三档之一，写在正文第一行，逐字匹配：

| 结论 | 意思 | `tasks/round.md` 的状态位 |
| --- | --- | --- |
| `已收尾` | 目标都达成，证据齐，下一轮可以直接接 | `状态：已收尾` |
| `等一句答复` | 只差人给一句话，其余都做完了 | `状态：等一句答复` |
| `需重开一轮` | 目标没达成、或做到一半发现方向要改 | `状态：需重开` |

三档对应的是三种不同的下一步，所以不能用自由文本代替：`已收尾` 之后可以开新的一轮，`等一句答复` 之后只能等人，`需重开一轮` 之后要先重写 `tasks/round.md`。写成「基本做完了」这种话，闸门判不出来，人也判不出该做什么。

## 落点与命名

写到 `tasks/closing-<轮次>.md`，例如 `tasks/closing-R-003.md`；`<轮次>` 取自 `tasks/round.md` 顶部的 `轮次：R-00N`。同一轮只留一份：改结论就改这份文件，不另开 `-v2`。

收尾包进版本库（它是一轮的事实），不进中心库，也不进 `submit_result` 的 `artifacts`——那是工单的成果，这是轮的收尾。

## 在途集合只有一份定义

「还有没有没干完的活」这件事，本轮只有一个答案。在途（`在途集合`）指的是下面六个状态，**`planned` 不在其中**：

| 算在途（会拦住收尾） | 为什么算 |
| --- | --- |
| `dispatching` / `running` | 已经有人接了，正在改 |
| `awaiting_review` | 成果在验收里，同一批文件还会被改 |
| `blocked` | 开了工、在等一句话 |
| `ready` / `rework` | 等人领走：活没干完，只是还没人接 |

**`planned` 不算在途。** 它是「还没轮到、已经在库里排着」：不产生尝试、没有会话在做，所以排着队的单不该把一轮的收尾挡住。2026-11-21 收尾 R-015 时正相反——AW-094 留在 `ready`，钩子连拒三次，最后只能 `cancel_ticket` 才收得了尾；那一张本来就是该被领走的，被取消掉是真的丢了活。`planned` 落库之后这类单有了位置：排着就排着，收尾照收。

**这份定义在代码里也只有一份**：`tools/work_gate.py` 的 `CLOSING_BLOCKING_STATES`（另带 `WAITING_STATES` = `ready` / `rework`，即「在途里没有人在做、只在等人领走」的那两格）。

- `python tools/close_gate.py --check` 从它导入（`IN_FLIGHT_STATES`），自己不写一份；
- 收尾提交的例外（钩子）按它判；
- `python tools/work_gate.py --list` 按它报：stderr 上打一行「在途 N 张（dispatching … / running … / awaiting_review … / blocked … / ready … / rework …）；池子里另 M 张 planned 排着，不算在途」，其中 `ready` / `rework` 不为 0 就非零退出并点名是哪几张。池子里那张单不会被这一行放过就没人看：紧接着逐张点名「池子：<单号> planned，排了 X.X 天，N 条条件」，0 条时写「条件空着」，最老的一张超过 `PLANNED_MAX_DAYS = 7` 天时再报一行 `pool-stale` 并非零退出（不然入口越轻、池子越长，长到没人看就是另一种蒸发）。

以前这里是两份：`close_gate` 只有四个状态，钩子那边六个，于是同一件事两个答案——`--check` 说可以收、提交被连拒三次，而 `--list` 一声不响。现在三处读同一个常量，`tools/test_close_gate.py` 里有一条用例直接断言两边是同一个对象。

## 中心库怎么被发现（一处定义）

三个闸门（`work_gate`、`auto_merge`、`close_gate`）与两个巡检工具（`idle_watch`、`wait_audit`）读哪一份中心库，只由 `tools/center_config.py` 一个文件回答。以前每一处自己写一句 `Path.home() / ".agents" / "center.json"`，于是 `install.py --agents-home <目录>` 装完的工作区里，闸门照样去读 `~/.agents`——那是**另一套库**，实测读到 `{{WORKSPACE}}` 的中心库并报 `SCHEMA_MISMATCH`。库没坏，是找错了，而同一件事写在几个文件里就必然有几个答案。

顺序就下面这七步，前一条不成立才看下一条：

| # | 位置 | 谁写的 | 说明 |
| --- | --- | --- | --- |
| 1 | `--db` | 人当场给的 | 最高优先，脚本与钩子都认 |
| 2 | `TASK_CENTER_DB` | 环境变量 | 钩子、CI、测试用它 |
| 3 | `TASK_CENTER_AGENTS_HOME` | 环境变量 | 一台机器上有多份安装时显式指定用户级目录 |
| 4 | `<工作区>/.agents/center.json` 的 `agents_home` → `<agents_home>/center.json` 的 `db` | `install.py` | 安装时的 `--agents-home` 落在工作区里（不进版本库），闸门按它找库 |
| 5 | `<工作区>/.data/task-center.sqlite3` | `install.py` 初始化 | 工作区自带的库；老安装没有指针，靠这一条 |
| 6 | `~/.agents/center.json` | 老安装 / 默认安装 | 默认档（不传 `--agents-home`）走这一条，与以前逐字相同 |
| 7 | 都没有 | — | 报 `DB_NOT_FOUND`，非零退出，**不新建库** |

三条要记住的后果：

- **第 4 步指丢就到此为止。** 指针写着 `agents_home`，而那份 `center.json` 不在（被挪走、被删掉、装到别的盘又换了机器）时，报 `DB_NOT_FOUND` 并说出缺的是哪个文件。**不回落到 `~/.agents`**：那正是这个单的病根，静默读到另一套库比报错贵得多。同理，也不许为了让它跑起来新建一个空库。
- **默认档不变。** 不传 `--agents-home` 时装的是 `~/.agents`，指针也指它，所以第 4 步读到的就是第 6 步那一份。老安装（没有指针）直接走第 6 步。两种情况下 `work_gate.py --list` 的输出与以前一模一样。
- **沙箱安装默认没有指针（AWK-113）。** `--agents-home` 不是本机真实用户目录、又没给 `--allow-user-config` 时，安装器不写用户级 `center.json`，也不写工作区指针——否则第 4 步会指到一个不存在的文件、当成「指丢」报 `DB_NOT_FOUND`。没有指针就走到第 5 步，读的是本工作区 `.data` 那份库，装出来的工作区照常可用。
- **工作树里回到主检出。** `.agents/center.json` 与 `.data/` 都不进版本库（`kit/.gitignore` 忽略了它们），`.worktrees/<工单号>/` 里自己那份往往不存在；第 4、5 步按 git 公共目录找到主检出再看一遍——它问的仍是同一个工作区。

改了发现逻辑就得改这里，反之亦然：`tools/test_work_gate.py` 的 `CenterDiscoveryTest` 与 `tools/test_auto_merge.py` 的 `CenterDiscoveryTest` 逐条锁住上面七步、指丢时的报错、以及「默认档仍然读 `~/.agents`」。

## 合并放行收尾包，不代它提交

**结论：`python tools/auto_merge.py` 第 2 步的「已跟踪文件无改动」对三个路径放行**——`tasks/closing-*.md`、`tasks/round.md`、`tasks/rounds.md`；其它任何已跟踪文件照旧一步不动地拒绝。放行时它会逐条列出这几个文件、说清它们没有被合进去，并在结尾固定打一行「收尾包仍待提交」。`--dry-run` 同样放行、同样打这一行。

**为什么必须是这三个、为什么只能是这三个。** 收尾包写在合并之前：一轮的最后一两张单合完，这一轮才算完；而收尾包本身只能在本项目一张在途单都没有时提交（见下面「谁来提交收尾包」里的「三条前提同时成立才放行」）。两件事在收尾那一刻互斥——单还没合就不能算收完，而收尾包没写完时删不得也丢不得。于是「先交收尾包再合单」不是更严的流程，是把合并无限期挡住：2026-11-23 一天里为此 stash 了三次（合 AW-118 / AW-119 / AW-122 各一次），每次都要人记住再 `git stash pop`。

**为什么不是「允许工作区有点脏」。** 脏内容会被「合并后再跑一次全量测试」那一场读进去，让一次本来正常的合并变红、被 `git reset --hard` 回滚——那比拒绝合并更贵。所以放行只按**路径与文件名**判（`tasks/` 这一层，不是按目录、不是按后缀，`tasks/plan-*.md` 照旧拦），并且由用例钉住两件事：`tools/`、`task_center/`、`PRD/` 里的未提交改动仍然拒绝；测试不许读那三个文件（`tools/test_auto_merge.py` 用审计钩子核这一条）。

**忘了提交由谁发现。** 合并不会替它记住，也不会替它提交；发现它的是每轮开工的第一条命令与收尾闸门：`python tools/work_gate.py --list` 报「本轮 R-00N 未收尾」，`python tools/close_gate.py --check` 报工作区不干净。两处都指向这一份文件。**不要把它当成「可以永远不提交」**：`git stash` 从此不再是合并的前置步骤（那正是这张单要去掉的），但收尾包该提交的时候还是要提交。

## 谁来提交收尾包

收尾包**单独提交**，不需要 `TASK_CENTER_TICKET`。钩子会把它认成一次「收尾提交：R-00N」，打印这一行就放行。

**先分清两件事：收尾，和改收尾包。** 判据只有一条——`tasks/round.md` 的状态位这次有没有改成 `已收尾` / `等一句答复` / `需重开` 三档之一。

| 暂存区 | 这次提交是什么 | 拿什么放行 |
| --- | --- | --- |
| 收尾包 + `tasks/round.md` 状态位改成三档之一 | 收尾这个动作本身 | 收尾提交例外：本项目在途集合为空即可，不要工单 |
| 只动 `tasks/closing-*.md`，可以带 `tasks/rounds.md` 与 `tasks/round.md` 的状态行；状态位没有改成三档之一（例如给已收尾的轮次补记，或把状态位从三档改回 `进行中`） | 一条普通改动 | 工单：本项目的某张单当前尝试 `running` 且已绑定会话 |

两行的暂存区清单是**同一份白名单**，不是两份：`tasks/round.md` 在两支里都只允许改状态行，每一条增删行都含 `状态：`，轮次行、本轮目标、结束条件一概不许夹带。

第二行是 2026-11-23 补上的。以前只要暂存区里有 `tasks/closing-*.md` 就按收尾提交判，于是「收尾包就是成果本体」的工单在 `running` 期间提交必被 `CLOSING_REJECTED`——AW-124 就是这么被逼到 `git commit --no-verify` 的。**`--no-verify` 不是出路**：那条路没有依据，也没有记录。

**为什么收尾不能走普通工单路径。** `close_gate --check` 要求库里本项目没有任何在途工单；而普通改动的放行要求一张绑定在 `running` 尝试上的工单。这两件事不可能同时成立——收尾包只能在「一张单都不在飞」的时候提交，普通提交只能在「有一张单在飞」的时候提交。所以收尾提交必须像合并提交那样，是一条被显式承认的例外。

**例外放开的三个路径。** 暂存区里的每一条都必须是下面三种之一（两支都用这套白名单，改收尾包的那一支也不许夹带）：

- `tasks/closing-<轮次>.md`（收尾包本身，至少一份）；
- `tasks/round.md`，且每一条增删行都含 `状态：`（只许改状态位）；
- `tasks/rounds.md`（历史账本那一行）。

**收尾提交：三条前提同时成立才放行。**

1. 暂存路径全部落在上面三个路径内；
2. 本项目在途集合为空（`dispatching` / `running` / `awaiting_review` / `blocked` / `ready` / `rework` 全空；`planned` 不算，见「在途集合只有一份定义」）；
3. `tasks/round.md` 的状态位改成三档之一，且至少有一份 `tasks/closing-*.md`。

而且 `tasks/round.md` 顶部读得到 `轮次：R-00N`、中心库读得出来。拿不到暂存区、读不了库、读不到轮次行，一律拒绝并写明原因：一处读不出来就放行，等于给所有提交开一条「没报错就是通过」的旁路。

**收尾包改动：拿什么证明有工单背书。** 要同时满足两条，缺一条就拒：

1. 只有 `tasks/closing-*.md`（可以带 `tasks/rounds.md` 与 `tasks/round.md` 的状态行），**没有别的东西**——`tools/`、`task_center/`、`PRD/` 里任何文件夹带进来都拒；`tasks/round.md` 里状态行以外的任何一行（轮次行、本轮目标、结束条件）同样拒；
2. 本项目有一张工单，`get_ticket` 里 `current_attempt` 的尝试 `state=running` 且 `session_id` 非空——也就是真的有个会话正在做这件事。`ready` / `rework`（等人领走）、`awaiting_review`（成果在验收）、`done`（已结束）都不算。

这条判据只有一处实现：`tools/work_gate.py` 的 `ticket_backing()`，与 `verify()` 里那个「已绑定」是同一个条件（钩子拿不到调用方的会话号，能核的就是「有一张单正在被某个会话执行」）。**要它点名的是哪张单**：放行时打印 `收尾包改动：R-00N 的收尾包由工单 AW-xxx 背书（当前尝试 … 在 running、已绑定会话 …）`。

**借这一支把状态位从三档改回 `进行中`：允许，但它仍是一条普通改动。** 重开一轮是真实需要——上一轮写成「已收尾」之后又来了一张单，状态位得改回 `进行中`。这一支能带 `tasks/round.md` 的状态行，所以它走得通，代价与别的收尾包改动一样：必须在 `tasks/round.md` 的状态位上动手、每一增删行都含 `状态：`、并且有一张 `running` 且已绑定会话的工单背书。它换不到收尾提交那条例外——状态位不在三档之一，钩子就不把它当收尾；本项目没有一张 `running` 且已绑定会话的工单时，它照样被拒。反方向（`进行中` → 三档之一）不是这一支：那是收尾本身，按上面「三条前提同时成立才放行」判。用例钉在 `tools/test_work_gate.py`：`test_closing_packet_change_may_reopen_the_round_status`（允许，且提示说出真实改动）与 `test_reopening_the_round_without_a_ticket_is_rejected`（没有工单就拒）。

**越界会怎样。** 夹带别的文件、把轮次行或本轮目标一起改、借「补记收尾包」顺手改 `tasks/round.md` 的状态以外内容、或没有工单背书的收尾包改动——都被拒并点名是哪一条。收尾包改动**仍必须有一张工单**：它换来的是「有依据地改收尾包」，不是「收尾包可以随便改」。被拒后不要拆开蒙混，也不要 `--no-verify`。

**为什么钩子不再先看 `TASK_CENTER_TICKET`。** 先看就等于收尾这条例外永远不会触发：收尾提交的定义就是「没有工单能背书」。所以判定顺序是「先问这次提交在不在收尾（状态位动没动），再问有没有工单」。

提交完之后，`python tools/work_gate.py --list` 应该在 `已收尾` / `等一句答复` / `需重开` 三种状态上退出 0，而且库里的在途集合要是空的：`ready` / `rework` 留着没人领时它会点名并退出非零（那是没干完的活），`planned` 排着不算（它不进在途集合）。仍然是 `进行中`、而库里已经没有在途单时，它会报「本轮 R-00N 未收尾」并退出非零——这一条是每轮开工的第一条命令。

- **结构非零就是不许说「这一轮结束」。** 缺节、第 3 节裸「无」、结论写成自由文本、状态位是 `进行中` 却想宣告结束，都当场点名缺什么。
- **`--check` 的三条事实各自独立成句。** 工作区不干净（成果在磁盘上、不在版本库里）、中心库里本项目仍有在途工单（`planned` 之外的那六个状态）、`round.md` 的状态位与第 7 节结论不一致——任意一条不成立都不能收尾。
- **闸门只管形状，不管真假。** 证据是不是真跑过、第 4 节的取舍是不是合理，脚本判不了，那一步由独立验收和人看。

## 三条现场事实为什么在闸门里

结构齐了不等于这一轮真能收：AW-067 收尾时 `tasks/plan-019` 只在磁盘上、没进版本库，验收时才发现；也出现过多张单同时在途、却有人以为这一轮已经结束。这两件事都有确定性的判法（`git status --porcelain`、库里的在途工单），所以放进闸门，不写成提醒。
