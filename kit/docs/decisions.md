# 随包口径：反复被引用的四条判据

这份文档是**随套件发布的**，与 `PRD/` 里的需求文档分工不同：需求文档记「为什么这么定」，
这里只记**照着就能做、做完能当场判对错**的口径。它存在的原因是这些口径被跨文件的注释、
计划与 skill 反复引用，而引用方不该依赖某个人本机上的需求文档——包里没有那份文件，
引用就会指向不存在的东西。

**改这里的任何一条，先全文搜同一条判据还出现在哪**：`AGENTS.md` 第六条、
`docs/protocol.md` 的「回信落库」与「`blocked`：工单在等一句话」两节、
`docs/skill-loading.md`，以及 `skills/` 下引用本文件的 SKILL.md。一处改了、别处留旧话，
就是新的假话。

四条口径对应四类事：**消息走哪条通道**（三档）、**做完怎么回**（回执一条）、
**怎么算送到**（送达判据）、**项目怎么算一个项目**（项目接入面）。

## 消息通道三档

一条消息该走哪一档，按「它要影响哪一轮的产出」问，不按话题重不重要问。

| 档 | 入口 | 作用于哪一轮 | 回执判据 |
| --- | --- | --- | --- |
| 一 入队 | `send_to_session`（带 `target_session_id`） | 目标**当前这一轮之后** | 只有 `created` 是没打中；其余任何非空原值都算打中已存在的会话 |
| 二 插话 | `steer_session` / `steer_session_queued_message` | 目标**正在进行的这一轮** | `delivery=steered` |
| 三 同步提问卡片 | 提问卡片 | 占住**提问者自己的这一轮**，外部进不来 | 没有外部回执 |

四条判据，顺序问下来，前一句能定就不往下问：

1. 要改的是目标**当前这一轮**的产出吗（纠错、补约束、撤掉它刚做的那一步）→ 档二。在这里入队等于让它赶不上。
2. 在当前这一轮**结束之后**处理就行吗（下一件事、追加任务、结果回传）→ 档一。
3. 是不是**要人拍板**，且这个决定事后要能被别的会话查到 → 档三禁用，走 `ask_ticket` 落库 + 结束本轮。
4. 1 与 2 判不出来（拿不准会不会改变这一轮）→ 按 1 处理。插错只多一条消息，漏插会让整轮产出按旧指令做完。

**档一只有一类失败：`created`。** `queued` / `resumed` / `already-active` 与枚举外的取值
一律照记、不得自行映射成近似的三值之一——枚举比宿主的取值窄，映射就把事实换成了推定。
「发过去了」不等于「它这一轮看到了」，这是分档的第一个理由。

**档三为什么禁。** 卡片占住提问者本轮，本轮不结束就没有消费队列的时机，别的会话连排队都进不去；
问题也不进工单库，别人读 `get_ticket` 看不出这张单是在干还是在等。要让一个人拍板，
正确动作是 `ask_ticket` 落库、结束本轮，等答案回来再唤醒。

## 回执一条

执行会话做完只发**一条**回执给协调会话，正文写**工单号 + 状态 + 提交 sha 或 review id**，
**不写 `wake_kind`**，也不为它再补第二条。理由不是「省事」而是「写不准」：那个值只出现在
`send_to_session` 的发送回执里，一条消息写不出自己这一条的发送结果；把它写进正文，
库里的值就是从推定来的。

协调会话一侧：

- **一张单最多一条 `sent`。** 第二次记 `sent` 是重复回执，应当被判失败，不是覆盖。
- **落库时 `wake_kind` 填 `unknown` 占位。** 这条路径上协调会话取不到宿主原值，所以填 `unknown`
  并在 `detail` 里写明「本次 `wake_kind` 未取到，`unknown` 是占位」——这一列只校验形状，
  它自己记不下「这是推定」，省了 `detail` 就再也分不出这一行是事实还是推定。宿主直接把值报给
  协调会话时（例如别处调 `record_notice`），才按原值记。
- **`failed` 可以多条，也算走过回执。** 每条的失败原因写在 `detail` 里；回执没送达但原因记下来了，
  否则事后查不出「到底发没发」。
- **终态只落库，不唤醒。** `done` / `rework` 记进库即可。只有三种情况该发消息：`wake_kind=created`
  误建了任务、工单 `blocked` 在等人一句话、以及刚落了问题的 `ask_ticket`。
- **验收后的合并要看这条有没有走过。** 一张单的回执记录为空时不许记合并；先补一条 `sent`，
  或记一条写清原因的 `failed`。

## 送达判据

**看会话列表，不看投递回执。** 协调会话发完收到回执后，按工作目录列一次会话，看有没有
多出**标题就是这条回执正文**的新任务：没有多出即算送达；多出了就是宿主把回执当成了新建任务。

- **`created` 是有后果的那个值。** 它说明消息根本没到原会话；动作是先停掉误建的那条任务，
  再带 `target_session_id` 重发。`queued` / `resumed` / `already-active` 只表示消息进了原会话，
  没有副作用。
- **入队之后必须核队列。** 目标已经跑完过一轮、而自己那条还留在队列里，就是「该插没插」；
  这一轮已经按旧指令做完了，这是已发生的损失，不是待观察的风险。补插的判据是
  `delivery=steered`；仍是 `queued` 说明这一轮已收尾、插不进去，回到三档判据重新选。
- **自身会话标识向宿主取，不从路径猜。** 执行会话取自己的标识，取到之后按工作目录反查一次标题，
  对得上才拿去 `bind_session`。禁止从临时目录名或任何路径拆一个字符串当标识。

## 项目接入面

**`root` 是身份，`project_id` 是标签。**

- **身份只认绝对路径，且唯一。** 「这是哪个项目」由目录的绝对路径回答。标签（`project_id`）
  是给人看的，可以重名、可以改、给错了也不拦住开单。
- **列表即范围，登记只是记账。** 能不能在某个目录开单，取决于那个目录是不是人真在那里工作，
  不取决于库里有没有一行登记。所以 `create_ticket` 允许带着 `root` 顺手记一行再开单，不必先单独登记。
- **同一路径重复登记复用原记录**，不报冲突、不改已有标签；把自己的标签指向第二个目录才报冲突。
- **标签给错了**先撤销登记再重登；登记记录里的路径不能就地改，修法就是撤销重登。
- **有工单的项目不许撤销登记**，否则工单指向一个不存在的项目，事件与验收记录随之失据。

**仓库里同时存在多个同名目录是正常情况**（多个伙伴工作区都叫 `workspace`）。标签重复不阻断派发，
回执与清单要靠 `root` 或宿主里的别名分辨，不能只看 `project_id`。
