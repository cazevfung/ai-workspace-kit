# 怎么把它分享给任何人：三种载体与最终选择

这份文档回答一个问题：**一个已经跑稳的 AI 工作区，用 GitHub 项目、Cindy 插件、还是打包成 skill 分享最好？**
结论先说：**主载体是 GitHub 仓库 + 一键安装脚本**；技能包与插件做成薄入口，负责把人带到仓库，而不是各自承担一次完整安装。

判断依据不是「哪种更时髦」，而是这套工作区**到底依赖什么才能跑起来**。

---

## 1. 这套工作区依赖什么

把依赖拆开看，会发现问题不在「提示词」这一层：

| 依赖 | 具体是什么 | 谁提供 |
| --- | --- | --- |
| 运行时 | Python 3.10+（核心只用标准库） | 用户机器 |
| 文件系统 | 工作区目录、`.data/task-center.sqlite3`、`tasks/`、`PRD/` | 用户机器 |
| 版本控制 | git 仓库、`.worktrees/<工单号>` 工作树、commit 钩子 | 用户机器 |
| 本地配置 | `~/.agents/center.json`（中心库指针）、`~/.agents/skills/` | 用户机器 |
| 技能 | 25 个 `SKILL.md`（纯 Markdown + 少量脚本） | 本套件 |
| 宿主能力 | 创建会话、`send_to_session`、`get_current_session_id`（派发环节） | Cindy 等宿主 |

关键点：**价值有一半长在文件系统上**。工作树隔离、提交钩子、本地库、闸门的退出码——
这些不是「一段说明」，而是真实的外置状态。任何只能在沙箱里传文本的载体，都装不全这一半。

---

## 2. 三种载体的能力边界

### A. GitHub 仓库 + 安装脚本

能做的：

- 交付全部文件：核心代码、四道闸门、376 项测试、25 个技能、文档、PRD 模板；
- 在用户机器上执行真实副作用：建目录、写 `~/.agents/`、`git init`、配置钩子、初始化库；
- 版本化与可审计：别人能看到每个规则为什么存在，也能 fork、提 issue、回滚；
- 跨 agent：只要宿主读 `AGENTS.md` 与 `~/.agents/skills`，Cindy / Claude Code / Codex 都能用。

代价：要求用户会 git clone、有 Python。可以用一行命令或 `install.ps1/.sh` 把它降到最低。

### B. Cindy 插件（`.cindy` / `ghost.json`）

能做的：在 Cindy 里有一个可发现、可更新的入口；可以调用宿主 API；可以做界面与工具。

做不到的（或代价很高的）：

- 插件运行在宿主沙箱内，**默认改不了用户主目录与 git 配置**；装工作树、配 `core.hooksPath`、
  写 `~/.agents/skills` 这类动作要么被沙箱挡住，要么需要用户逐项授权，体验远不如一个脚本；
- 只有 Cindy 用户能用；Claude Code / Codex 用户拿不到；
- 插件包适合「工具与连接器」，不适合「往磁盘上铺一个项目骨架」；
- 每改一次工作区规则，都要重新打包、发版、过审，而仓库只需要一次 `git pull`。

结论：插件可以是**入口之一**（点一下 → 调起安装脚本），但不该是唯一载体。

### C. 打包的 skill（SkillHub / `.skill`）

能做的：一句话装进 agent，发现成本最低；适合「先试试」的人。

做不到的：

- 技能本质是**给模型看的说明**，不是安装器。它可以带 `scripts/` 与 `assets/`，
  但「装 25 个技能 + 初始化数据库 + 配 git 钩子」这类动作仍需调用外部脚本；
- 技能目录里塞一个完整工作区（几百 KB 到几 MB）会让技能更新变成大包更新，
  也不符合技能「发现便宜、按需加载」的设计；
- 技能没有版本化的工作区代码，修复一个闸门 bug 要重发整个 skill。

结论：技能是**分发引导**，不是**安装载体**。把它做成「一句话 → 去 clone 并运行安装器」最合适。

---

## 3. 最终方案：一个主载体 + 两个薄入口

```
GitHub 仓库（唯一真相）
  ├── install.py / install.ps1 / install.sh   ← 完整安装（主渠道）
  ├── skills/                                 ← 25 个技能，随仓库分发
  ├── kit/                                    ← 工作区骨架
  └── plugin/                                 ← 可选：Cindy 插件的薄包装（调起安装器）
skills 市场的入口 skill（指向仓库）              ← 薄入口，不复制内容
```

三条原则：

1. **只有仓库能装全。** 插件与技能负责「让人知道并愿意装」，不负责「装完整」。
2. **安装脚本是唯一安装逻辑。** 三个入口最终都调用同一个 `install.py`，
   避免三套逻辑各自漂移。
3. **技能与工作区同版本发布。** 技能在 `skills/`，随仓库 tag 一起走；
   不单独维护一份会过期的副本。

---

## 4. 「任何人」具体指哪几类人

| 人群 | 入口 | 体验 |
| --- | --- | --- |
| 用 Cindy 的人 | 仓库 README 或插件入口 | clone → `python install.py` → 工作区出现在项目列表 |
| 用 Claude Code / Codex 的人 | 仓库 README | 同上；技能装到 `~/.agents/skills`，用 `--link-agents` 顺带链接到 `~/.claude` 与 `~/.codex` |
| 只想先试技能的人 | 市场里的入口 skill | skill 告诉 agent「clone 仓库并运行安装器」，不复制内容 |
| 完全不用 agent 的人 | —— | 这套系统对他们没有意义；它本来就要求一个会读 `AGENTS.md` 的宿主 |

---

## 5. 为什么不直接把原工作区打包

原工作区里有大量项目专属内容：真实工单、验收记录、个人路径、业务 PRD。
直接打包会把别人的数据一起发出去，也会让新用户一进来就面对几百条不属于他的记录。

套件的做法是：

- **代码与技能**：原样带走，只把本机绝对路径替换成安装时注入的 `{{WORKSPACE}}`；
- **文档**：保留规则与「为什么」，去掉具体工单号、日期与本机路径；
- **数据**：不带走任何 `.data/`、`.worktrees/`、真实 PRD 与 tasks 历史；
- **设计史**：原始 PRD 与 AGENTS 记录放在 `design/`，满足「想知道为什么」的读者，不参与安装。

`maintainer/sync_from_origin.py` 记录了这个同步过程：改了什么、复制哪些目录、如何替换路径。
上游规则更新时，重跑它再人工抽查即可。

## 6. 已知限制（诚实清单）

- **派发仍需宿主**：`claim_ticket` 之后「新建一个执行会话」这一步依赖 Cindy 的
  `send_to_session`；其他宿主需要自己补这一步，或手工开会话再 `bind_session`。
- **跨平台差异**：Windows 用目录联接（junction）链接技能，macOS/Linux 用符号链接；
  `install.py` 已按平台处理，但没有在所有发行版上穷举测试。
- **没有远端推送**：合并只在本地 `master` 上进行；要接 GitHub 远端，按你自己的仓库流程加。
- **技能里仍有中文**：面向中文用户；英文用户可读 `README.en.md`，技能内容暂未翻译。
