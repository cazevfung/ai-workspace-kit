## 1. 要解决什么问题

工单跑到一半，需要人给一句话才能继续：选 A 还是 B、这个口径对不对、这批数据从哪来、这条差异算不算缺陷。现在的做法只有一种——执行会话在聊天里问一句，然后等。它会坏在三个地方，而且这三处都在仓库里有痕迹：

1. **问了没有记录。** 答案只活在某个会话的聊天记录里。协调会话读 `get_ticket` 看到的是 `running`，判断不出这张单是「正在干」还是「在等人」。`docs/protocol.md` 末节「尚未实现」把「阻塞求助」列在里面，这是它具体指的那件事。
2. **等待可能把本轮占住。** 同步提问卡片会让这一轮停在原地，连带收不到协调会话的恢复指令、收不到人的补充说明。plan-006 的派发消息里专门叮嘱过「不要用提问卡片把本轮占住」，因为那是实测撞到过的坑。
3. **没人能接管。** `recover_ticket` 要求核对当前尝试，但「该不该停止等待」这个判断恰恰在被卡住的那个会话里做不了——它正卡着。于是卡住的单只有一种结局：人自己想起来了。

现有的工单状态没有一个是「在等一句话」：`ready` / `dispatching` / `running` / `awaiting_review` / `done` / `rework` / `cancelled`。用 `rework` 表达等待会把「要改」和「要答」混成一件事，用 `running` 表达则等于假装还在干活。`tasks/plan-006-并行冲突与决策通道.md` 的「未决」节把这件事剩下的三个岔口点名列了出来：`blocked` 记在工单上还是尝试上、谁能答、进 `blocked` 之后算不算占用活跃尝试。本文件就是回答这三条，外加两条同源的（唤醒链路、与 `recover` 的关系）。

## 3. 角色分工

- **协调会话**：派发、收口、报回执。它能在人给不出答案时**转述**人的结论，转述必须留凭据（4.6）。它不得替人**决定**内容：`answer` 字段写的是「人说了什么」或「人明确授权我怎么处理」，不是协调会话自己的偏好。
- **执行会话**：提问、落库、结束本轮、被唤醒后读回答案继续干。它不得回答自己的问题（`SELF_ANSWER`），也不得自己 `recover_ticket` 解自己的封。
- **验收会话**：不参与答题。它读 `get_ticket` 时应当能看到「这次尝试在什么时候问过什么、谁答的、答案是什么」，这是它判断「成果是不是按最终结论做的」的依据。
- **人**：唯一的最终决定者。入口是聊天（点卡片或回消息），不是数据库；落库这一步由会话或协调会话代做，凭据见 4.6。

### 4.1 R1：`ask_ticket` 提问

| 字段 | 必填 | 类型与边界 | 说明 |
| --- | --- | --- | --- |
| `project_id` | 是 | 字符串 ≤200 | 工单所属项目 |
| `ticket_id` | 是 | 字符串 ≤200 | 工单号，全局唯一 |
| `attempt_id` | 是 | 字符串 ≤200 | 必须是 `tickets.current_attempt`，不是它报 `STALE_ATTEMPT` |
| `session_id` | 是 | 字符串 ≤500 | 必须等于该尝试的 `attempts.session_id`，否则 `SESSION_MISMATCH` |
| `question` | 是 | 1–2000 字符 | 一句话到一小段：要决定什么、有哪几个选项、各选项的后果是什么。只写「怎么办」不算合格提问 |
| `options` | 否 | 0–6 项 `{"id","text"}`，`id` ≤20 且不重复，`text` ≤200 | 空数组合法与不传等价，表示开放题。选项只用于让人一眼可选，不是答案的枚举约束——`answer` 是自由文本，可以选「A」，也可以写「都不选，改成 C」 |

结果与副作用：返回 `question_id`、`state`（`blocked`）、`asked_at`。写一条 open 问题；`attempts.state` 由 `running` 改 `blocked`；`tickets.state` 由 `running` 改 `blocked`；`revision` **不变**。

`revision` 不变是刻意的：`revision` 表达的是「需求代次」——`revise_ticket` 才递增它。等待一个字不是新代次，如果这里也递增，那么每一次提问都会让基于旧 revision 的校验全部失效（`expected_revision`、`STALE_REVISION`），唤醒后必须先重新领取才能继续，这跟「接着刚才那次尝试干」是矛盾的。

### 4.2 R2：`answer_ticket` 回答

| 字段 | 必填 | 类型与边界 | 说明 |
| --- | --- | --- | --- |
| `project_id` | 是 | 字符串 ≤200 | 与工单所属项目一致，否则 `PROJECT_MISMATCH` |
| `ticket_id` | 是 | 字符串 ≤200 | 回答哪张单 |
| `question_id` | 是 | 字符串 ≤200 | 必须是该工单当前 `open` 的那一条，否则 `QUESTION_MISMATCH` |
| `answer` | 是 | 1–4000 字符 | 人的结论原文，允许带理由。不要求格式，也不从选项里反推 |
| `answered_by` | 是 | 枚举 `human` / `coordinator` | 谁答的。这是自报字段，见 4.6 的诚实边界 |
| `answered_by_session_id` | 条件必填 | 字符串 ≤500 | `answered_by=coordinator` 时必填；`answered_by=human` 时必须不传 |
| `prd_sha256` | 是 | 64 位十六进制 | 回答所依据的需求版本，从 `get_ticket` 的 `prd_sha256` 原样抄。与工单当前值不同报 `STALE_PRD` |

结果与副作用：返回 `answer_id`、`question_state`（`answered`）、`ticket_state`（`running`）。写一条答案；问题由 `open` 改 `answered`；`attempts.state` 由 `blocked` 改回 `running`；`tickets.state` 由 `blocked` 改回 `running`；`revision` 不变。

必须写明的一点：**工单回到 `running` 只代表「库里不再等答案」，不代表那个会话已经在跑。** 核心没有宿主适配层（`docs/protocol.md`：「本版只实现第1、3、4、6步的本机记录和校验」），它不知道会话是否还活着。会话活着这件事由唤醒方用 `list_sessions` 核对，见 4.5。

### 4.3 R3：错误码与触发条件

新增四个码（`ALREADY_ASKED`、`QUESTION_MISMATCH`、`NOT_COORDINATOR`、`SELF_ANSWER`），其余复用既有码，不另造同义码（`INVALID_STATE` 已经覆盖「状态不对」，不要为「不在 running」发明一个 `TICKET_NOT_RUNNING`）。

| 错误码 | 触发条件（给定…则…） | 调用方处置 |
| --- | --- | --- |
| `INVALID_STATE` | 给定 `tickets.state` 不是 `running`（例如还在 `dispatching`、已 `awaiting_review`、已 `done`、已 `blocked`）且调用 `ask_ticket`，则拒绝 | 读 `get_ticket` 看它在等什么；已 `blocked` 说明问题已经提过了，去 `answer_ticket` 而不是再问一个 |
| `STALE_ATTEMPT` | 给定 `attempt_id` 不等于 `tickets.current_attempt`，或该尝试的 `revision` 与工单当前 `revision` 不同（即尝试已被 `supersede`、被 `recover` 作废、或被 `revise` 换掉），则两个操作都拒绝 | 不要再拿旧编号重试；旧尝试的问答记录只作为审计，继续干活要走 `recover_ticket` + 重新领取 |
| `SESSION_MISMATCH` | 给定 `session_id` 与该尝试已绑定的 `attempts.session_id` 不同（大小写不同也算不同，见 `docs/protocol.md`「会话标识与工单标识」），则 `ask_ticket` 拒绝 | 用真正绑定的那个会话提问；不要「换个标识凑一个」 |
| `ALREADY_ASKED` | 给定该尝试已有一条 `open` 问题，又调用 `ask_ticket`，则拒绝 | 一条问题只问一件事。要追加，就在唤醒后正常说话或另开一条新问题（先把当前这条答完） |
| `QUESTION_MISMATCH` | 给定 `question_id` 不存在、不属于该工单、或已经不是 `open`（`answered` / `voided`，例如在被 `recover_ticket` 作废之后答案才到），则 `answer_ticket` 拒绝 | 读 `get_ticket` 的问题列表，确认真实存在且仍在等答案的那一条；问题已作废就不要再补答案，答案本身过期了 |
| `PROJECT_MISMATCH` | `project_id` 与工单所属项目不一致 | 核对项目归属 |
| `STALE_PRD` | `answer_ticket` 的 `prd_sha256` 与工单当前 `prd_sha256` 不同（需求在等待期间被改过），则拒绝 | 答案依据的需求已经变了。让协调会话决定：要么按新需求重新提问（`recover` 后重开），要么先 `revise_ticket` 再派发 |
| `NOT_COORDINATOR` | 给定 `answered_by=coordinator` 且 `answered_by_session_id` 不等于该尝试的 `coordinator_session_id`，则拒绝 | 只有派发这张单的协调会话能代答；别的会话要答，走 `answered_by=human` 转述人的原话，或让原协调会话来做 |
| `SELF_ANSWER` | 给定 `answered_by_session_id` 等于该尝试的 `session_id`（执行会话回答自己的问题），则拒绝 | 这是自己给自己拍板。要么等人答，要么把结论交回协调会话 |
| `INVALID_INPUT` | 未知字段、缺必填字段、`answered_by` 不在枚举内、`answered_by=human` 却带了 `answered_by_session_id`、选项 `id` 重复或超限 | 照字段表核对；本表是闭集，多传字段一律拒绝，不静默忽略 |

### 4.4 R4：`blocked` 记在哪一级，与 `active_session` 唯一索引是什么关系

**结论：两处都写，但权威在工单级。** `tickets.state='blocked'` 是对外的唯一状态；`attempts.state='blocked'` 只说明「这一次尝试卡住了」。理由有三条，都可以在代码里指到：

1. **可见性只在工单级。** `get_ticket` 与 `list_tickets` 返回的主体是 `tickets` 行，`attempts` 是它下面的数组。只记尝试级，另一个会话（协调会话、验收会话）查 `list_tickets` 时看不到任何「在等答案」的痕迹，问题 1 就没解决。
2. **只记工单级会丢归属。** `recover_ticket` 之后工单回到 `ready`、`current_attempt` 置空，如果尝试上没有 `blocked` 这个中间态，事后就无法区分「这次尝试是被人答完继续的」还是「这次尝试被作废了」。
3. **尝试级的 `blocked` 必须被显式列进作废语句。** `_invalidate` 现在只把 `state IN ('dispatching','running','submitted')` 的尝试改成 `superseded`；`blocked` 不在这张表里，一旦加上这个态却不改这条语句，`recover_ticket` 之后库里会留一次「已作废、但看起来还在等答案」的尝试。这是实现单必须一起改的两行之一（另一行是 `blocked` 进 `recover_ticket` 的允许状态集合，见 4.7）。

**与 `active_session` 唯一索引的关系：`blocked` 占用活跃尝试。** 这个索引现在的定义是：

```sql
CREATE UNIQUE INDEX active_session ON attempts(session_id)
 WHERE session_id IS NOT NULL AND state IN ('running','submitted');
```

结论是把 `'blocked'` 加进它的谓词，变成 `state IN ('blocked','running','submitted')`。这不是随手收紧，而是因为「不占用」会立刻产生一个具体的坏结果：如果把 `blocked` 排除在索引之外，被卡住的会话就能去领别的单；等答案到达、`answer_ticket` 把那一次尝试从 `blocked` 改回 `running` 的那一刻，同一个 `session_id` 上就同时存在两条 `running` 尝试，正好撞这个唯一索引——一条合法的答案会以 `CONFLICT` 收场。想绕过它只有两条路：让答案静默降级成 `ready`（丢掉「哪次尝试在等」），或者不再把尝试改回 `running`（那么唤醒后就没有可继续的尝试）。两条都写不出干净语义，所以选择让索引认这个态。

于是「进 `blocked` 后同一会话还能不能领别的单」的答案是：**不能。** 需要说清它约束的是谁——领单不是执行会话的动作，它只被派发；真正被约束的是 `bind_session`：任何会话若拿同一个 `session_id` 去绑定另一张单的新尝试，会在索引上得到 `CONFLICT`。代价是把那个会话闲置，而不是把吞吐堵死：新工单本来就该派给新会话（`docs/protocol.md`「派发的载体」），所以闲置一个等答案的会话不损失并行度。解封的正规手段是 `recover_ticket`（4.7），它会 `supersede` 掉这次尝试、释放索引槽位。

### 4.5 R5：答案落库后靠什么把会话叫起来

先写一段接口事实，它是整条链路的约束条件，2026-11-17 用 `cindy_helper` 的 `list_tools` 逐项核实过：

- `ask_user_question_async` 的入参只有 `questions[{question, options}]`，**没有目标会话参数**；回执是 `request_ids` 与 `pending_count`，不是答案。
- `manage_user_questions` 只有 `action: list | withdraw`，**没有 answer 动作**；描述写的是「your current task's unanswered asynchronous questions」——作用域是本任务自己。
- 因此不存在「拿另一个会话的 `request_id` 替它点掉它的提问卡片」的入口。卡片只能由用户在提问者那一侧点。
- 更关键的一层：就算能点，答案也只落在提问者的聊天里（`ask_user_question_async` 的说明是「answers arrive as user input; a later answer can start a new turn」）。工单读不到聊天，答案等于没有记录——这就退回了问题 1。

**所以卡片不能充当决策通道的载体，唤醒只能靠一条新消息。** 这不是设计偏好，是接口现状推出来的唯一可行路径。链路分六步：

1. 执行会话调用 `ask_ticket`（4.1）。工单与尝试都进 `blocked`，问题落库。它**结束本轮**——不是「等在原处」，而是本轮结束；占住的本轮收不到任何后续消息，这是 4.1 与本节共同的前提。
2. 人看到（或协调会话读到 `list_tickets` 里的 `blocked`）之后给出结论。谁把它写进库见 4.6：人或协调会话调用 `answer_ticket`。
3. 写库的那一刻起，答案的权威就在库里。协调会话随后用 `send_to_session` 的 **jump 模式**（传 `target_session_id`，即创建回执里那个执行会话 id）投递一条唤起消息。目标在跑就入队、已关闭会自动 resume，不需要新的宿主能力。回执里的 `wake_kind` **按宿主原值记**：`queued`、`resumed`、`already-active` 都是见过的取值，枚举外的也照记，调用方不得自行映射成三值之一（枚举比宿主窄，映射会把事实换成推定）；唯一被特判的是 `created`——它是失败信号，见第 6 步。
4. 会话醒来后读 `get_ticket`，从这次尝试上读回问题与答案（`questions` / `answers` 两个数组，与 `attempts`、`submissions`、`merges` 并列），按答案继续干，最后 `submit_result`。
5. 唤起消息里**只放 `question_id` 与一句指令**（例如「AW-0xx 的 q-0xx 已答，读回后继续」），不复制答案正文。答案复制进消息就有第二份真相，而它不会随库里的修订一起变；读错副本比读不到更糟。
6. 投递失败按失败码处置：`ARCHIVED` / `DELETED` / `NOT_FOUND` 说明原来那个会话已经不在，**不许换一个会话接着写**（成果、尝试、提交都绑在那个会话标识上，换人就等于伪造 `SESSION_MISMATCH` 之外的第二条真相），只能走 `recover_ticket` 重新派发；`queued` 不需要重试（任何非 `created` 的宿主原值同理，例如 `already-active` 表示目标当时就在跑），等它当前这一轮结束；`AGENT_NOT_READY` / `HOST_NOT_READY` 稍后重试同一条消息，不要重复 `answer_ticket`。回执里出现 `created` 时，那是唯一被特判的 `wake_kind`：宿主把这次投递当成了新建任务，回执没有到达任何人，要停掉那条误建的任务再带上 `target_session_id` 重发。

### 4.6 R6：谁能答，代答凭据落在哪

**结论：人与协调会话都可以答，但两者走不同的 `answered_by`，凭据落在答案字段里，不落事件。**

- `answered_by='human'`：`answered_by_session_id` 必须为空。这是诚实边界——库里无法验证「这一句真的是人说的」，按本仓库一贯口径（`docs/protocol.md`「不代表已验证宿主身份」「不是身份认证」），它是自报字段。它的作用不是防伪，是让后来的人看得出**这条结论有没有被转述**：`human` 表示「这是人给的原文」，`coordinator` 表示「这是协调会话代记的」。
- `answered_by='coordinator'`：`answered_by_session_id` 必填，且必须等于该尝试的 `coordinator_session_id`，否则 `NOT_COORDINATOR`；若它等于 `attempts.session_id`，则是执行会话自答，报 `SELF_ANSWER`。代答的权力来自「谁派的这张单」，不是来自「谁能读到这个库」。
- **凭据落在答案字段，不落事件。** 位置是 `answers` 表的两列 `answered_by` / `answered_by_session_id`。理由：`events.detail` 存的是回执快照（`core.py` 里 `packed({"request_id": …, "result": …})`），它的用途是操作流水，不是查询入口；把「谁答的」只写进事件，将来查一条结论要解 JSON 回执，而两个会话的写法未必一致。代价是 `answers` 是新增表，需要 schema 6；这是实现单的成本，本版只把落点定死。事件仍然会自动留一条 `answer_ticket` 回执（所有写操作都写事件），它带 `answer_id`，与答案是引用关系而不是重复存储。
- **一条问题只接受一个答案。** `questions.state` 从 `open` 到 `answered` 是一次性的；本版不提供覆盖、作废或「改答案」操作。答错了走 `recover_ticket` 重开（4.7），问题随之 `voided`。这条限制与 `merges` 只允许一条记录同源：允许覆盖，就等于让「当时是基于什么继续的」变成最后一次写入说了算。

### 4.7 R7：答之前能不能 `recover_ticket`，`blocked` 算不算异常

**结论：答之前可以 `recover_ticket`，而且这是人在长时间不给答案时唯一的确定性出口。**

- 现状：`_recover_ticket` 只接受 `dispatching` / `running` / `awaiting_review`。本版要求把 `blocked` 加进去（实现单改一行），并把 `blocked` 加进 `_invalidate` 的状态集合（4.4 的第 3 条理由）。
- 语义：`recover` 之后那次尝试变 `superseded`，它的问题记录保留、标记 `voided`。如果答案这时才到，`answer_ticket` 报 `QUESTION_MISMATCH`（问题已不是 `open`），而不是悄悄写进一条已失效的尝试。
- **不许「recover 之后自动把旧问题搬到新尝试上」。** 新尝试的 `revision` 已经加一，旧答案依据的 `prd_sha256` 也可能已经过期；搬过去就是把一份过期结论当成新尝试的依据。要接着问，就在新尝试上重新 `ask_ticket`，拿一个新的 `question_id`。
- 谁可以 recover：按既有口径由协调会话在核对副作用后调用，写明 `reason`。本版**不新增调用者身份字段**，也不宣称「执行会话不能自己 recover」有代码校验——它现在只是一条流程约定，`recover_ticket` 的入参里没有调用者标识（`FIELDS` 里只有 `project_id` / `ticket_id` / `attempt_id` / `expected_revision` / `reason`）。要不要加这个校验属于实现单的取舍，本文件不假装它已经存在。

## 8. 消息通道三档与选择判据

本节是操作口径，不是新契约：1–7 节的结论一字不改，本节只回答一个更窄的问题——**一条消息该走哪条通道，走错了怎么当场发现。** 依据是本机 `cindy_helper` 的工具实况，2026-11-17 由 AW-030 执行会话逐项取 schema 核实，调用回执见 8.4。

### 8.1 三档能力边界

| 档 | 入口 | 作用于哪一轮 | 回执判据 |
| --- | --- | --- | --- |
| 一 入队 | `send_to_session`（传 `target_session_id`） | 目标**当前这一轮之后** | 只有 `created` 是没打中（宿主新建了任务）；其余非空原值都算打中已有会话——`queued` / `resumed` / `already-active` 与枚举外的取值一律照记（见 4.5 第 3 步） |
| 二 插话 | `steer_session_queued_message` / `steer_session` | 目标**正在进行的这一轮** | `delivery=steered` |
| 三 同步提问卡片 | `ask_user_question_async` | 占住**提问者自己的这一轮** | 无外部回执；别人既排不进、也看不到 |

**档一，入队，只是排队。** `send_to_session` 的 schema 只有 `message` 一个必填字段；传 `target_session_id` 就是「发给一个已有会话」（jump 模式）。它**没有**任何 steer、delivery 或优先级参数——取回的完整 `properties` 里只有 `message` / `target_session_id` / `title` / `working_dir` / `project_path` / `device` / `model` 这些创建与寻址参数，没有一样能表达「插队」。所以档一的语义是确定的：**宿主把消息投进那条已有会话，回执的 `wake_kind` 记的是它怎么处理的**——`queued`（排在原会话这一轮之后）、`resumed`（直接唤醒原会话）、目标当时正在跑时回的 `already-active`（2026-11-18 实测），枚举外的取值也照记，调用方不得把它们映射成 `queued` / `resumed` 之一：枚举比宿主的取值窄，映射就把事实换成了推定。**判定只有一类失败：`created`**——那是宿主把这次投递当成了新建任务，消息根本没到原会话；其余任何非空原值都算打中。提醒：`already-active` 说明消息进了那条会话，但它是否排在本轮之后由宿主决定，本节与调用方都不做推断。**「发过去了」不等于「它这一轮看到了」，这是本节存在的第一个理由。**

**档二，插话，才进当前轮。** 两个入口，分工不同：

- `steer_session_queued_message({session_id, queued_message_id})`：把一个**已经在队列里**的消息提进当前轮。`queued_message_id` 来自 `send_to_session` 回执或 `list_session_queue`；两个字段都必填，`additionalProperties: false`，多传就报 `INVALID_ARGS`。回执 `delivery=steered` 才算真插进去了；返 `delivery=queued` 就是没插成，原因写在回执里（对端这一轮已经收尾，或已经不在跑）。
- `steer_session({session_id, message})`：直接把一段完整正文注入当前 turn，**不需要先入队**。schema 里 `message` 的说明原文是「要注入当前 turn 的完整消息正文」。

由此得出一条必须写下来的操作事实：**因为 `send_to_session` 没有 steer 参数，档二的常规路径是两步——先入队拿到 `queued_message_id`，再 steer。** 「发的时候顺便决定插不插」在本机做不到；要一步到位，只能用 `steer_session` 直接注入。

**档三，同步提问卡片，是唯一一档外部完全不可介入的。** 三条接口事实（4.5 已核过一次，这里重申是因为它决定了「为什么必须把它异步化」）：

1. `ask_user_question_async` 的入参只有 `questions[{question, options}]`，**没有目标会话参数**——它只能问「自己这一轮」。
2. `manage_user_questions` 只有 `action: list | withdraw`，**没有 answer 动作**，且描述明写作用域是「your current task's unanswered asynchronous questions」——不能替别的会话点掉它的卡片。
3. 答案只落在提问者的聊天里（「answers arrive as user input」），不进工单库。

**因果链，逐环扣死：** 卡片占住提问者本轮 → 本轮没结束，这个会话的消息队列就没有消费时机 → 所以别的会话**连排队都进不去**（档一在这里不是被降级，而是根本轮不到）→ 同时问题不落库，`get_ticket` 看不到它在等什么，协调会话与验收会话都无从判断这张单是「在干」还是「在等」→ **因此在工作区流程里，决策必须异步化：走 4.1 的 `ask_ticket` 落库 + 结束本轮，靠 4.5 的新消息唤起。** 卡片不是「次优通道」，它是会把整条链路堵死的那一档。

### 8.2 四条判据

按「影响哪一轮产出」问，不按话题重要性问。顺序问下来，前一句能定就不往下问：

| 序 | 问句 | 是 → 动作 |
| --- | --- | --- |
| 1 | 这条消息要改的是目标**当前这一轮**的产出吗？（纠错、补约束、撤掉它刚做的那一步） | 档二：`steer_session` 直接注入；或入队后 `steer_session_queued_message`。**在这里入队等于让它赶不上** |
| 2 | 这条消息在**当前这一轮结束之后**处理就行吗？（下一件事、追加任务、结果回传） | 档一：`send_to_session` 入队 |
| 3 | 这条消息是不是**要人拍板**，且这个决定事后要能被别的会话查到？ | 档三禁用。走 `ask_ticket` 落库 + 结束本轮（4.1 / 4.5） |
| 4 | 1 和 2 判不出来（拿不准它会不会改变这一轮的产出） | 按 1 处理：插话。插错只是多一条消息，漏插会让整轮产出作废——成本不对称，所以往「插」偏 |

第 3 条排在 1、2 之后，是因为判据问的是「影响哪一轮」，而卡片同时违反 1 和 2：它既改变不了目标本轮（外部进不去），又不留下能事后处理的记录。它唯一还排得上用场的地方是**非工作区流程**的纯交互确认（例如需要人当场点一下的界面操作）——那里没有落库与唤醒的需要，也就没有把卡片异步化的理由。

### 8.3 可观测信号：队列滞留 = 该插没插

发完不能就此结束，必须核一遍。动作是这四步，照做即可：

1. 记下 `send_to_session` 回执里的消息 id；回执没给就先 `list_session_queue` 找。
2. `list_session_queue({session_id})`——返回 `{ok, session_id, queued_count, queue[]}`。
3. 看自己那条是否还在 `queue` 里。**目标已经跑完过一轮、而自己的消息还留在队列里 = 「该插没插」。** 这一轮的产出已经按旧指令做完了，这是已经发生的损失，不是待观察的风险。
4. 补插：`steer_session_queued_message({session_id, queued_message_id})`，回执必须是 `delivery=steered`。仍是 `delivery=queued` 就说明这一轮已经收尾、插不进去了——此时不要再反复 steer，回到判据 1 重新判断：要影响的那一轮已经过去，就得明确告诉人或重新派发。

这条信号的用处在于它**可判定**：不需要猜对方有没有看到，队列里有就是没看到。

### 8.5 自身会话标识怎么取

**取法：`cindy_helper` 的 `call_tool` 直接调 `get_current_session_id`，参数 `{"name":"get_current_session_id","args":{}}`。** 2026-11-17 AW-030 执行会话的真实回执：

```json
{"ok":true,"session_id":"813bff91-5a3b-47e5-adbe-29164fff9651","agent_kind":"pi",
 "working_dir":"{{WORKSPACE}}","project_path":"{{WORKSPACE}}",
 "workspace_kind":"project","remote_host_id":null}
```

**它不出现在 `list_tools` 的搜索目录里，这一点必须写明。** 同一个会话里，`list_tools({query:"get_current_session_id"})` 返回 `{"ok":true,"tools":[],"total":0}`，`list_tools({name:"get_current_session_id"})` 返回 `UNKNOWN_TOOL`，而 `call_tool` 带这个名字调用成功。原因是结构性的：`list_tools` 只索引「已发现」的工具，`get_current_session_id` 是路由层可以直接转发的入口，不在那张可搜的表里。

**AW-027 的误判就是这么来的。** 它的 submission 里写了「宿主没暴露 `get_current_session_id`」，依据是按名字搜不到——搜不到不等于不存在。写在这里是为了让下一个人少踩一次：**搜不到时先按名字用 `call_tool` 试一次，再下「宿主没有」的结论。**

**与 `AGENTS.md` 第五条末句的关系（已修，AW-031）：** AW-030 时第五条仍断言宿主取不到自己的 session id、只能靠反查发现错标识——本节的回执已把前半句证伪，但第五条不在那一单的写域内（只许追加第六条），所以当时只记成「已知冲突」、没有改。AW-031 已把第五条末句改成本节的取法（自身标识用 `call_tool` 调 `get_current_session_id` 自取，再按 `list_sessions` 反查 title 与 workingDir 再用），**两处现在一致，不再存在冲突**；若以后再出现分歧，取法以本节（§8.5）为准。
