## 1. 要解决什么问题

现在「别的项目要做长线任务，就交给 AI 工作区」只是一句口头约定，没有任何落盘依据。它坏在五个地方，每处都在仓库或库里有痕迹：

**缺口一：流程 skill 只在项目内可见。** `pdsa-workflow`、`plan-gate`、`prd-authoring`、`skill-routing`、`ticket-dispatch` 这五个流程 skill 放在 `.agents/skills/`，那是项目级目录，只在 `{{WORKSPACE}}` 里可见。为什么现在的做法不行：从别的目录开的 chat 根本加载不到这套流程，「交给 AI 工作区」这句话背后没有可执行的东西去接，交接等于空转。

**缺口二：没有跨项目接入锚点。** 只有本仓库有 `AGENTS.md` 会被宿主注入，Cindy 里另外 24 个项目对这套体系一无所知。为什么现在的做法不行：一个会话在别的项目里，没有任何注入内容告诉它「这件事要交接」，它连「该交接」都不知道，更不会主动触发。

**缺口三：把「登记」当成了「许可」。** 中心库只登记了 2 个项目（`ai-workspace`、`xingling-chuan`），Cindy 项目列表里有 25 个，其中六个是 `bots/*/workspace` 这种目录同名的伙伴工作区。为什么现在的做法不行：只要登记被当成许可，派发到任何没登记的目录就先要人补一步登记，而 Cindy 列表本身已经是「哪些目录在工作」的事实来源；更要紧的是从目录名派生标识时，六个同名 `workspace` 会撞成一个，工单落点分不出来。口径改成「列表即范围、`root` 是身份」，见 §4.4。

**缺口四：协调会话没有跨项目身份。** `coordinator_session_id` 只是个自报字符串，库里查不到协调者来自哪个项目，也查不到回信到底发没发出去。为什么现在的做法不行：回信是整条链路的收口，发没发出、发到哪都不可查，交接等于没有回执，出了岔子无从追。

**缺口五：交接只传功能，不传判断。** 三行模板只要求写「要做的事」，把背景补全的责任整体推给收件方去读原对话。2026-11-18 的 1205 配乐交接是实证：用户原话里的「我觉得做的还是不够好」与「还可以魔改别人的 skills」都是这次要不要重做、做到什么程度的依据，三行消息只留下「调研 skill、提炼风格、产出清单与流程」这一串功能名；协调会话确实调了 `get_chat_history` 读到了整段历史，也读了 `BGM清单_v0.1.md`，但写出的 PRD 第一节与八条验收条件仍然全部从文件反推（缺 prompt 列、缺自家基线、缺决策落库），用户的不满没有变成任何一条判据。为什么现在的做法不行：读到不等于用上——历史里属于「判断」的部分（上次哪里不行、这次什么算好、什么绝不能被改掉）没有任何一节被要求写下，于是它在转抄的每一步都可以被丢掉，而丢掉的产物看起来仍然完备、验收也仍然能全绿。

## 3. 各类会话分工

- **协调会话**：在 `{{WORKSPACE}}` 里工作的会话天然是协调者。它负责派发、收口、发回执、向人转述结论；回信只由它发一次，执行会话不许直接发给原会话。
- **执行会话**（交接发起方，PRD 原称「执行会话」，这里沿用旧名但指的是来源会话）：在别的项目里接到长线任务的会话。它负责识别「要交接」、写六节交接包、取自己的标识、发四行交接消息，交接之后不再推进同一件事。
- **验收会话**：不参与交接。它读 `get_ticket` 时应当能看到回信结果，作为判断「闭环有没有走完」的依据。
- **人**：唯一最终决定者。入口是聊天，落库由会话代做。

### 4.1 R1：入口用 Cindy 自定义提示词，写指针不写正文

入口用 Cindy 的自定义提示词：全局生效，额度 8000 字符，当前只用了 188。提示词里只放触发条件、四行动作和例外分支，交接协议放固定路径的文件——指针不写正文。这样改协议不用碰提示词，提示词也不会被正文撑爆额度。

最终提示词文本（唯一权威副本）已落在 `docs/intake.md` 的「最终提示词文本」一节，正文 ≤400 字符，指针指向 `~/.agents/intake/intake.md`，此处不再内嵌草稿。

### 4.2 R2：例外分支——已经在 AI 工作区里就不发

提示词必须带例外分支：已经在 `{{WORKSPACE}}` 里工作时，这个会话就是协调者，直接按既有流程开工单，**不要向自己派发**。没有这条，协调会话自己也会被提示词触发「交接」，把一条正在推进的单再派给自己，撞 `SELF_DISPATCH`。

### 4.3 R3：交接协议与四行消息模板

0.12 起，交接消息是四行，背景由一份先落盘的六节交接包承担，不再只靠「对方去读原对话」：

1. **第 1 行**：要做的事（一句话主题）。
2. **第 2 行**：来源项目名（没绑项目就写「无绑定项目」）与来源会话 id，原样写，不许缩写。
3. **第 3 行**：交接包的绝对路径，并写明「六节齐全，缺节不得接收」。
4. **第 4 行**：背景以交接包为准；历史可用 `get_chat_history` 按第 2 行的 id 核对。

**为什么不再只写三行。** 三行版本把「补背景」整体托付给收件方去读原对话，而原对话里最容易丢的恰恰是判断类信息：用户说过「上一次哪里不行」「这次什么算好」「什么绝不能被改掉」。这些句子在转抄时不像功能名那样有位置可放，于是最先被丢；丢完之后产物仍然能写得完备，验收也仍然能全绿。2026-11-18 的 1205 配乐交接就是这条路：协调会读取了原对话，写出的 PRD 却只回答了文件层面的缺口。把判断写成结构化的六节，是让「读到」变成「写下来」的唯一办法——第三行给路径，闸门查缺节，缺了就拒收。

**六节交接包**（正文与模板在 `docs/intake.md`）：

| 节 | 内容 | 必填判据 |
| --- | --- | --- |
| 1. 用户原话 | 逐字引用，不改写、不摘要；与「重做、不满、必须保留」有关的句子一句都不能省 | 至少一段引用块；缺引用即失败 |
| 2. 要交付什么 | 主题、形状、给谁看、什么算成功 | 非空 |
| 3. 做过什么、为什么不行 | 上一版做了什么、用户怎么评价、这次要改哪一层；没有前史就写「无前史」并说明依据 | 非空；不能只写「待补充」 |
| 4. 硬约束 | 不可改的工具、时长、风格、文件、口径；每条注明来自原话还是推断 | 非空 |
| 5. 已确认事实 | 绝对路径、已跑过的命令与输出、版本号 | 至少一个绝对路径 |
| 6. 未决问题 | 问题—影响—选项；必须由人拍的标 `human` | 非空（没有就写「无」） |

**落点。** 来源会话绑着项目时，写到该项目 `交接/<YYYY-MM-DD>-<slug>.md`；没有绑定项目时写到 `{{WORKSPACE}}/.data/intake/<session-id>-<YYYY-MM-DD>.md`。两种情况都写绝对路径进消息第 3 行。

**协调会话的接收动作。** 先跑 `python tools/intake_gate.py <包>`：非零退出就用 `send_to_session` 退回来源会话，说明缺哪一节，不写 PRD、不开单。闸门通过后再用 `get_chat_history` 读一次原对话，抽查第 1 节有没有删减，并把抽查结论写进 PRD 的「需求来源」节——脚本保证不空，抽查保证不假，两件事不能互相替代。

**PRD 侧。** PRD 必须有「需求来源（逐字）」一节，把交接包第 1、3 节原样搬进来（用 `intake_gate --extract` 输出，不手抄），第一条验收条件是「PRD 该节与交接包逐字一致」。这条让「用户的不满」从此有一条能被 diff 的落点，而不是只活在协调会话的理解里。

交接之后，原会话不许继续推进同一件事；收到回执只向用户转述，不许再动手。这条写在交接协议里，是交接是否成立的判据。

### 4.4 R4：Cindy 项目列表里的每个目录都可以开工单

**列表即范围，登记只是记账。** Cindy 项目列表里的每个目录都可以开工单：不设登记门禁、不做过滤、不删任何目录。理由不是「列表里每一行都可信」，而是「登记不是授权」：能不能在某个目录里开单，取决于那个目录是不是人真在那里工作，Cindy 列表本来就是这件事的事实来源；把登记当前置条件是两层记账互相追认，只会让派发先卡在人身上。

**六个同名 `workspace` 的冲突与解法。** Cindy 列表里有六个 `bots/*/workspace` 目录，`directory_name` 全是 `workspace`（Cindy 里六行的别名分别是 `Buddy 数据喵`、`Buddy 工程喵`、`Buddy 文案喵`、`Buddy 美术喵`、`Buddy 舆情喵` 与 `Buddy 周瑜的老公`）。它们不是可以丢掉的垃圾目录：实测六个都是 git 仓库，各有自己的 `AGENTS.md` 与 `CLAUDE.md`，是可以独立接单的工作区。冲突在于：`project_id` 若从目录名派生，六个目录会撞成同一个 `workspace`，一张工单到底落在哪个伙伴工作区就分不出来。解法是分开两件事——

- **`root` 是身份。** 每个目录的绝对路径才是「这是哪个项目」，它唯一（现库已是 `root TEXT NOT NULL UNIQUE`），只认路径、不认名字。
- **`project_id` 是标签。** 它是给人看的标签，由发起会话给；同一 root 重复登记**复用原记录**、不改已有标签；标签重复（六个都叫 `workspace` 而 `project_id` 叫 `buddy-data`）不阻断派发；标签给错了也不阻断派发——改标签是登记面的事，不是开单的前置条件。

一句话记住这条规则：root 是身份，project_id 是标签。身份只认绝对路径且唯一，标签可以重名、可以改、给错了也不拦住开单。

**代价写清楚。** （1）目录一多，探针候选会变长：PRD-003 §5 第 3 步要跑探针时，候选里会出现技能目录这类非工作目录；判据仍是 `root` 与路径，不是目录名，所以候选变长不等于更容易选错，但读起来比以前长。（2）没有门禁之后「某目录能不能开单」不再有库里的白名单可查，依据是 Cindy 列表本身；列表被删行时，已登记的 `root` 仍在库里，两边不一致只能靠人看。（3）标签重复时，回执与清单要靠 `root` 或 Cindy 别名分辨，不能只看 `project_id`。

### 4.5 R5：身份与回信记录

回信地址就是 `coordinator_session_id`，不需要新字段。要加的是两样落库可查：协调者自己的工作目录，以及回信结果（`sent` 或 `failed` 加原因）。回信只由协调会话发一次，执行会话不许直接发给原会话；失败不重派，留一条 `NOTIFY_FAILED` 等人来看。

（0.10 修正：本段开头「不需要新字段」已经不成立——回执发错地方时库里看不出这一次到底发到了哪，所以 0.10 加了 `notices.target_session_id` 与 `wake_kind`，见本节末的实施落点（0.10）。本段其余两句保持。）

**实施落点（0.7，AW-051）。** schema 6→7 加两项：`attempts.coordinator_workdir`（可空，`claim_ticket` 可选传入）与 `notices` 表（`id`、`ticket_id`、`attempt_id`、`origin_session_id`、`status`、`detail`、`created_at`）。写入走新操作 `record_notice`：`status` 只收 `sent` / `failed`；`session_id` 必须等于该尝试的 `coordinator_session_id`（否则 `NOT_COORDINATOR`，不写行）；一张单最多一条 `sent`（`one_sent_notice` 部分唯一索引兜底，第二次报 `ALREADY_NOTIFIED`），`failed` 可多条且不改工单状态，回执带 `alert: NOTIFY_FAILED`。读取走 `get_ticket`：`attempts[].coordinator_workdir` 与 `notices[]` 在同一份回执里。本单只做落库，不投递、不自动重发——库里记的是「协调会话声明它发了」，不是宿主确认送达。

**实施落点（0.10，AW-060）：把「发给谁」与「宿主怎么处理的」也记下来。** 0.7 那版写了一句「回信地址就是 `coordinator_session_id`，不需要新字段」——这句话在实际派发里不成立：回执投错的常见形态恰恰是发给了执行会话自己（或别的会话），而库里只有一条 `coordinator_session_id`，事后看不出这一次到底发到了哪。所以 0.10 改三处：

1. schema 7→8：`notices` 加 `target_session_id`（NOT NULL，存量行留空串表示「历史未记」）与 `wake_kind`（NOT NULL，同）。`record_notice` 校验 `target_session_id` 必须等于该尝试 claim 时写下的 `coordinator_session_id`，不等报 `NOT_TARGET` 且不写行——回执发错地方比没发更难发现，所以这一条当场拦下。
2. `wake_kind` **不按白名单收**：只特判 `created`——宿主把它当成新建任务而不是投递（那条新会话的标题往往就是回执原文），这时一律落 `failed`、回执带 `alert: NOTIFY_CREATED_TASK` 并让这次调用非零退出，而 `notices` 那一行仍然入库（事后要查得到，所以它不是「报错就没发生」）；`queued`、`resumed`、`already-active` 与枚举外的取值一律原样入库，调用方不得把它们映射成近似的三值之一。只校验形状：空串、纯空白、超过 40 字、含内部空白或换行报 `INVALID_INPUT` 且不写行。停掉误建的新会话仍由人做，本单只报错。
3. 「回信只由协调会话发一次、失败不重派」之外再加一条收口：`merge_ticket` 在该单 `notices` 为空时报 `NO_NOTICE`。`failed` 也算走过（回执没送达但原因记下来了）。它拦的是「验收了、合了、回执不知道发没发」这条路；已有合并记录的单行为不变，先报 `ALREADY_MERGED`。

### 4.6 运行位置约定（验收证据怎么跑）

§5 每条证据命令一律在 master 检出根目录 `{{WORKSPACE}}` 运行：命令里引用仓库内文件用相对路径（如 `docs/intake.md`），引用中心库或代码目录用绝对路径。需要读分支（在途工单工作树）上的文件时，必须写绝对路径（带工单工作树目录前缀），同时注明它属于哪张在途工单、合并后该改成什么。当前没有任何证据需要读分支文件——证据要么读 `docs/intake.md`（主检出正文）、要么查 `task_center/`（已合入 master 的代码）、要么查中心库。

### 4.7 R6：无项目会话的落点

要在一张工单里推进某个目录的事，而那里还没有项目、也没有会话在工作时，落点分三件事：先把目录建出来并注册成 Cindy 项目，再根据原会话当前状态选一条路径进去，最后收口。

**前两步两条路径共用：**

1. **建目录。** 目标目录还不存在就先建出来。`create_project` 只接受**已存在的**目录，它不会替你建。
2. **注册成 Cindy 项目。** 调 `cindy_helper` 的 `create_project`，传该目录的绝对路径。它只做一件事：把这个已存在的目录加进 Cindy 项目列表；不建目录、不初始化 git、不建任务、不启 agent；同一路径重复调用复用同一个项目。

**第三步按原会话状态二选一。** 原会话已空闲且人确认要迁时，用 `move_session` 把它迁入目标项目，保留原会话的对话上下文，人可以在原会话继续；原会话仍在跑时（交接的常见形态），在目标项目新建会话接续、原会话停手：

- **路径①：迁移已空闲的原会话。** 调 `cindy_helper` 的 `move_session`，`session_id` 传原会话、`working_dir` 传第二步回执里的 `project_path`。上下文跟着会话走，不用重建；迁完就在原会话接着做，不另开一条。
- **路径②：原会话在跑，新建会话接续。** 用 `send_to_session` 新建一条任务，`project_path` 传第二步回执里的 `project_path`（`working_dir` 可以不同），标题与正文写清工单号、attempt 与要做的事；新会话自己取 `session_id`，再 `bind_session`；原会话交接之后停手，回执到了只向人转述。

**`move_session` 的限制，写在这里免得当它是万能的。先说清楚两件事别混：工具本身不要求确认，给 `session_id` 与 `working_dir` 就执行**——2026-11-17 对一个已空闲的本地会话直接调它，先迁入指定项目、再迁回原项目，两次都没有任何确认步骤，迁完消息数与对话内容不变。**「迁移前先问人」是我们自己的规矩，不是这个工具的前置条件**：同一个工具也能搬别人的会话，所以凡不是本会话自己的会话，迁移之前必须先经人同意；这一步工具不拦，只能自己守。上文的「人确认要迁」、R6 与 AC09 里的「经人确认」，指的都是这条规矩，不是工具会弹一步让你点。工具自身的限制是：只接受**空闲的本地任务**；明确拒绝移动正在运行的任务与正在调用它的那条任务（工具自述：`Running tasks … cannot move`、`Cannot move the calling task while it is running.`）；已归档/已删除、Bot 自有、Review 任务与 SSH 远程任务也移不了；它不移动项目文件、也不建任务。所以这条限制的结论就一句——**空闲可迁、在途不能迁**：交接发生在源会话正推着一件事的时候，那一刻直接把它搬过去做不到。

**代价，写死，不假装能消掉**（路径②主要吃其中四条；路径①省掉第 1 条，其余照旧）：

1. **上下文要重建。** 新会话不继承源会话的记忆，靠工单（`get_ticket`）、成果文件与 `get_chat_history` 补背景；所以交接消息必须带全工单号与 attempt 标识，否则新会话得先回头找。
2. **登记先于任何工单。** 目录刚建出来就注册，注册错了只能 `unregister_project` 撤销后重登；一旦那个目录上已有工单，撤销会被拒。
3. **两个会话会并存一段。** 原会话停手不等于它被关掉：只要它还在，就可能有人在那边继续追问，产出会在两处分叉。这是靠人守的地方，库里拦不住。
4. **派发消息里写不进新会话的标识。** 新会话的 `session_id` 只有它自己知道，交接消息写不进去也不能猜，只能由它自己取、自己绑。
5. **路径①的迁移动作不在中心库留痕。** `attempts` 只记 `session_id` 与 `coordinator_session_id`，没有「这个会话迁过项目」这一列；事后要查只能看宿主会话的 `working_dir`。

### 4.8 R7：六节交接包与闸门

交接包的结构、落点与拒收动作已经在 §4.3（0.12 重写的那一段）写清；这一节只定实现边界与判定口径，避免两处说法分叉：

- **形状。** 包是 UTF-8 的 Markdown 文件，六节标题固定为 `## 1. 用户原话`、`## 2. 要交付什么`、`## 3. 做过什么、为什么不行`、`## 4. 硬约束`、`## 5. 已确认的事实`、`## 6. 未决问题`。顺序不许变，标题文字不许改——闸门按这六个标题匹配，改一个字就是缺节。
- **闸门。** `tools/intake_gate.py <pack>` 只查形状，五条判据：文件存在且能按 UTF-8 解码；六个标题齐全且顺序正确；第 1 节含至少一段以 `>` 开头的引用；第 3 节非空且不是「待补充」「TODO」这类占位；第 5 节至少有一个绝对路径（`X:/`、`X:\` 或 `\\` 开头）。`--extract` 只打印第 1 节正文，供 PRD 原样搬运。退出码：通过 0，有问题 1，用法错误 2。
- **闸门不查真假。** 「原话是不是真的、有没有被删减」脚本判不了；那一步由协调会话用 `get_chat_history` 读原对话抽查，抽查结论写进 PRD 的「需求来源」节。两条规则各管一段，不互相替代。
- **不改的东西。** 不新增中心库 schema、不改 `task_center/`、不改 `docs/protocol.md`：交接包是文件层的协议，与工单状态机无关。
- **退回也是一次派发。** 缺节时协调会话用 `send_to_session` 带 `target_session_id` 发回来源会话，消息只写缺哪一节与闸门输出；来源会话补完再发一次。退回不占工单号，也不写事件。

**已知缺口（代价，写死，不假装能消掉）**：

1. 自定义提示词是非强制的——宿主注入不做校验，触发条件写错了不会当场报错，只能事后发现。
2. 内容型项目没有 commit 钩子可拦——本仓库靠 `tools/work_gate.py` 拦「无工单改文件」，别的内容项目没有这一层，交接协议在那边只能靠约定。
3. 一次长线任务等于三个会话（来源会话 + 协调会话 + 执行会话），上下文靠消息与库恢复，不靠单一会话记忆。
4. 交接在途时要换一个会话：原会话已空闲则可直接 `move_session` 迁入目标项目并保留上下文，原会话还在跑就只能新建会话接续、源会话的记忆不会跟着走（详见 §4.7）。
