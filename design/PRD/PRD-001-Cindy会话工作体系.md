# PRD-001：基于 Cindy 对话框的 AI 工作体系

- 状态：总体方向与集中工单方案已获用户认可，按阶段推进；本机工单核心与项目候选层已实现并测试，真实会话适配未开始
- 版本：0.10
- 日期：2026-11-17
- 所属项目：{{WORKSPACE}}
- 当前实施范围：先建设和测试本机工单核心，再接入真实 Cindy 会话。不开启定时自动化，不修改其他业务项目。

## 1. 我们要解决什么问题

用户希望 AI 能持续推进开发或其他工作，在合适的步骤调用模型、Skills、MCP 和工具，完成执行、检查和返工。用户需要随时知道工作进行到了哪里、结果是否合格，以及哪些事情需要自己决定。

此前的使用体验包括消息串行、子任务创建失败、多项工作在聊天中相互混淆。新方案不以修复旧功能为目标，而是让项目进度和工作依据独立于某一个对话框的记忆存在。

## 2. 已确定的架构边界

1. 不再使用 OmniFlow 插件，也不再使用伙伴功能；不将它们的排障、修复或复用作为前置条件。
2. 协调、规划、执行和验收一律通过 Cindy 普通对话框（session）完成，不用伙伴或协同 Worker 分组替代。
3. AI 工作区是协调项目，不是所有业务工作的执行目录。业务执行与验收必须归属对应业务项目。
4. PRD、工单和验收记录持久保存；聊天历史提供线索，但不是唯一的进度来源。
5. 会话间派发使用 Cindy 原生控制能力，不通过模拟点击聊天框实现。
6. 后续自动化仍使用 Cindy 原生能力；本次没有授权创建或启用定时自动化。
7. 不自动卸载旧插件、关闭旧任务或删除旧资料。

## 3. 第一版要交付什么

第一版先让用户手动触发一个完整工作闭环：

需求与验收条件确定 → 建立工单 → 派发执行 → 提交成果 → 独立验收 → 通过、返工、重新规划或等待决策。

用户应能够从工单找到对应的需求版本、执行会话、实际成果和验收结论。原执行会话中断后，新的会话可以依据这些记录继续工作。

第一版不要求 AI 自主生成任意流程，也不要求复杂看板。先提供可阅读的任务列表和详情，后续看板读取同一份状态，不能另存一份人工同步的进度。

## 4. 各类对话框如何分工

| 对话框 | 项目归属 | 负责什么 | 不得做什么 |
| --- | --- | --- | --- |
| 协调会话 | AI 工作区 | 接收目标、整理优先级、建议下一步、派发已授权工作、向用户提出决策请求 | 不把所有业务项目资料混装进同一上下文，不自行扩大授权范围 |
| 规划会话 | 对应业务项目 | 阅读相关需求，形成计划、步骤与预先确定的验收条件 | 不通过修改需求掩盖执行失败 |
| 执行会话 | 对应业务项目 | 按绑定的工单和需求版本执行，提交成果与检查证据 | 不自行宣布验收通过，不转去其他项目修改材料 |
| 验收会话 | 对应业务项目，使用独立上下文 | 按既定标准检查具体成果，记录结论和理由 | 不只依据执行者总结判断，不暗中降低验收要求 |

上述分工是职责，不意味着每项小任务都要创建四个会话。第一版规划可以由协调会话发起，但业务执行和独立验收必须分开。

**「分开」不能只写在职责表里。** 0.8 之前的情形已经重复发生过：协调会话 claim 之后自己把活儿干完，库里只有一张工单、一条会话，`get_ticket` 看上去一切正常。所以在 0.9 里，这条变成可被拒绝的事实：`claim_ticket` 必须记下发起派发的协调会话标识，`bind_session` 收到同一个标识就返回 `SELF_DISPATCH`，工单停在 `dispatching`。派发就是新开一个会话；没有会话创建能力时按 AGENTS.md 硬规则五处置，不许自己动手。

一个执行会话同一时间只处理一个工单的一个执行尝试。无关工单另建会话；同一任务返工可以复用原会话，但必须产生新的尝试记录，并重新核对需求版本。

## 5. 项目上下文如何加载

每次工作开始时必须明确：项目标识、项目目录、工单、当前步骤、执行尝试，以及所依据的 PRD 和工作流版本。

项目说明应包含目标、范围、主要资料入口、可用工具和审批边界。进入项目的 Skill 负责整理和加载相关内容，不负责凭聊天语义猜测项目归属。

项目归属不明确或与目标目录不一致时，应停止派发并澄清。只绑定项目不代表已经实现文件访问隔离；技术方案还必须确认 Cindy 权限边界，以及如何阻止越界写入。

## 6. PRD 与工作流如何管理

每个业务项目建立 PRD 文件夹。每份 PRD 记录目标、范围、排除项、验收条件、依赖、待决策问题和变更历史。

PRD 可以修订和归档，但历史版本不得被无记录地覆盖。文件夹位置不能成为判断当前有效版本的唯一依据。

一个 PRD 可以拆出多个工单；每个工单必须指向明确的 PRD 版本与验收条件。工作流模板可以复用，但每次运行有独立记录，不能共用“当前步骤”。

执行期间修改 PRD 时，需要说明影响哪些工单、哪些验收需要重做，以及现有执行应该继续、暂停还是重新规划。过期版本的成果不能自动完成新版工单。

第一版固定使用 PDSA 模板，不建设任意拖拽式流程编辑器：

- Plan：确定本次目标、方法、依赖、交付物与验收条件。
- Do：执行工作并提交实际成果与必要证据。
- Study：独立检查成果，并判断偏差来自实现、计划还是外部条件。
- Act：通过后推进；有缺陷则返工；计划不成立则重新规划；缺资料或授权则等待。

## 7. 工单至少记录哪些内容

| 记录 | 必须包含的信息 |
| --- | --- |
| 项目 | 稳定标识、名称、Cindy 项目路径、说明文档入口；登记错了可撤销（有工单时拒绝撤销） |
| PRD | 稳定标识、版本、文档位置、状态与变更说明 |
| 工单 | 标识、项目、PRD 版本、目标、交付物（主题与形状）、排除项、依赖、验收条件、当前状态 |
| 执行尝试 | 标识、步骤、session、实际目录、模型配置、开始时间、最后活动、结束原因 |
| 成果 | 文件或其他可验证对象的位置、版本或摘要校验信息、检查证据 |
| 验收 | 对应成果版本、检查项、结论、理由、验收 session 与时间 |
| 事件 | 谁在何时触发了什么状态变化，以及依据和关联执行 |

工单、执行记录、验收结论与事件集中存储在 AI 工作区的 SQLite 数据库，由统一入口更新。PRD 和成果留在各业务项目，中心通过标识、位置与版本关联；项目任务列表是中心数据的视图，不建立第二份可修改状态。

**工作流运行不单独建记录。** PDSA 各步由工单状态、执行尝试与验收记录表达：Plan 对应工单的验收条件与交付物，Do 对应一次执行尝试，Study 对应一次独立验收，Act 对应状态变化。暂停原因写入 `recover_ticket` 的 reason 与事件表。理由：在同一库里再造一份步骤状态，会出现两份进度真相，而这正是本 PRD 要消除的问题。触发再议的条件：出现并行多步骤模板，或需要步骤级审计时，再评估是否升表。

不得让各个 agent 自行写 SQL，或无协调地覆盖同一份 JSON/Markdown 状态文件。第一阶段用 Python 标准库提供本机 JSON 命令入口，以事务处理并发、状态校验与重复请求；不启动公网服务，不把 SQLite 放在同步盘上多机共写。

该入口暂属于同一操作系统账号下的可信协作工具，不是对恶意 agent 的安全隔离层。会话标识与目录字段必须在后续 Cindy 接入时由真实宿主回执核对，不能只凭调用方提供的字符串声称已验证身份。

session 状态和工单状态必须区分：会话运行结束不代表成果已提交，更不代表业务已验收完成。

## 8. 工单如何推进

| 状态 | 意义 | 允许的下一步 |
| --- | --- | --- |
| 待规划 | 目标存在，但执行条件或验收要求还不完整 | 形成计划，或请求用户决策 |
| 待执行 | 计划完整，等待依赖、授权和执行资源满足 | 领取任务并派发 |
| 执行中 | 有明确的有效执行尝试 | 提交成果、报告阻塞、暂停或取消 |
| 待验收 | 成果与证据已提交 | 创建独立验收尝试 |
| 验收中 | 正在检查指定版本成果 | 通过、返工、重新规划或请求决策 |
| 待返工 | 已记录具体缺陷 | 创建新的执行尝试，保留旧记录 |
| 受阻或待决策 | 暂不具备推进条件 | 条件解除并记录依据后恢复 |
| 已完成 | 必要验收通过且证据已记录 | 需求变化时明确重开或创建后续工单 |
| 已取消 | 用户或已授权规则终止工作 | 不自动恢复 |

阻塞记录必须说明原因、解除条件及恢复时应回到哪个步骤，不能只写“卡住了”。只有合法验收结果才能将待验收工作转为完成。

### 开工前的工单闸门

规则本身不够。本工作区前两轮的真实情况是：文档、计划、检验脚本全部做了，**中心库里工单数为 0**——所有改动绕过了工单，因为闸门只检查计划文件，而计划文件不要求有工单。

所以第一道可执行闸门放在改动落盘的那一步，而不是放在提醒里：

1. **任何会写入本仓库或其他业务项目文件的动作，先 claim 一张工单并 bind 本会话。** 只读问答、探查、写计划可以没有工单；一旦要改文件，就必须有。
2. `tools/work_gate.py --ticket <编号>` 核对：工单存在、属于本仓库所属的项目、当前尝试已绑定且处于 `running`。不满足则以非零退出并打印补救命令。**项目归属一律从仓库路径反查**，不接受 `--project` / `TASK_CENTER_PROJECT` 指定别的项目——否则一个残留的变量就能拿 B 项目的工单为 A 项目背书。数据库可用 `TASK_CENTER_DB` 覆盖，供测试与旁路演练使用。
3. 两个仓库都装了 commit 钩子（`.githooks/pre-commit`）：未设置 `TASK_CENTER_TICKET`，或该工单没有活跃尝试，提交直接被拒。
4. 钩子没有隐身开关：0.7 曾经用一个 `.task-center-enforce` 文件当总开关，缺文件就静默放行，比没钩子更危险（验收时被指出）。现在每次提交都核；要关就显式 `git config --unset core.hooksPath`，关的是哪个仓库、代价是什么，都在命令里。

钩子只能拦住“经过 git 的改动”，也能被 `--no-verify` 绕过。它提高的是默认路径的成本，不是安全边界；判断仍然靠验收。

## 9. 派发和结果回传需要保证什么

1. 先保存工单与派发意图，再调用 Cindy 创建或唤醒会话。
2. 核对并保存回执中的目标 session、实际项目和执行目录；消息投递成功不等于执行已经开始。
3. 目标忙碌并进入队列时，不重复发送相同任务。
4. 回执不确定时，先核对现有会话和执行记录，不盲目再次创建。
5. 执行者按约定提交结构化成果记录。会话间回信只是通知，工单记录才是可恢复依据。
6. 重复提交同一结果不能重复推进下一步；旧尝试迟到的结果不能覆盖新尝试。
7. 失联不直接判定失败。恢复前先核对实际产物、会话和副作用，避免再次执行已成功的动作。
8. 系统不能靠工单防重就宣称所有外部动作只会发生一次。涉及发送、发布、付费等操作，必须另有业务级去重或人工核对。

具体结果提交入口、并发领取和失败恢复机制必须在实现前验证，不能把提示词约定当成程序保证。

### 派发的载体

2026-11-17 的那几轮真实演练（`tasks/real-session-drill.md`）用的是**项目里的普通会话**：`cindy_helper` 的 handoff 类 `send_to_session` 不传 `target_session_id` 时新建任务，指定 `project_path` 与 `title`，新会话出现在该项目会话列表里，可以点开、追问、自己回传结果。

后续几轮退化的原因说清了：先把 `cindy_orca` 的 worker 当成了会话，又把一次性 subagent 当成了会话。两者都不是“项目里的 chat”：Orca worker 在协同面板里，subagent 没有界面。载体优先级因此写死：

1. **项目普通会话**（`send_to_session` 新建，指定 `project_path`）——默认载体。
2. 宿主确实没有新建任务的能力时，才用一次性独立上下文子任务，并在工单的提交说明里标清“载体是一次性子任务，无法追问”。
3. 两者都不可用——停下来告诉人，不许协调会话自己执行（§4、`SELF_DISPATCH`）。

协调会话自己的标识必须向宿主取（当前任务信息、工作区回执里的 session id）。**禁止从临时目录名、运行目录或任何路径猜一个字符串当会话标识**：猜出来的东西会进记录，但对应不到任何会话，比自报字符串更糟。

## 10. 模型、Skills、MCP 和权限如何选择

每个步骤使用明确的执行配置：职责、输入、输出、模型、所需 Skills、允许的工具、验收规则和停止条件。

第一版提供少量固定配置，不要求 AI 自动比较全部模型。模型不可用时报告并按预先授权的规则处理，不擅自切换账号、电脑或供应商。

验收使用独立上下文；可以选不同模型，但不同模型不能代替真实检查。模型与工具的精确可用项，以 Cindy 当前能力查询为准。

## 11. 第一轮试点怎样做

建议使用一个经用户确认的隔离试点项目，完成低风险文档任务，例如按给定材料制作一份检查清单。该例子只用于测试，不代表业务方向已经选定。

先完成一次正常派发和验收，再注入一次缺陷，验证拒收、返工和再次验收。然后模拟执行中断，验证新会话能从记录接手。

增加第二个隔离项目后，再测试跨项目隔离与真实并发。不能仅凭建立了两个 session 就宣称并行成功，必须记录实际执行区间。

通过这些试验后，再接入真实业务项目。试点不涉及发布、删除、付款、对外发消息或改动生产数据。

## 12. 验收标准

状态列只表达该条**是否已被证据满足**：`已验证` 指有可指到的测试或演练记录；`部分验证` 指核心逻辑已验证、端到端场景未验证；`未验证` 指没有任何证据。任何一条都不得用一句概括代替。

| 编号 | 要求 | 状态 | 证据 |
| --- | --- | --- | --- |
| AC01 | 协调、执行与验收使用 Cindy 普通 session，不调用 OmniFlow 或伙伴 | 部分验证 | 架构已定（§2）；本机核心不涉及派发，真实会话适配未开始 |
| AC02 | 每次执行可追溯到明确项目、工单和需求版本；错误项目绑定被拒绝 | 已验证 | `test_binding_wrong_project_directory_rolls_back`、`test_cross_project_query_rejected`、`test_prd_path_cannot_escape_project` |
| AC03 | 用户能从任务列表进入详情，找到 session、成果和验收依据 | 部分验证 | `get_ticket` / `events` 可查全部要素；列表与详情界面未做 |
| AC04 | 执行完成但未验收的工单不显示为已完成 | 已验证 | `test_submit_has_receipt_but_not_done` |
| AC05 | 故意提交的不合格成果被拒收；修复后重验，历史保留 | 已验证 | `test_reject_rework_accept_keeps_both_attempts`、`tasks/real-session-drill.md` |
| AC06 | 原执行会话中断后，新会话依据记录接手，不要求重讲背景 | 已验证（隔离试点） | `tasks/real-session-drill.md` 中断接手演练：执行会话 0d24b667 留下草稿，recover 后由 62cc5384 接管完成 |
| AC07 | 重复派发、重复回报和迟到结果不导致重复推进或错误覆盖 | 已验证 | `test_exact_retry_returns_original_receipt`、`test_two_processes_cannot_claim_twice`、`test_late_recovery_intent_cannot_supersede_new_attempt` |
| AC08 | PRD 变更后识别受影响任务，不把旧结果当新版验收依据 | 已验证 | `test_changed_prd_blocks_submit_until_explicit_revision`、`test_artifact_or_prd_changes_block_acceptance` |
| AC09 | 两个隔离项目中独立任务实际执行区间重叠，且不混用材料 | 部分验证 | `tests/test_concurrency.py` 3 项：两条尝试用 Barrier 同时停在 running，事件时间戳算出区间重叠，串行变异下重叠为负（断言有效）；跨项目查工单 `PROJECT_MISMATCH`、引用他项目文件 `PATH_OUTSIDE_PROJECT`、同会话双绑 `CONFLICT`。`examples/dual_project_drill.py` 实测重叠 0.022 s。执行者仍是本机两条线程，真实 Cindy 会话对并行未做（依赖 AC01 的适配） |

## 13. 后续阶段做什么

人工触发的闭环稳定后，再启用验收通过后的自动推进、定时兜底检查、并发控制、费用与时间上限，以及面向决策和阻塞的看板。

自动推进只能在现有授权范围内进行。用户取消或暂停的工作不能被巡检自动重新启动。需要审批时，审批必须绑定具体动作和版本。

跨设备运行、任意工作流生成、自主修改验收标准、完整 Jira 功能和大规模历史迁移不在第一版范围内。

## 14. 当前能力证据与待验证事项

已读取的 Cindy 工具声明表明：可以指定项目创建普通 session，选择运行模型和目录，可选独立 Git worktree；已有会话忙碌时投递会排队；可以查询 session 运行状态，也有定时自动化入口。

普通独立 session 不自动建立父子编排或结果回传。真实并发、稳定回传、异常恢复与文件访问隔离尚未完成端到端验证。

本 PRD 不以工具声明代替实际测试，也不承诺尚未确认的事件订阅或后台常驻能力。

已实现但 PRD 尚未覆盖落点的：项目候选层（`task_center/probe.py`，只读、不落库）已按派生式方案完成，`SCHEMA_VERSION` 保持 2；它只产出候选，不参与绑定判定，因此不影响 AC02。
