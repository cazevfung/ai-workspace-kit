## 1. 要解决什么问题

PRD-001 第 5 节规定“进入项目的 Skill 负责整理和加载相关内容，不负责凭聊天语义猜测项目归属”，并要求“项目归属不明确时停止派发并澄清”。这条规定是对的，但它只说了不许做什么，没说在不许猜的前提下，**项目归属从哪里来**。

工单核心本身不承担这件事：每个操作都要求显式传入 `project_id`，中心只校验它存在（`core.py::_project`）以及工单确实属于该项目（`PROJECT_MISMATCH`）。没有任何代码把“这句话在说哪件事”和“哪个项目”连起来。

第一版曾经考虑的做法是给项目登记一份描述（目标、范围、资料入口、审批边界）。这个做法被否决，理由写在下面第 3 节：**它是一份快照，会以用户内容变化的速度过期。**

## 2. 已确定的架构边界

1. **派生，不存储。** 项目状态在每次需要时从客观事实现算，不落库、不缓存、不写画像字段。
2. **探针只产事实，不做匹配。** 哪些目录存在、多久没动、有没有坏，是事实，写成代码永不需要维护；“这句话指哪个项目”是模糊判断，交给会话层，写成规则就会随项目改名而衰减。
3. **不动工单核心。** 零 schema 变更，`SCHEMA_VERSION` 保持 2，`core.py` 不需要改动。探针是独立只读模块。
4. **判定在核心之上。** 核心继续只收已经判定好的 `project_id`，绝不内嵌自然语言处理。
5. **发现不等于注册。** 扫描结果只产生候选，永不写入 `projects` 表；只有显式注册才产生可绑定实体。AC02 因此保持不变。

## 3. 为什么不能存项目描述

三条机制，每条都独立成立：

- **字段会冻结。** `execute()` 拒绝未知字段（`Unknown payload fields`），这是防止拼错被静默忽略的有效保护，代价是字段名一经发布不能追加。而“项目的性质”恰恰是最难提前枚举的维度。
- **描述会衰减且误导。** 任何手写描述在写入那一刻就开始过时。没有描述时系统会去问；有陈旧描述时系统会自信地答错。**误导比缺失更糟。**
- **粒度错配。** 用户真正需要的是“这个项目现在最要紧的事是什么”，它每天在变，任何 schema 都放不下。

因此本设计的核心是：**不追求把描述存得更好，而是存得更少。** 派生结果不可能过期，因为它没有存下来的版本。

## 4. 探针的输入、输出

只读命令行，与 `python -m task_center` 并列，不进 `execute()` 事务，不写数据库（SQLite 以 `mode=ro` URI 打开）：

```
python -m task_center.probe --db <库> --roots <父目录...> [--depth 2] [--limit 8] \
    [--active-days 14] [--coordinator <项目id>] [--explain]
```

输入只有两类事实：扫描起点、工单库路径。**不接收用户那句话。** 输出是事实表，不是结论：

```json
{"ok":true,"result":{
  "registry":{"available":true,"reason":null,"count":1},
  "coordinator":{"project_id":"ai-workspace","activity":"active",...},
  "rank":[{"root":"D:\\星铃传","state":"candidate","activity":"active",
           "last_touch":"2026-11-06T04:16:21+00:00","markers":["README.md"],
           "signals":["no git; bounded file walk","newest file 11d ago","101 files"]},
          {"root":"D:\\node-relay-research\\dify","state":"candidate","activity":"active",
           "git":{"last_commit":"2026-11-16T02:09:48+00:00","recent_commits":1},
           "signals":["last commit 1d ago","1 commits in 30d"]}],
  "broken":[{"project_id":"legacy","root":"D:\\已删除","state":"broken",
             "signals":["registered root no longer exists"]}],
  "counts":{"ranked":45,"returned":8,"broken":0,"scanned":51,"nested":6,
            "omitted":{"active":0,"unobserved":0,"dormant":37}}}}
```

承担判断成本的只有三个字段：`state`（registered / candidate / broken）、`activity`（active / dormant / unobserved）、`last_touch`。其余是给人看的证据。

## 5. 信号的选择与放弃

| 信号 | 代价 | 会被什么骗 | 结论 |
| --- | --- | --- | --- |
| 目录存在、可读 | 1 次 stat | — | 用，作前置校验 |
| 是否 git 仓库 | 1 次 stat | 解压出的副本没有 `.git` | 用 |
| 最近提交时间 | 1 次 git（实测约 85 ms） | 浅克隆、压缩导入只有一个提交 | **首选** |
| 近 30 天提交数 | 同一次调用内得到 | 同上 | 用 |
| **目录自身 mtime** | 1 次 stat | **改子目录里的文件不会改父目录 mtime** | **不用** |
| 有限深度扫文件 mtime | O(文件数)，上限 2000 | 深度不够会漏 | 只在无 git 时启用，深度上限 2 |
| 已注册项目的最近工单 | 1 次 SQL | 长期没开单的项目看起来没活动 | 后续接入 |
| `git status` 脏标记 | **多一次 git，成本翻倍** | 大仓库很慢 | **不用**：成本翻倍换一个弱信号 |
| 正文语义 / 向量检索 | 读 N 份文档 + 建索引 | **答错时最自信**，索引随内容失效 | **不用** |

目录 mtime 这条值得单独记录，因为它是一个会**反向误判**的陷阱：`D:/项目A` 的 mtime 只在直接子项增删时更新，在 `项目A/src` 里改 20 个文件，父目录时间戳一动不动。若用它判断活跃度，最活跃的项目会被判成沉睡。已验证的守护用例：`test_git_history_wins_over_a_fresh_file`（两年前的提交 + 一分钟前改过的深层文件，必须仍判 dormant）。

## 6. 排序：时间只降序，不提权

`rank()` 先按活动带（active → unobserved → dormant），带内按 `last_touch` 倒序。**时间信号永远不能单独把项目抬到“确定”档。**

理由是实测出来的：在 `D:/` 上跑出的前 8 名里有 4 个是 `node-relay-research/` 下刚 git init 的第三方研究副本，另有 1 个是技能目录而不是项目。它们确实“最近被动过”，但和用户要做的事无关。**刚改过 ≠ 正在说它。**

截断也是设计的一部分：列表越长，调用方付的 token 成本越高且永续。`--limit` 默认 8，被省略的数量按活动带记在 `counts.omitted` 里，**不让人误以为列表就是全部**。

## 7. 三段式召回（会话层）

探针只提供事实，下面是会话层使用它的顺序：

| 层 | 触发 | 代价 | 置信 | 动作 |
| --- | --- | --- | --- | --- |
| L0 | 话里出现项目 id / 项目名 / 已知路径 | 0 | certain | 直接用 |
| L1 | 宿主回执已有 `project_root`（会话内） | 0 | certain | 直接用 |
| L2 | 名字模糊命中（含前缀、别称） | 1 次探针 | likely | 提一句“在 X 做？”后继续 |
| L3 | 按最近活动排序取前 K | 1 次探针 | likely | 同上，必须带非时间信号 |
| L4 | 候选为空、分差不够、信号不足 | — | ambiguous | 列 2–3 个带证据的选项让人选 |

L1 是最重要的一层：真实演练记录显示，派发回执里带 `project_path` 与 `working_dir`，而 `bind_session` 正是用它做的目录校验。**宿主已经在免费告诉系统“这个会话属于哪个项目”。** 只有从协调入口发起、且话里没提项目名时，才需要落到 L3。

因此本设计的成本结构不是“把昂贵判定优化到便宜”，而是**让昂贵判定大多数时候不需要发生**。

L4 之后仍有两个必须挡住的出口：

- **候选不等于可派发。** 命中的目录若未注册，只能提议注册，不能绑定。工单要求 `project_id`，这是硬约束。
- **非项目事项不进派发。** 探针不接收用户原话，因此永远无法识别“这根本不是项目里的活”。这条只能在会话层写死，否则会出现给每句话都硬塞一个项目的失败。

## 8. 已实测的证据

2026-11-17，在 `D:/` 上运行 `--roots D:/ --depth 2 --db <测试库> --coordinator ai-workspace --explain`：

| 指标 | 实测 |
| --- | --- |
| 耗时 | 651 ms / 662 ms / 731 ms（三次） |
| 输出体积 | 3933 字节（含 `--explain`） |
| 扫描候选 | 51 |
| 实际排名 | 45（6 个因嵌套被排除，1 个协调入口被排除） |
| 被截断 | 37 个 dormant |
| 测试 | 新增 13 项全部通过；全套 66 项通过 |
| 变异验证 | 去掉“嵌套排除”和“超时不算活跃”两处检查，2 项用例失败；恢复后全部通过 |

同一目录首版实现耗时 17 秒，原因分别是：把 `D:/` 本身当候选（无标记也算）、每个仓库两次 git 调用、串行执行。修复后改为“根目录必须有标记才算候选 + 每仓库一次 git 调用 + 8 线程并行”。

## 9. 防骗规则

1. **空壳判 dormant 且打 `empty_shell`。** 目录存在但无文件，是最像项目的东西。
2. **root 失效判 broken，必须显式出现。** 不能静默略过——静默漏报是派生信息唯一的致命失败模式。可按同名目录或 git remote 提示“疑似搬家”，但**绝不自动改写 `root`**（有 UNIQUE 约束，且会破坏既有工单的可追溯性）。
3. **嵌套候选不参与排名。** 子目录自带标记时，若祖先已是候选，只保留祖先。实测 `D:/星铃传` 与 `D:/星铃传/编辑审视` 同时入选、时间戳完全相同，会让人误以为是两个项目。
4. **扫描起点与深度是配置。** 深度上限 4，噪声目录（`node_modules`、`.venv` 等）跳过，符号链接不跟随。
5. **协调入口默认不排名。** 它是协调会话的 cwd，若参与排序会造成“什么都指向 AI 工作区”的系统性假阳性。
6. **git 超时判 unobserved，绝不判 active。** 把超时当活动，等于把“没观测到”反转成“最活跃”。
7. **失败必须可见。** `--explain` 输出扫描根、跳过原因、耗时、阈值与标记清单。成本为零，但它是发现“探针一直没看到某个项目”的唯一途径。

## 10. 唯一的自演化点

每次项目归属被确认后，记一行 `(措辞片段, project_id, 时间)`。累积之后 L2 的命中率上升、落到 L3 的次数下降，**成本随时间下降**。

它存的是事实（“上次这么说指的是这个”），不是规则（“出现 X 就选 Y”）：前者错一行不影响其他行，后者错一条会系统性错。

**明确不可自动演化**：验收条件、授权范围、谁能当独立验收者。前一类错了代价是多问一句，后一类错了是验收标准被悄悄降低，不可见、不可逆。本 PRD 延续 PRD-001 第 13 节“自主修改验收标准”的排除。

## 11. 不做的事

- 不落库任何项目描述、不建画像字段、不升 schema。
- 不自动注册项目（发现 ≠ 注册）。
- 不自动改写已注册 root。
- 不用向量检索或语义相似度。
- 不在 `core.py` 内做任何自然语言判断。
- 不接收用户原话作为探针入参（避免把匹配规则写进代码）。

## 12. 验收条件

- AC01：探针不写数据库；对已有库运行后字节完全一致（已覆盖）。
- AC02：库不存在时报告 `database absent` 且不创建文件（已覆盖）。
- AC03：已注册 root 消失时出现在 `broken`，不静默消失（已覆盖）。
- AC04：目录 mtime 陷阱不会把老项目判成活跃（已覆盖）。
- AC05：git 超时判 unobserved（已覆盖）。
- AC06：嵌套候选不重复排名（已覆盖）。
- AC07：输出体积与耗时在 `D:/` 深度 2 下不超过 1 秒、4 KB。
- AC08：协调会话能用产物回答“有哪些项目、谁在动、谁坏了”，且**不对项目归属给出未经确认的结论**。
- AC09：候选为空或分差不足时，会话必须提问而不是选一个。
- AC10：命中的是未注册目录时，只提议注册，不绑定、不派发。
- AC11：与任何项目无关的请求不被硬塞进某个项目。

AC08/AC09 尚未接入真实协调会话验证；AC10/AC11 已由演练按规则人工比对，尚未自动化。

## 13. 未决问题

1. **与 PRD-001 TEST-003 的缺口同源。** 演练记录指出：验收条件回答“做到了吗”，不回答“是不是这件事”，导致跑偏的成果合法通过。这与项目定位是同一个结构缺口——**系统缺少“这件事是哪件事”的表达**。若认为工单也需要这一层，应同样采用“派生 + 确认”而非“新增主题字段”，否则会重演快照衰减。
2. `projects.root` 失效之后是否提供 `repair_project`（显式、带审计）仍待定，本 PRD 只要求可见。
3. 扫描根配置本身仍会衰减（用户搬目录后不更新）。这是全案唯一残留的手工维护点，刻意只保留这一处。
4. 是否把“最近工单标题”并入探针信号，需等协调视图确定后再定。
5. 命中记录（唯一的自演化点）尚未实现，因此“越用越省”仍只是设计推断，没有证据。
