## 1. 要解决什么问题

到 2026-11-21，中心库里已经有 157 张工单、208 次提交、187 次验收。把这些记录按区段量一遍，执行与验收这两段都很快（领取到提交中位数 5.4 分钟，提交到验收 3.6 分钟，验收通过到合并 2.4 分钟），但三个位置的数字很难看：

- 150 张已验收工单里有 71 张没有合并记录（47%）。验收通过到合并只要两分半，所以这不是慢，是没有人被要求去跑这一步。
- 157 张单里有 60 张跑了不止一轮（38%），40 张被 `revise_ticket` 改过条件（25%）。35 次验收驳回里，17 条的 reason 谈「口径」、11 条谈「命令」，也就是约一半的返工起因是条件本身写不清，不是成果没做到。
- 928 条验收条件里只有 338 条（36%）带可执行命令，显式标「判断类」的只有 12 条。剩下的既没有命令，也没说自己判不了。

现象背后的结构是这样：**这套机制里能落成退出码的规则都挺住了，靠人记的规则都在漏。** 具体漏在四处：

1. **条件形状没有闸门。** `ticket-dispatch` 第八节已经写明「`criteria` 只收两种写法：命令加期望输出，或标判断类并写反例」，`prd-authoring` 第三节也写了同样的话，但 `create_ticket` 什么都不校验。口径写在 skill 里，写 SKILL.md 的人读了、写条件的人不一定读，读没读也看不出来。
2. **并行是一个带逃生舱的布尔值。** `allow_parallel` 被越过 16 次（CHM-036 到 CHM-045），一次都没拦住人。事由不记、范围不记，三张单同时改一个仓库、同时抢一台真机，屏幕反复横跳，靠人看出来的。
3. **被拒绝的动作不留痕。** `events` 只写成功路径，被闸门拒掉的调用什么都不留。所以「串行保护到底拦过几次」「谁试过用别人的工单背书」这类问题永远查不出来，也无法判断某条闸门是有效还是在空转。
4. **机制假设的安装面没人核过。** `work_gate` 由每个仓库的 `core.hooksPath` 触发，但中心库里没有字段、也没有脚本去核对某个已登记项目是否真的装了钩子。一个项目进来就是裸的，从库里看不出来。

## 2. 边界

- 不做租约心跳，也不做超时自动重派。`PRD-005` 的 D6 已决，理由是它需要定时自动化，而定时自动化在工作区边界之外。用库里已有的时间戳算「等了多久」足够回答「它是不是停了」。
- 不做验收条件的语义判定。「这条条件合理吗」机器判不了。形状闸门只判两件事：可执行，或者你已经明说这是判断类。
- 不回溯历史。已有的 928 条条件、71 张未合并单、157 张单的历史状态一律不改，闸门只对新开的单与新的 `revise_ticket` 生效。
- 安装面检查只报告，不替人改别的仓库配置。`project_doctor` 打印缺什么、怎么补，不动 `git config`。
- 不新增状态，不改既有状态机的语义。R3 只加一种只读的事件行。
- 不动 Cindy 设置、不动业务项目目录、不发布服务。

### R1 条件形状闸门

`create_ticket` 与 `revise_ticket` 校验 `criteria` 里每一条的形状，只收两种：

- 文本里含至少一处反引号包裹的命令，且该命令的动词在已知命令名单内（`python` / `git` / `grep` / `ls` / `find` / `wc` / `node` / `npm` / `bash`）；
- 文本以 `判断类` 开头，且同一段文本里出现「反例」二字。

两者都不满足时拒绝，错误码 `CRITERIA_NOT_JUDGEABLE`，一行不写。拒绝时回执要点名是第几条（`C3`），并给出改法。

**条数下限按状态分（0.4 补，AW-109）。** 条件列表的长度只有一档例外：

| 动作 | 收几条 | 空了报什么 |
| --- | --- | --- |
| `create_ticket` / `revise_ticket`，单子处在 `planned` 且这次调用不换状态 | 0–100 | 不报错：这是「已经知道要补什么、还写不出验收条件」的念头落点 |
| `create_ticket` / `revise_ticket`，其余状态 | 1–100 | `CRITERIA_NOT_JUDGEABLE`（「一条都没有」是「这张单还不可以被验收」，不是字段写坏了） |
| `revise_ticket` 带 `restart`、或对已完成单带 `reopen`（落点都是 `ready`） | 1–100 | 同上——**「按落点状态判」：这两条路把单送回 `ready`，不能借 `planned` 的宽限绕过下限** |
| `claim_ticket`，任何状态 | 至少 1 条 | `CRITERIA_NOT_JUDGEABLE`，message 指回 `revise_ticket` |

形状错误（非列表、缺 `id` / `text`、`id` 重复、超过 100 条）仍报 `INVALID_INPUT`：那不是「一条都没有」，是这份输入写坏了。

为什么放宽这一档：`planned` 已经占了「还没开工、在库里排着」那个位置，而空条件正是那个位置唯一表达不出来的东西。放宽只落在入口上——`claim_ticket` 守着开工下限（`PRD` 的推进条件里「验收条件非空」本来就是一条），所以一张空条件的单领不走、也不会被 `next_action.py` 派出去。`docs/protocol.md` 的 `criteria` 一节与 `PRD/PRD-014-计划队列与依赖.md` R1 写同一件事。

历史条件不回溯：闸门只作用于调用当下传进来的 `criteria`，库里已有的行不重判。

### R2 并行声明

`claim_ticket` 传 `allow_parallel: true` 时：

- 必须同时给 `parallel_reason`：非空字符串，1–200 字，写清为什么这两张单可以同时跑；
- 可以给 `parallel_scope`：字符串数组，1–20 条，每条是一个项目内相对路径、目录，或一段以 `资源:` 开头的资源标识（例如 `资源:真机`）。

两项都写进 `claim_ticket` 的事件，与既有的 `parallel_with` 并列。缺 `parallel_reason` 时拒绝，错误码 `PARALLEL_REASON_REQUIRED`，工单停在原状态。

`parallel_scope` 进库是为了让后来的人能核对：`work_gate` 在 `mode=running` 放行时，若这张单的事件里声明过 `parallel_scope`，把暂存路径与声明的路径逐条比对，越界时打印警告行（不拒绝——放行权仍归工单本身）。

### R3 拒绝留痕

任何写操作被拒绝时，在 `events` 留一行，`operation` 为原操作名，`detail` 写 `{"rejected": <错误码>, "request_id": <编号>}`。要求：

- 不写 payload 全文，避免把口令、token 一类内容带进库；
- `request_id` 缺失或与既有记录冲突时仍然留痕，`request_id` 写 `null`；
- 这一行不影响任何既有判定：`events` 仍按 `ticket_id` 查，拒绝行的 `ticket_id` 取自 payload（没有就为空）；
- `requests` 表的幂等语义不变：被拒绝的调用不写 `requests` 行，用同一编号重试仍会重新判定。

### R4 进度与收尾可观测

`python tools/work_gate.py --list` 在现有四列之后增加两列：尝试开始时间、本单最后一次事件时间（取自 `events` 的最大 `created_at`），并在末尾打印「共 N 张在途，其中 M 张最后落库超过 45 分钟」。

`--stalled-minutes N` 是可选参数，只覆盖上面那个统计阈值（默认 45）：**传了才判红，不传只统计**。传了 `N` 且确实有单的最后事件时间距今超过 `N` 分钟时，退出码 1，并在 stderr 打印一行「疑似停住：」后跟工单号与各自最后事件时间；不传 `N` 时按默认 45 分钟统计、照旧打印同一句汇总，这一项恒不判红——**不传参数时，`--list` 的退出码不会因为「某张单超过 45 分钟没落库」变成 1**，只可能因为别的项非零（例如「本轮 R-00N 未收尾」）。之所以不设默认判红：这份清单有两个场合在用，巡检要一条能变红的命令（传参数），开工前查「有没有人在做」却不该因为别人正在跑就跑不成，否则钩子与日常检查会把它当噪声跳过。传了非正整数（`0` 或负数）按用法错误处理：stderr 提示「--stalled-minutes 必须是正整数（分钟）；不传就只统计不判红」，退出码 1。

`list_unmerged` 增加 `since_days`（整数，1–365，可选）：给了就只列 `created_at` 在这个天数之内的已验收未合并单。

`python tools/close_gate.py --check` 增加一条现场事实：**窗口内**没有「已验收但未合并」的工单。

窗口口径三件事写死，不留解释空间：

- **长度**：默认 7 天，用 `--unmerged-days N`（整数，1–365）覆盖；起点是「现在减去 N 天」，落在 `created_at >= 起点` 的算窗口内。
- **按哪个时间算**：按工单的 `created_at`（开单时间），不按验收通过时间、也不按分支合并时间。
- **判据**：`state='done'`、没有合并记录、且 `created_at` 在窗口内的那几张单，就是这条事实要求为空集合；非空时退出码 1。窗口外的单（`created_at` 早于窗口起点的已验收未合并单）不在这条里，**明确不算超窗、不判红**。

窗口外单必须排除，不是宽容：本仓库有一批历史单是直接在 `master` 上做的、没有合并记录，永远合不了（清单用 `python tools/auto_merge.py --list` 查，2026-11-21 那次是 `ai-workspace` 17 张）。把它们算进这条，每一轮收尾都会恒为红，闸门就退化成一句噪声，人只会学会跳过它。所以「本轮之前的历史单不算超窗」与上面 `list_unmerged` 的 `since_days` 同一起点、同一算法，只是默认值不同（`since_days` 不传是全量，这一条不传是按 7 天判）。

超窗时怎么报：退出码 1，先一行汇总「窗口 N 天内有 M 张已验收未合并」，随后逐张点名，每张写 `工单号（created_at <时间戳>，开单第 K 天）` 并给补法——能合就跑 `python tools/auto_merge.py --ticket <工单号>`，这一轮合不了的就在 `recover_ticket` 的 reason 里写清为什么留着不合并。报的是窗口内全部单号，不截断、不抽样，窗口外的一张也不列。

这一条没有「只统计」的模式：只要窗口内有单就非零，默认 7 天本身就是它的判红口径。

### R5 安装面检查

新增 `python tools/project_doctor.py [--db <库>] [--json]`，对每个已登记项目只读检查三件事：

- 这个根是 git 仓库时，`core.hooksPath` 是否指向本仓库的 `.githooks`；
- `.worktrees/` 是否在 `.gitignore` 里；
- 仓库根是否有 `AGENTS.md` 或 `CLAUDE.md`。

有任何一项不成立时退出码 1，逐项打印「哪个项目、缺哪项、怎么补」。全部成立时退出码 0。非 git 项目只报「不是仓库，不检查钩子」，不算失败。

### R6 作废语义：改判据不作废在飞的工作

一个数管一件事，不许一个动作同时改两个。

- `criteria_version`（工单级与尝试级各一列）**只随判据变**：`revise_ticket` 每调用一次且 `criteria` 确有变化时 `+1`，回执回显 `from` / `to` 两个值。它不触发任何尝试状态变化。
- `revision` **只随换会话或重开变**：`recover_ticket`、`cancel_ticket`、`revise_ticket` 传 `restart: true` 这三条路各 `+1`；这三条路径之外，包括普通 `revise_ticket`，`revision` 一动不动。

**作废尝试只有三个入口**：`recover_ticket`、`cancel_ticket`、`revise_ticket` 带 `restart: true`。三者都把当前尝试置 `superseded`（未被验收的提交与开放问题按既有口径处理），其余任何动作——包括 `revise_ticket` 改判据——都不得改 `attempts.state`、不得清空 `current_attempt`。

改判据时若有尝试在飞（`dispatching` / `running` / `awaiting_review` / `blocked`），回执必须带 `must_wake` 对象，含三样：`session_id`（该尝试绑定的会话）、`attempt_id`、`criteria_version`（`from` 与 `to` 两个值）。同一时刻写一条 `criteria_revised_in_flight` 事件，`detail` 里记同样三样。回执带 `must_wake` 不等于消息已经发出去——它只回答「要叫谁、为什么叫」，发送仍由协调会话按 `PRD-005` §4.1 那条路走。

### R7 基座身份：每份提交说得出基于哪版目标分支

`submit_result` 的 `base_sha` **必填**，收 40 位十六进制（与 `head_sha` 同一道形状闸门），取法写死一条命令：在提交处的工作树里跑 `git merge-base HEAD <目标分支>`（默认 `<目标分支>` 为 `master`），把输出原样填进来。不许填「填表那一刻 master 的 sha」——rebase 之后两者语义不同：`merge-base` 是「这棵树实际从哪分叉」，master 的 sha 只说明「填表那一刻 master 在哪」。

`list_tickets` 增加 `behind` 列：`git rev-list --count <head_sha>..<目标分支>`，即目标分支上有、这份提交里没有的提交数。算不出来时写 `?`，**不写 `0`**——`head_sha` 为 NULL 的历史提交、分支已被删、仓库不可达，这三种情况写 0 就和「基于最新 master」分不开，那个 0 会变成一句假话。

### R8 租约与滞留：死会话不再无声占着槽位

`attempts.last_seen` 在该尝试每次落库动作时刷新。刷新点集中在一处写入层函数里，不在各操作里各写一遍；覆盖 `bind_session`、`submit_result`、`ask_ticket`、`answer_ticket`、`record_notice` 这些落到这条尝试上的写操作。

滞留阈值写死为 **45 分钟**，与 `python tools/work_gate.py --list` 现有的 45 分钟口径同一根：`idle_minutes >= 45` 记为滞留。阈值按项目可配不算实现——那样验收时对不出同一个数。

滞留**只标记不改状态**：`get_ticket` / `list_tickets` 增 `idle_minutes`（整数）与 `stale`（布尔）两个只读字段，工单 `state`、尝试 `state`、`revision` 一个字节不动。要结束一张滞留单仍然只能由人/协调会话走 `recover_ticket`。

`claim_ticket` 增可选 `preempt_stale`（布尔，默认 false）：只有显式传 `true` 才领得走一张滞留单（它的最新 `last_seen` 已超 45 分钟）；成功后写一条 `preempted_stale` 事件，`detail` 点名被抢占的 `attempt_id`、它的 `session_id` 与 `last_seen`。不传 `preempt_stale` 时滞留单照旧报 `DISPATCH_BUSY`，不自动抢占。

### R9 资源互斥：同一件物理资源只有一个主人

资源标识的形状写死为 `资源:<类型>:<值>`：冒号分隔、三段都非空、`值` 不含空白，例如 `资源:device:8BBUT26815006530`、`资源:port:8712`。形状不对（缺 `资源:` 前缀、少一段、多一段、值里带空白）报 `INVALID_INPUT` 并点名是哪一条。它与 R2 的 `parallel_scope` 里那种写法共用一个解析器——声明与占用不能是两套语法。

`claim_ticket` 的 `resource_scope` 里每条 `资源:` 标识给该尝试登记一条占用（`resource_key`、`attempt_id`、`acquired_at`、`expires_at`）。同一个 `resource_key` 已被**未过期**的占用持有时报 `RESOURCE_BUSY`：工单停在原状态、一行占用都不写，回执点名三件事——持有它的**工单号**、持有它的**尝试 `attempt_id`**、以及该占用的 **`expires_at`**（UTC ISO 8601）。判定跨项目生效：同一个 `resource_key` 不分项目。判定顺序排在 `DISPATCH_BUSY` 之后、写库之前——先越过串行保护，才轮到资源这一道。

`expires_at <= 现在` 的占用视为已归还，可被重新领取；尝试被 `superseded` 或整张单进入终结状态时占用随之归还，不必等到过期。

### R10 合并唯一入口：合并提交只来自 `auto_merge`

`.githooks/commit-msg` 增加合并提交校验：仓库里存在 `MERGE_HEAD` 时，必须能在 `.data/merge-journal/<工单号>.json` 读到本次合并的记录，且记录里的 `pid` 对应进程还活着；两者任一不成立就拒绝这次提交，stderr 打印「合并只能走 `python tools/auto_merge.py --ticket <工单号>`」，退出码 1。

journal 由 `auto_merge` 在 `git merge` 之前写下（含 `ticket_id`、`pid`、`target_branch`、`source_branch`、`started_at`），合并成功、`merge_ticket` 写回记录之后删掉。所以「有 `MERGE_HEAD` 却没有活着的 journal」只有一种解释：这次合并不是 `auto_merge` 发起的，或者是它失败退出后留下的半成品——两种情况都不该留下合并提交。

主检出守卫：`tools/auto_merge.py` 在目标检出的当前分支不是目标分支（默认 `master`）时拒绝执行——非零退出，目标分支与源分支都不动，打印自愈命令 `git -C {{WORKSPACE}} switch master`。`python tools/work_gate.py --list` 增一列「主检出当前分支」，不在目标分支时打印同一行警告与同一条自愈命令，既有各列的判红口径不变。
