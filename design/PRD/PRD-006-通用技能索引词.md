## 1. 要解决什么问题

PRD-004 建了节点级路由表，但那张表只在**被加载之后**起作用。一个会话在加载任何 skill 之前，能看到的只有每个 skill 的 `name` 和 `description` 一行。所以「能不能调到合适的 skill」这件事，最后落在这些行字上——就是处置表「本机通用 / 接入」那一组，一个 skill 对应一行 `description`（截至 2026-11-18 是 20 行）。

现在这组字有两个毛病：

1. **说的是上游的通用词，不是我们卡住时说的话。** 典型：`test-driven-development` 是 “Use when implementing any feature or bugfix, before writing implementation code”。我们实际的想法是「先写测试还是先写实现」。字面上一句都不重合。
2. **个别 `description` 在描述别的项目。** `merge-latest-branches` 写的是「合并所有分支、**发布看板**、冲突自动处理后继续」——那是看板项目的语境。我们 N22 要的是「验收通过后合进 master，测试绿才合」，它一个字没提。

还有第三个，属于结构而非措辞：N08（计划）、N19（审查）、N27（并行/续接）各挂着 3 个 skill，三行 `description` 互相不可区分，光看索引判断不出该读哪个。

把这些都压给 `skill-routing` 一行 `description` 是不合理的：那等于让一个单点承担 35 个 skill 的召回。

## 2. 边界：只写索引，不改内容

| 做 | 不做 |
| --- | --- |
| 改「本机通用 / 接入」那一组通用 skill 的 `description` 一行（条数以处置表为准，截至 2026-11-18 是 20 个） | 不改任何 skill 的正文（`---` 之后的内容） |
| 每行补入真实的中文触发句（「测试红了」「验收完了要不要合」） | 不新增、不删除、不重命名 skill |
| 改完把 live 快照进仓库（连 `description:` 行一起），登记之后正文再被改能当场发现 | 不动本仓库 `.agents/skills/` 下 4 个的 `SKILL.md` |
| 仓库里存「期望索引词表」，脚本比对 live 文件 | 不动 Cindy 托管的 2 个（`cindy-skill-creator`、`learn`） |
| 只动 `description` 而不是加长整份文件 | 不改 `nodes.md` / `roles.md` / `installed-skills.md` 的路由结构 |

为什么只改 `description`：它是唯一进入提示的那一行。正文再改也不会增加召回，改错了反而污染别的项目。

## 3. 为什么要把改动同时落进仓库

这一组文件在 `~/.agents/skills/`（条数随处置表变化，截至 2026-11-18 是 20 个），多数是 `D:/agent-skills/installed/` 的副本（2026-11-16 从 obra/superpowers 等 5 个上游仓库安装），**不在任何版本控制里**。直接改字有三重风险：改坏了没有 diff 可看；上游更新时被静默覆盖；事后没人知道当初改了什么。

所以本 PRD 要求三件配套物，全部进仓库：

1. **快照**：每个接入文件**最近一次登记时** live 的逐字节副本（连 `description:` 行一起），用于「正文在登记之后有没有被改过」的比对，以及把文件还原到那次登记的样子。它**不是**改前存档：改前原文只在 git 历史里，取法见 R5。
2. **期望索引词表**：每个 skill 必须命中哪几个中文触发词。这是意图的唯一记录。
3. **校验脚本**：比对 live 文件的 `description` 与期望词表；不一致就非零退出并指出是哪个 skill 少了哪个词。上游覆盖了我们的改动，它会当场报错。

## 4. 需求条目

**R1 范围**：「接入」节点的通用 skill，即 `installed-skills.md` 的「本机通用 / 接入」那一组；名单与条数以该表为准，本文不写死数字（截至 2026-11-18 是 20 个）。处置表加一行，范围就自动跟着变。

**R2 只改一行**：改动只落在 `description:` 这一行，正文一个字不动。快照记的是 live 的整份逐字节副本——连 `description:` 行一起，不剔除、不虚构「改前」，所以文件与快照之间**不存在「允许不同的那一行」**：正文被改过就报 `body-changed`，`description:` 写成别的措辞就报 `description-drifted`（判据是词表里的 `approved`，不是「这次改没改过」）；两者都绿时，live 与快照整份逐字节相同（含 `description:` 行）。两把尺子用 `--only body` 与 `--only desc` 分开，`body` 一侧比对时把 `description:` 行剔除，只是为了同一处差异不被报两次，不意味着那一行允许不同——`test_check_index.py` 有这条反例。适用范围限于「登记之后」：快照证明不了「当初除了这一行一个字节都没动过」，那段差异只留在 git 历史里（见 R5）。

**R3 中文触发词**：每个 `description` 至少包含 2 个来自真实工作语言的触发短语（例：「测试红了」「验收完了要不要合」「拆任务」「断点续跑」「像标签堆叠」）。词表本身要能被机器读出来，不是靠人读着像。

**R4 长度受控**：每个 `description` 不超过 240 个字符（现状 79–487，已有 405/487 两个偏长的）。过长的索引会挤占提示，且不增加命中率。

**R5 快照与回滚**：快照是**最近一次登记时** live 的逐字节副本（含 `description:` 行），不是「加索引词之前」的原样。它足以把任意一个文件还原成**最近一次登记的状态**，还原后 `--only body` 应为通过。

要取**改前正文**（上游原始的 `description` 与正文），去 git 历史：本仓库最后一次保留「改前原样」快照的提交是 `edaa04f`。

```bash
git show edaa04f:.agents/skills/skill-routing/index/snapshot/<skill>/SKILL.md
```

别拿 `git show edaa04f:skills/<skill>/SKILL.md` 当改前：`skills/` 入库（AW-039）发生在索引词改写之后，那份里已经是改后文本。

**R6 校验可复现**：一条命令能回答「处置表上那一组是否都与期望一致」（条数以该表为准，截至 2026-11-18 是 20 个，脚本按词表逐条比对，不靠文档里的数）；不符时退出非零并列出 `skill / 缺失词`。

**R7 反例有效**：脚本自身的用例要能证明它会失败——故意删掉一个期望词、故意改坏一个文件，都必须让检查变红。

## 7. 未实现 / 待验证

- 未实现：**命中率的实证**。本 PRD 能证明「每个 skill 的索引里有了我们说得出的话」，不能证明「会话因此更容易加载它」。后者要在真实会话里验：给一个只带中文问句的探测会话，看它读没读对应文件。
- 未验证：上游更新后快照与 live 的差异处理流程（脚本会报错，但重打补丁的动作还没写进任何文档）。
- 已知不改：同节点多 skill 的「该读哪个」，仍由 `skill-routing` 的 `roles.md` 与 `nodes.md` 兜底，本单不解决索引层面的互相区分。
