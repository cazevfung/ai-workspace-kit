## 1. 要解决什么问题

到 2026-11-21 晚，同一个项目上同时有几个主任务在派单，而「谁在写哪个文件、谁有权改项目级的东西、这次改动是不是第 N 次改同一个文件」三件事在库里都没有位置。四条可核对的事实：

- **同一个文件在 34 分钟里被三张单接力改。** 2026-11-21 当天 `AGENTS.md` 被四张单改过：`AW-082`（13:43 加「消息通道发前闸门」几条）、`AW-091`（18:26 在常用命令里加一行 `idle_watch`）、`AW-092`（18:52 把 `AGENTS.md` 里一处行号引用从旧值改成 `582`，改的是 `fingerprint(project["root"], path)` 那一行在 `task_center/core.py` 里的位置）、`AW-095`（19:00 加第八条本体 8 行）。后三张单的提交时间 18:26 / 18:52 / 19:00 全落在 34 分钟里，三张单分属两个协调会话（`AW-091`、`AW-095` 是 `7ab2590d` 派的，`AW-092` 是 `a7e4ca66` 派的）。复算：

  ```bash
  git log --all --since='7 days ago' --pretty='%ad %s' --date=format:'%m-%d %H:%M' -- AGENTS.md
  ```

  期望看到 `11-21 18:26 AW-091 …`、`11-21 18:52 AW-092 …`、`11-21 19:00 AW-095 …` 三行，以及 `11-21 13:43 AW-082 …`。**这三处改动互相不知道对方存在**：`AW-092` 改行号、`AW-095` 改同文件另一节，谁都没读对方的成果，只是恰好没撞同一行。

- **第三张单是第一张单的 bug，隔了两小时。** `tools/idle_watch.py` 被三张单改：`AW-091` 建（2026-11-21 18:26 +08:00 / 10:26Z）、`AW-093` 校准（18:46 / 10:46Z）、`AW-098` 修判法（同一张单两次提交：20:20 / 12:20Z 与 20:27 / 12:27Z）。第三张单修的正是第一张单建的那部分（`meta_kind` 判序），从第一张单那条提交（18:26）到 `AW-098` 第一次修改它（20:20）隔了 1 小时 54 分（算到 20:27 那次就是 2 小时 1 分）。**这五条提交分四张单、各自先在 `ticket/<单号>` 上，再按 18:36（`a386ef4`，`AW-091`）、18:53（`5973483`，`AW-093`）、20:43（`c09a8d7`，`AW-098`）三个时间点陆续合进 master；`AW-100` 的 `ce18305`（20:48）到现在只在 `ticket/AW-100` 上**。也就是说「这个文件现在是什么版本」在当晚换过四次，而每次都得人手去看。复算：

  ```bash
  git log --all --pretty='%ad %s' --date=format:'%m-%d %H:%M' -- tools/idle_watch.py
  ```

  期望 5 行（时间倒序）：`11-21 20:48 AW-100 …`、`11-21 20:27 AW-098 …`、`11-21 20:20 AW-098 …`、`11-21 18:46 AW-093 …`、`11-21 18:26 AW-091 …`。这条事实有两面：反复改同一个文件本身，以及**改到第几版了看不出来**——同一个文件的版本演进横在 master 与未合并分支两处，只查 master 会在某个窗口里少算一张单（本单 v0.1 就栽在这里：提交证据里把「`AW-098` 还没合」当成了当下事实，而它在 PRD 提交前 2 分 32 秒就已经合了，见 §9）。

- **「这一轮」只有一个，协调者不止一个。** R-015 的轮次目标是占用/作废/合并那五条（原文在 `tasks/closing-R-015.md` §1），`tasks/rounds.md` 的 R-015 行只记了 `AW-090` 与 `AW-092`——两张都是 `a7e4ca66` 派的。同一天 `7ab2590d`（在跑的巡检会话）派出并做完的 `AW-091`、`AW-093`、`AW-095`，加上当天还在验收、当晚 20:43:04 才合入的 `AW-098`，**四张单没有作为任何一轮的成果进过 `closing-R-*.md`**：它们的单号在一份收尾包里出现过，但只在 R-015 的「未做到或偏离」第 7 条「编号两次被抢」里被当成债务例证记了一笔（`tasks/closing-R-015.md` 第 3 节第 7 条，提到 `AW-091`、`AW-093`），**没有任何一份收尾包把这四张单当成本轮成果**，它们也没有在任何 `round.md` 的目标里出现过。`tasks/round.md` 是工作区级单份的，写在上面的「本轮目标」只能属于一个协调者，而项目级的事（升 schema、改 PRD、合并、收尾）当天有两拨人在做。复算：

  ```bash
  grep -n "AW-09" tasks/rounds.md | tail -3
  ```

  期望 R-015 那一行（`tasks/rounds.md:25`）只出现 `AW-090` 与 `AW-092`，没有 `AW-091` / `AW-093` / `AW-095` / `AW-098`。再看四张单的单号在收尾包里到底哪儿出现过：

  ```bash
  grep -rn "AW-091\|AW-093\|AW-095\|AW-098" tasks/closing-*.md
  ```

  期望只命中 `tasks/closing-R-015.md:34` 那一行（第 3 节第 7 条「编号两次被抢」），不出现第二处——即只在债务里被提过，没被当成任何一轮的成果。

- **并行的写域声明可以是不准的，而不准不会被发现。** 2026-11-21 本项目有 5 张单带 `allow_parallel_override` 领走（`AW-091`、`AW-092`、`AW-093`、`AW-095`、`AW-098`）。其中 `AW-092` 声明的是

  ```json
  "parallel_scope": ["task_center/", "tests/", "docs/protocol.md"]
  ```

  而它实际改了 17 个文件，**声明之外的有 5 个**：`AGENTS.md`、`PRD/PRD-013-工单机制的执行面.md`、`tasks/independent-review.md`、`tools/work_gate.py`、`tools/test_work_gate.py`。而当时并行的 `AW-091` 声明的写域恰好包含 `文件:AGENTS.md`。复算：

  ```bash
  git diff --name-only 5973483 abf6b1b        # abf6b1b 是 AW-092 的合并提交，5973483 是它合并前的 master
  ```

  期望输出里同时有 `AGENTS.md` 与 `PRD/PRD-013-工单机制的执行面.md`，而上面那行 `parallel_scope` 里两个都没有。这条事实最贵的部分是它**连带骗了下一张单**：`AW-095` 领单时的 `parallel_reason` 原文写着「AW-092 在 task_center/ 与 PRD 文档里做 schema 9→10，…本单只改 AGENTS.md 一个文件」——它信的是 `AW-092` 的声明，而那份声明是错的，于是两张单同时在改 `AGENTS.md`。它们没撞，只是因为改的是不同行。

这四条不是四件小事，是同一条结构缺失的四个出口：**派单是按「一张单一个会话一棵树」设计的，而现实中是「多张单、多个协调者、同一批文件」。** 前者能表达的检查只有串行保护与写域声明，两者都在单张单的粒度上；一旦有人在一张单里顺手改了别的东西（上面第四条），或者三张单接力改同一个文件（第一、二条），或者两个协调者各自认领「这一轮」（第三条），库里看不出来，闸门也判不了。

### R1 搭车：一张分支带多张单、一次验收

**定义。** 一组搭车 = `ticket_links` 里 `rides_with` 边的**一个连通分量**（`PRD-014` 的 R3 已定这个 kind 与「不单独拦」，本文只追加它的用法层）。组号取组内**号最小**的那张单（号由库发、单调递增，所以最小号就是最早建的那张），展示为 `ride:AW-101`，那一张叫**车头单**。一组至少两张单——一张单不叫搭车。

**不新增 schema。** 组的存在完全由已经有的三样东西表达：`ticket_links` 的 `rides_with` 边、`tickets.batch_id`（`PRD-014` R4 的车次）、`attempts.session_id`。不另设 `ride_id` 列：一个组既要能被并发校验、又要能被合并校验，用边加车次已经够，多一列就是多一处需要同步的真相。

#### R1.1 `rides_with` 与车次的区别

两者都回答「这几张单绑在一起」，但回答的不是同一个问题，不能互相替代：

| | 车次（`PRD-014` 的 R4，`batches`） | 搭车组（本条新增） |
| --- | --- | --- |
| 回答什么问题 | **资源占用窗口**：谁占着资源、一次构建、什么时候归还 | **开发与验收单元**：哪几张单共用一棵树、一次验收、谁验收 |
| 最小规模 | 1 张单（单张也能成车次） | 2 张单（一张不叫搭车） |
| 库里怎么表达 | `batches.id` + `tickets.batch_id` + `batches.owner_session_id` | `ticket_links` 里 `rides_with` 边的连通分量 |
| 结束标志 | 车次内最后一张单写合并记录，`batches.closed_at` 落值 | 组内最后一张单的验收结论落下、合并记录写完（本轮两者同时发生，见下） |
| 谁读它 | `claim_ticket`（槽位与 `BATCH_OWNED_BY_OTHER` 校验）、`auto_merge`（一次合并） | 执行会话（一棵树）、验收会话（一次验收）、`review_result` 与 `merge_ticket`（整组联动） |

**两组关系写死一条：一组搭车必须整组落在同一个车次里**——否则一个会话拿不到第二张活跃尝试（`attempts` 的槽位放宽是 `PRD-014` R4 给的，只有带 `batch_key` 的单才不占那条索引）。**本轮默认一组对应一个车次**（`batches` 里一行、`closed_at` 与组内最后一张单的合并记录同时落）；一个车次装多组搭车不在本轮实施范围，留 §7 未决。`PRD-014` 的车次语义（谁持有、三种释放时机、一次合并）一个字不改。

#### R1.2 五个动作各怎么写

组内 N 张单始终只有**一棵工作树**：`.worktrees/<车头单号>/`，分支 `ticket/<车头单号>`。组内其它单不建树、不建分支。理由不是省事：多棵树等于同一文件在两个树里各写一遍，合并时必然撞——而撞的正是 R2 要预演的那种冲突。

| 动作 | 做几次、谁做 | 写什么 | 验收会话一眼能核的事实 |
| --- | --- | --- | --- |
| `claim_ticket` | 组内**每张单各一次**，全部由同一个协调会话派给同一个执行会话；车头单先领 | 第 2 张起必须 `allow_parallel: true` + `parallel_reason`（写明「与车头单 `<车头单号>` 同组 `ride:<车头单号>`」）+ `parallel_scope`（整组共同改的路径）；组内每张单带同一个 `batch_id` | `events` 里每张单各一行 `claim_ticket`，`parallel_with` 点名车头单；`get_ticket` 里组内单的 `batch_id` 全同 |
| `bind_session` | 组内**每张单各一次** | 组内所有 attempt 的 `session_id` 必须相同（同一个执行会话；换人 = 整组 `recover_ticket`，不允许单独换一张） | 组内每张单的 `attempts[-1].session_id` 逐字相同 |
| `submit_result` | 组内**每张单各一次** | 各自 `artifacts`（**只列本单改的文件**，路径前缀是车头单的工作树 `.worktrees/<车头单号>/`，不是自己的单号——没有自己那棵树）+ 同一个 `head_sha` + 同一个 `base_sha`；R2 的 `conflict_preview` 各算一次（同一 `<head>` 与同一目标分支，结果必然相同） | 组内每张单的 `submissions[-1].head_sha` 逐字相同；`git rev-parse ticket/<车头单号>` 与它们相等 |
| `review_result` | 整组**只一次** | 对**车头单**跑一次，payload 带 `ride` 数组（组内全部单号）；库给组内每张单各写一行 review，同一个 `review_id`、同一个 `verdict` | 组内 N 张单的 `reviews[-1].review_id` 相同、`verdict` 相同 |
| `merge_ticket` / `auto_merge` | 整组**只一次** | 只对车次最后一张单跑 `auto_merge`（`PRD-014` R4.5 已定）；合并成功后组内**每张单各写一条合并记录，`commit_sha` 相同** | `merges` 里组内 N 张单各一行、`commit_sha` 相同；`python tools/auto_merge.py --list` 不再列它们 |

**验收对象写死一句：组的分支头（`head_sha`），一棵树，一次 `run_tests`，一次逐条 AC。** 不是「每张单各一棵树各验一次」。这条不是风格选择：`tools/close_gate.py` 的「窗口内已验收未合并」事实与 `list_unmerged` 都按单算，组内只给车头单写合并记录的话，其余 N-1 张会永远停在「已验收未合并」，每轮收尾都恒为红——闸门退化成噪声，人只会学会跳过它。所以「一次验收」必须配「整组各一条合并记录」，两件事一起写死。

#### R1.3 验收条件

- AC-R1-1（命令类）：在副本库上把一组两张单（`blocked_by` 无关，用 `rides_with` 相连、同一 `batch_id`）都领到同一个会话下：第二张必须传 `allow_parallel: true` 与 `parallel_reason`。期望 `get_ticket` 两张单 `state=running`、`attempts[-1].session_id` 逐字相同、`batch_id` 相同；第二张的 `claim_ticket` 事件里 `parallel_with` 点名第一张。
- AC-R1-2（命令类）：组内两张单各自 `submit_result`（同一 `<head>`）后，`git rev-parse ticket/<车头单号>` 与两张单的 `submissions[-1].head_sha` 三者逐字相同；第二张单的 `submissions[-1].artifacts[].path` 每一行都以 `.worktrees/<车头单号>/` 开头，没有一行以 `.worktrees/<第二张单号>/` 开头（`grep -c "\.worktrees/<第二张单号>/"` 期望 `0`），且 `git worktree list` 里没有第二棵树（`git worktree list | grep -c "<第二张单号>"` 期望 `0`）。
- AC-R1-3（命令类）：对车头单跑一次 `review_result` 带 `ride` 数组后，组内 N 张单的 `reviews[-1].review_id` 相同且 `verdict` 相同；只跑 `auto_merge --ticket <车次最后一张单>` 之后，`merges` 里组内 N 张单各一行、`commit_sha` 相同、`python tools/auto_merge.py --list` 不再列它们。
- AC-R1-4（判断类）：五个动作是否各被写清「做几次、写什么、谁核」，且「一次几棵树」「一次几次验收」「验收对象是谁」三个问题各只有一个答案，`rides_with` 与车次的区别是否同时回答了「谁读它」与「最小规模」。反例：只写「支持几张相关的单一起做掉」而不回答一次多少棵树、一次几次验收。

### R2 提交时冲突预演

**在哪个操作里跑：`submit_result`。** 理由：提交是唯一一个「分支已经成型、还没进验收」的时刻——早于此分支还在长，晚于此时验收会话已经在读一份看不出冲突的成果。

**命令写死一条：**

```bash
git merge-tree --write-tree --name-only <head_sha> <目标分支当前 tip>
```

`<目标分支>` 默认 `master`，与 `base_sha` 同一口径；`<目标分支当前 tip>` 用 `git rev-parse <目标分支>` 取，**不是** `base_sha`——预演问的是「这份成果将来合进现在的目标分支会撞哪些文件」，用分叉点问等于没问。

**输出怎么读（2026-11-21 在 git 2.53.0 上实测）：**

- 第一行是这次合并的树对象 id，不是文件；
- **其后到第一个空行为止的每一行是一个冲突文件路径**（相对仓库根、`/` 分隔），无冲突时这一区为空；
- 空行之后的 `Auto-merging …` / `CONFLICT (content): …` 是给人读的说明，**不进字段**；
- 退出码：无冲突 `0`，有冲突 `1`。

**回执字段叫 `conflict_preview`**，`submit_result` 回执与 `get_ticket` 的 `submissions[-1]` 里同名同形：

```json
{
  "target_branch": "master",
  "target_sha": "<40 位十六进制，预演那一刻目标分支的 tip>",
  "command": "git merge-tree --write-tree --name-only <head_sha> master",
  "exit_code": 0,
  "conflicts": []
}
```

- **无冲突时怎么表现：`conflicts` 是空数组、`exit_code` 是 `0`，字段照常出现，不是省略、不是 `null`。** 理由同 `PRD-013` R7 对 `behind` 的零值口径：字段缺席与「预演跑过且没撞」必须分得开，否则验收会话无法判断这一项有没有真的跑。
- **有冲突时：`conflicts` 是按字母序去重后的路径数组、`exit_code` 是 `1`，`ok` 仍然是 `true`。** 预演是给人看的事实，不是拒绝的理由：提交那一刻撞不撞不等于最终撞不撞（分支还要 rebase、重订，另一次提交可能就干净了）。把它做成闸门只会教人先 rebase 一次再提交，回执里就再也看不到真相。
- **算不出来时 `conflict_preview` 为 `null`**（仓库不可达、`head_sha` 不在本地、git 不可用）。写成一堆空值等于说「预演过了、没冲突」，那是一句假话。
- **落库：`submissions` 增一列 `conflict_preview`**（JSON 文本，可空）。`list_tickets` 不加列——它是验收时要看的东西，不是每轮开工要看的。

**验收会话该看到什么：** `get_ticket` 的 `submissions[-1].conflict_preview.conflicts` 非空时，验收会话必须在 `review_result` 的 `evidence` 里贴出这些路径，并逐条写出它怎么处理的（分支已 rebase 所以不复现 / 判定两边改的不是同一处 / 确实是冲突，判 reject）。**只看到 `ok=true` 就判 accept 算漏项**——`ok=true` 与「预演跑过且干净」是两件事。

#### R2.1 验收条件

- AC-R2-1（命令类）：在临时分支上造一次必撞的改动（同一文件同一行两边各改一次），`submit_result` 回执 `conflict_preview.conflicts` 含该路径、`exit_code` 为 `1`、`ok` 为 `true`；`get_ticket` 的 `submissions[-1].conflict_preview` 与回执逐字相同。
- AC-R2-2（命令类）：干净分支上 `git merge-tree --write-tree --name-only HEAD master` 退出 0、只输出一行树对象；同一分支 `submit_result` 回执落到文件后 `grep -c '"conflict_preview"' <回执文件>` 期望 `1`（字段存在而不是省略），且 `conflict_preview.conflicts` 为 `[]`、`exit_code` 为 `0`。
- AC-R2-3（判断类）：字段名、命令、无冲突时的表现、冲突时验收会话的动作四项是否齐全，且 `conflict_preview` 为 `null` 与 `{"conflicts":[]}` 的区别是否写死。反例：只写「提交时检查一下冲突」而没有字段名与命令。

### R3 项目协调者与项目级写操作

**同一项目同一时刻谁是协调者：** 那个会在 `tasks/round.md` 顶部写下 `协调者：<session id>` 一行的会话。轮次开着的时候，这一行就是唯一答案；轮次没开（`round.md` 没有轮次号）时**没有协调者**，此时任何项目级写操作都要先开一轮并登记——不许「大家都算一点」。

**为什么登记在 `round.md` 而不是库里：** `round.md` 本来就是工作区级单份的，而目前的病正是它只服务一个协调者（§1 第三条）。把它补齐成「一行轮次 + 一行协调者」是零 schema 成本的修法；进库要升 schema，还必须先定「协调者失效后那行怎么办」，那是另一件事。

**哪些算项目级写操作（五类，不多不少）：**

| # | 操作 | 为什么是项目级 | 判得了吗 |
| --- | --- | --- | --- |
| 1 | 改 `tasks/round.md` / `tasks/rounds.md`（轮次目标、结束条件、状态、历史行） | 它定义「这一轮干什么」，一个项目同一时刻只能有一套 | 库层判不了，巡检只报 |
| 2 | `migrate`（升 schema） | 动的是全库，所有项目、所有会话的证据都在里面 | **库层可判**：`migrate` 收 `session_id`，与 `round.md` 的协调者不符报 `NOT_COORDINATOR`，一行不写、版本不动（现状是 `task_center/core.py:505-506` 拿到 `migrate` 直接 return，既不写 `requests` 也不写 `events`，所以今天查不出谁迁的） |
| 3 | 写合并记录（`merge_ticket`，以及 `auto_merge` 的合并提交） | 它改目标分支与 `merges` 表，是所有人下一次 `base_sha` 的依据 | **库层可判**：`merge_ticket` 收 `session_id` 同上；`auto_merge` 在动手之前先核这一项（它最后才调 `merge_ticket`，等到那时已经合完了） |
| 4 | 改 PRD（新增、升版、改验收条件） | 依据一改，在飞的单全部 `STALE_PRD` / 判据失效 | 库层判不了，巡检只报 |
| 5 | 收尾（跑 `close_gate` 之后改状态位、写 `tasks/closing-<轮次>.md`、提交收尾包） | 它宣告「这一轮的事完了」，只能由认了这一轮的人说 | 库层判不了，`close_gate --check` 只报 |

**分两层不是偷懒，是照 `PRD-013` R4 的同一条推理：** 判得出的两件做成硬失败（退出码非零、一行不写），判不出的三件只报——把判不出来的事做成闸门，人只会学会绕过它。

**不是协调者的主任务能做什么：**

- 读全部（`get_ticket` / `list_tickets` / `events` / `work_gate --list` / `idle_watch`）；
- 单级写操作：`claim_ticket`、`bind_session`、`submit_result`、`review_result`，以及**只针对自己这张单**的 `ask_ticket` / `answer_ticket` / `revise_ticket` / `record_notice` / `recover_ticket` / `cancel_ticket`；
- 想改 PRD、想升 schema、想合并、想宣告收尾——**报给协调者**，消息正文只写指针（按 `AGENTS.md` 第六条：不带会过期的编号），由协调者做。

**巡检会话在这个模型里是什么角色：不是协调者，是只读加报告。** 它可以做三件：按 §4 R4 报告反复改动的文件、按巡检口径上报违规（含同步提问卡）、消息层干预（`steer_session` / 排队消息，按 `PRD-005` 三档）。它可以 `recover_ticket` 一张滞留单（单级，且 `reason` 里写明是巡检处置），但**五类项目级写操作一件都不做**。2026-11-21 的现场正好是这条的反例与正例各一半：巡检会话（`7ab2590d`）替协调会话迁过库（第 2 类，越界），而它在一次 `auto_merge` 上把取舍留给了协调会话（第 3 类，让路，正确）。

**冲突时谁让路：先登记先持有。** 两个会话都想做同一类项目级写操作时，`round.md` 上写着名字的那个做，另一个停下，把冲突写进消息（必要就走 `ask_ticket` 落库），不改、不并行、不「我先做完你再补」。持有着失效的判据与巡检同一根：**超过 45 分钟没有任何落库动作**（`PRD-013` R8 的滞留阈值），此时由**人**指定新的协调者并改那一行，库与脚本都不自动切换。

**R3 的实施前置（硬约束，写成本条的一部分）：** R3 的实施单 claim 之前，协调会话必须先把本条（R3 全文）指给**当时在跑的巡检会话**（2026-11-21 是 `7ab2590d`，会话标题「定时监控队列并自动干预卡住的任务」），并把它的回复落进 `tasks/`（同意 / 哪几条权限要留 / 哪几条要改）。**没落之前不许 claim R3 的实施单，不许单方面生效。** 理由不是礼貌：它今天替本项目迁过库、也把 `auto_merge` 的判断留给了协调者，这条规则直接收窄它的权限范围；先对齐再落，才不会出现「规则生效的那一刻，正在干活的那个会话突然越界」。

#### R3.1 验收条件

- AC-R3-1（命令类）：实施后 `head -6 tasks/round.md` 含 `协调者：<40 位以内的会话标识>` 一行；同一项目另一会话在同一时刻跑 `migrate`（在副本库上）期望 `ok=false`、`error.code=NOT_COORDINATOR`、`pragma user_version` 不变；登记的那个会话跑同一调用期望成功。
- AC-R3-2（命令类）：非登记会话跑 `python tools/auto_merge.py --ticket <一张 done 且未合并的单>` 期望非零退出、stderr 含 `NOT_COORDINATOR`，且 `git rev-parse master` 与 `merges` 表行数都不变；`--dry-run` 不受这条约束（它本来就不合并）。
- AC-R3-3（判断类）：五类项目级写操作是否逐类写出「为什么是项目级」与「判得了吗」，非协调者能做的事是否逐项点名（含「只针对自己这张单」这个限定），巡检会话的角色是否同时写出「可以做哪三件」与「五类都不做」，冲突让路是否给出「先登记先持有 + 45 分钟失效 + 由人指定」三个可判条件。反例：只写「每个项目要有一个协调者」而不说它管哪些操作、别人还能做什么。
- AC-R3-4（命令类·把「先与巡检会话对齐」变成可失败的检查）：R3 实施单 claim 之前，对齐记录必须已经落盘——文件名含「项目协调者」（例 `tasks/plan-0NN-项目协调者.md`），并原文抄录巡检会话的回复（至少一句可直接 grep 的原话片段）；`grep -c "<该原话片段>" tasks/plan-*-项目协调者.md` 期望不小于 `1`；同一段内容必须同时能在库里查到一条 `record_notice`（`get_ticket` 的 `notices` 里 `detail` 含该片段，`origin_session_id` 是协调会话）；R3 实施单的 `criteria` 必须包含本条（在 R3 实施单上 `get_ticket` 的 `criteria` 里 `grep -c "AC-R3-4"` 期望不小于 `1`），否则不许 claim。
  **为什么要单设一条**：v0.1 只把「先对齐」写在 R3 正文与 §7 的默认值里，AC-R3-1/2/3 没有任何一条会因为「没对齐」而失败——那就是一句靠人记得的话。

### R4 同文件反复被改的只读指标

**做在哪：新增 `python tools/churn_watch.py`**（只读脚本，与 `tools/project_doctor.py` 同一类：只报不拦、不改库）。

**窗口：默认 7 天，`--days N` 覆盖（1–365），`--until <UTC ISO 8601>` 给窗口的右端（缺省是现在）。** 起点是「右端减去 N 天」，按**提交时间**算，落在窗口内的提交参与统计。`--until` 不是锦上添花：没有它，这条指标的任何验收条件都只能写出「今天命中哪两行」，明天跑就不一样了——验收条件必须能在任何一天跑出同一个数。

**扫描范围：所有引用上的提交（`git log --all`），不只是 `master`。** 理由就是 §1 第二条：同一个文件的版本横在 master 与未合并分支两处（`AW-098` 的两条提交在 20:27 时只在 `ticket/AW-098` 上，直到 20:43 才合；`AW-100` 的 `ce18305` 现在只在 `ticket/AW-100` 上），只看 `master` 会在某个窗口里少算，而最该被看见的恰是还没合进来的那一版。但要说清一件事：**一旦那些提交被合进 master，master 的历史里也数得到它们，两种取法在那些窗口上就没差别了**——所以「只扫 master 是错的」不能靠当前仓库现场去证伪，它靠 AC-R4-1 的夹具（§4 R4.1）证伪。

**阈值：同一文件在窗口内被 ≥ 3 张不同工单改过，`--min-tickets M` 覆盖（默认 3）。** 「不同工单」从提交标题里取 `<前缀>-<三位数>`（`AW-092`、`CHM-037`）；**同一个工单的多条提交只算一张单**；取不到单号的提交（例如「本轮开始时的工作区基线」那几条）不进单数，单独计数，在输出末尾报一行「无单号提交 N 条」——不把它们塞进单数，否则一次备份就会把一个文件推过阈值。

**输出列（五列，顺序写死）：**

| 列 | 内容 |
| --- | --- |
| `文件` | 相对仓库根的路径，`/` 分隔 |
| `单数` | 窗口内改过它的不同工单数 |
| `单号` | 这些单号，按号升序，逗号分隔 |
| `最近一次` | 窗口内最后一次改它的提交时间（UTC ISO 8601）与提交短 sha |
| `最后一单的状态` | 单号最大的那张单在库里的 `state`，查不到写 `?` |

**只读，不改库：** 只跑 `git log` / `git log --name-only` 与一次 `select`（读 `tickets.state`），不写库、不建单、不改文件、不碰工作树。

**只报告不自动开单：** 输出末尾固定一行「要开单请人来开：本条只报告，不建单」，脚本不接受任何「顺手修一下」的参数。

**退出码恒为 0。** 这是报告不是闸门，理由与 `PRD-013` R4 对 `--stalled-minutes` 的处置同一根：一个每轮都会命中的信号一旦变红，人只会学会跳过它。要看机器可读的结果用 `--json`（回执含 `days`、`min_tickets`、`until`、`rows`、`untagged_commits` 五个键）。

**今天的两处现场（用 `--until` 钉住窗口的右端，任何一天跑出同一个数）：**

```bash
python tools/churn_watch.py --days 1 --until 2026-11-21T12:50:00Z --min-tickets 3
```

期望输出含两行：`AGENTS.md`（`单数` 是 `5`，`单号` 是 `AW-080,AW-082,AW-091,AW-092,AW-095`）与 `tools/idle_watch.py`（`单数` 是 `4`，`单号` 是 `AW-091,AW-093,AW-098,AW-100`）。窗口右端钉在 12:50Z 是因为它盖住了 `AW-100` 的 `ce18305`（12:48Z）而没盖住别的。**这两个数只随「过去某段区间里的提交」变，合并不会改它们**——合并改的是「从 master 能否走到那条提交」，不改提交时间；所以窗口一旦钉在过去，数就不会漂。

#### R4.1 验收条件

- AC-R4-1（命令类·证伪「只扫 master」）：在临时仓库里造夹具，三张单改同一个文件，其中两张单只在未合分支上：

  ```bash
  mkdir -p .data/churn-fixture && cd .data/churn-fixture && git init -q -b master . && printf 'a\n' > a.txt
  git add a.txt && git -c user.email=a@b -c user.name=a commit -qm 'AW-901 base'
  git checkout -qb ticket/AW-902 && printf 'a\nb\n' > a.txt && git -c user.email=a@b -c user.name=a commit -qam 'AW-902 second'
  git checkout -q -b ticket/AW-903 master && printf 'a\nc\n' > a.txt && git -c user.email=a@b -c user.name=a commit -qam 'AW-903 third'
  ```

  在上面这个夹具里跑 `python <本仓库>/tools/churn_watch.py --days 7 --min-tickets 3`，期望输出含 `a.txt` 一行、`单数` 为 `3`、`单号` 为 `AW-901,AW-902,AW-903`；**把实现改成只扫 `master` 后同一命令期望 `a.txt` 一行都不出现**（`git log master --pretty=%s -- a.txt` 只看得到 `AW-901`，`1 < 3`）。这条 AC 的用途就是证伪「只扫 master」的实现，不能换成拿本仓库现场数来写：`AW-098` 那两条提交 2026-11-21 20:43:04 合入 master 之后，`git log master` 与 `git log --all` 在同一个窗口里数到同一批单，证伪不成立。（v0.1 就是拿本仓库现场当这条的判据，被验收当场扒出来了。）

### R5 一张单牵扯到哪些会话、哪条消息

**要解决什么。** 一张单牵扯到的会话标识都已经在库里（`attempts.session_id`、`attempts.coordinator_session_id`、`reviews.reviewer_session_id`、`notices.target_session_id`），但派发消息一直靠人手抄：抄错一次整单只能 `recover_ticket`（`AW-027` 的派发消息里写过一个凭空拼的 `c1c2be32…`，`list_sessions` 里没有这条）。本条的交付物是把这四列聚合成一个能点开的 `sessions` 数组，**从 `get_ticket` 就能看到「谁提的、谁派的、谁做的、谁验的、回执发给了谁」**，而不是新增一个看板或让派发消息自己维护一份。

**取哪五层、从哪一列取（写死五层，不多不少）：**

| role | 取自 | 取不到时 |
| --- | --- | --- |
| `requester` | `tickets.requester_session_id`（`create_ticket` 的可选入参） | 不输出这一条——NULL 就是「没记」，**不拿协调会话冒充** |
| `coordinator` | `attempts.coordinator_session_id` | 不输出 |
| `executor` | `attempts.session_id` | 不输出 |
| `reviewer` | `reviews.reviewer_session_id` | 不输出 |
| `receipt_target` | `notices.target_session_id` | 不输出 |

**顺序写死**：请求方 → 协调 → 执行 → 验收 → 回执收件人；同一层有多条时按各行 `rowid` 升序（多代次尝试就是多条，每一代自己一条）。**空会话标识不产出条目**：不生成 `cindy://session/` 这种点开落不到东西的链接。

**每项八个键，回执那一项多一个 `message_id`：**

```json
{"role": "coordinator", "session_id": "404129f5-…",
 "session_url": "cindy://session/404129f5-…?device=…",
 "device": "…", "session_state": "active", "stale": false,
 "at": "2026-11-22T08:03:30+00:00", "source": "attempts.coordinator_session_id"}
```

`at` 是那一行记录落库的时间点（工单创建 / 尝试创建 / 验收 / 回执），`source` 是它来自哪一列。两样都不是装饰：只看 `session_id` 分不出「这一条是不是这一代次的」，也事后查不出一个链错的 id 是从哪一列进来的。

**链接形状与 device。** `session_url` 是 `cindy://session/<id>?device=<deviceId>`；`device` 取自宿主库 `sessions.agent_device_id`（只读、`mode=ro`），取不到时 `device` 写 `null`、链接退回 `cindy://session/<id>`，**不拼一个假值**。本机 1966 条会话的这一列全是 NULL，所以「没有 device」是常态：链接照样能点开，只是少了「哪台机器」这一层；拼一个猜的 device 反而让链接看起来更精确、实际点不到东西。

**归档与删除。** `session_state` 写宿主的 `sessions.status`；它等于 `archived` / `deleted` 时 `stale` 为 `true`——链接照给，但读者知道它指向一条旧会话，不是一条能接着说话的会话。宿主库读不到（不在本机、没有 `sessions` 表、文件不是 sqlite）时 `session_state` 写 `unknown`、`stale` 为 `false`：**未知不等于已失效**，把「查不到」写成「已归档」同样是一句假话。

**消息级：只存 id，不做 deeplink。** `notices.message_id`（`record_notice` 的可选入参）是消息级的唯一载体，库里不存正文。读法是 `get_chat_history`：拿 `sessions` 那一项的 `session_id` 与该条 `message_id` 去取，不去猜 URL。**不输出 `cindy://...?message=` 这种链接**：`cindy://session/<id>?device=…` 是本机验证过的形状（`PRD-010` §5），而 `?message=` 这个参数没有人验证过它能打开任何东西，写了就是把一句没验过的话变成派发依据。取不到 id 时这一列留 NULL，不拿时间戳或标题凑。

**请求方为什么真做一列。** 用协调会话冒充请求方是最省事的写法，也是这里最贵的一种错：两者大多数时候不是同一条会话（本工作区的常态是调度会话派、执行会话做），合并成一列之后**事后就再也分不出「谁提的」与「谁派的」**。所以 `tickets.requester_session_id` 是一列独立的、可空的记录，`create_ticket` 收它就写、不收就留 NULL。
