# 规划闸门

规划这件事最容易出的错不是想得不深，是**想到的东西没有经过该用的方法**。所以这个 skill 不提供思路，它保证三件事：该读的先读、该调的 skill 真的调、产出的计划可被机器检查。

## 一、强制序列（五步，不许跳）

**第 1 步：先读事实，再想方案。**

- `AGENTS.md`（项目归属、硬规则、已知未实现）
- `tasks/round.md`（本轮目标与结束条件）：记下本单对应的是**本轮目标哪一条**。没有这份文件时先问人这一轮要达成什么，不要自己编一个目标再拿它当依据。
- 相关 PRD，并记下**编号与版本号**——后面写进计划，没有版本的依据等于没有依据
- 涉及工单/派发的，读 `docs/protocol.md`（仓库根，代码已合入 master）

**第 2 步：按任务类型挑 skill。** 对照下表，一行可以触发多个：

| 你要做的事 | 必须调用的 skill |
| --- | --- |
| 写或改需求、验收条件 | `prd-authoring` |
| 拆任务、排实施顺序 | `planning-and-task-breakdown`、`writing-plans` |
| 判断下一步、暂停、返工、重新规划 | `pdsa-workflow` |
| 领取、派发、提交成果、发起验收 | `ticket-dispatch` |
| 写实现代码 | `test-driven-development`、`executing-plans` |
| 审查别人的产出 | `code-review-and-quality`、`requesting-code-review` |
| 收到审查意见要回应 | `receiving-code-review` |
| 要说「做完了」之前 | `verification-before-completion` |
| 目标本身不清楚、有多个方案难选 | `brainstorming` |
| 要新建 skill | `writing-skills` |
| 要隔离工作区 | `using-git-worktrees` |

**第 3 步：逐个真的打开 `SKILL.md` 读。** 只看 description 就当"已调用"是自欺——description 只说明它管什么，不说明它要求你怎么做。读的时候记一句：**它改变了什么**。写不出这一句，说明这个 skill 对本任务没用，那就换成有用的。

两个容易自欺的地方，2026-11-17 的盲测里真实发生过：

- **只读了前几十行就引用后面的结论。** 那次会话只读了 `brainstorming` 前 90 行（共 316 行），就把它“先聊清楚再落笔”的前半部分做到了，却漏了后半部分的“先写设计文档、拿到批准”流程。截断读取比不读更危险，因为它会让人自信地漏掉关键步骤。规则：没读全就在计划里写清 `（读了 1-N 行，其后未读）`，并不引用未读部分的结论。
- **点名用了却没打开。** 那次会话在任务排序里用了 `planning-and-task-breakdown`、`writing-plans`、`test-driven-development` 的结论，四个都没读。这也是 `doc_gate.py` 要检查“每个 skill 后面有没有写它改变了什么”的原因。

**第 4 步：按固定节写计划。**

计划文件写到 `tasks/plan-00N-名称.md`，必须含这六个二级标题（`tasks/round.md` 是另一套判据：本轮目标 / 结束条件 / 不做什么，不按这六个要求）：

| 节 | 内容要求 |
| --- | --- |
| `## 依据` | PRD 编号 + 版本号；依赖的既有事实（测试、演练记录） |
| `## 所用 skill` | 用反引号写 skill 名，且**该名字必须真实存在**；每个后面跟一句"它改变了什么" |
| `## 交付物` | 交付物的**主题、形状、给谁看、明确不覆盖什么**，并写一句「**服务本轮目标第 N 条**」——N 取自 `tasks/round.md`；写不出是哪一条，通常意味着这件事不属于这一轮 |
| `## 任务` | 每个任务一个 `###` 块，块内必须有完成证据（跑什么命令、看什么输出） |
| `## 不做什么` | 明确排除项。没有这一节，范围一定会在实施中膨胀 |
| `## 未决` | `[待澄清：…]` 集中登记；没有就写"无" |

**第 5 步：跑闸门。**

```bash
python tools/doc_gate.py tasks/plan-00N-名称.md   # 这份计划
python tools/doc_gate.py --all                    # 全部计划 + 全部 round 文件
```

`--all` 除了 `tasks/plan-*.md`，也会扫 `tasks/round*.md`：一个 round 文件都没有时它直接非零退出并让你先写 `tasks/round.md`，所以这份文件不能停在「记得写」上。不先跑这条、只跑单文件，等于绕过了对结束条件的检查。

任何一条不过就回去改文件，不许先开工再说。这条之所以是机器检查而不是"记得检查"：模型不一定自动加载 skill（工具侧只保证名字出现在提示里），但脚本失败是确定性的。

**第 5 步只管「本轮怎么做」，不管「本轮说完了没有」。** `doc_gate` 查计划与 `round.md` 的格式；一轮要收尾时另跑 `python tools/close_gate.py`（七节收尾包与三条现场事实，正文见 `docs/closing.md`）。两者不互相替代：计划过了闸不等于这一轮可以说结束，收尾包过了闸也不能替代计划的六节。

## 三、只读会话的出口

没有写权限的会话（执行工具受限时）做不到第 4、5 步。这时不许假装做过：

1. 把计划正文直接输出在回复里，并标一句「本计划未落盘、未过闸」。
2. 说明卡在哪一步（通常是 `## 依据` 缺 PRD 版本，或没有写文件的工具）。
3. 交给有写权限的会话落盘并跑闸门，**在过闸前不得据此开工**。

这条不是免罪符。它的作用是让“没做”和“做了”在字面上就分得开。

## 四、反模式

- **点名不读**：计划里写「用了 writing-plans」，实际没打开。判断标准就是那句"它改变了什么"能不能写出来。
- **编 skill 名**：写一个不存在的 skill 来显得周全。`doc_gate.py` 会拒绝。
- **把未决混进任务**：写「调研一下 X」当任务，其实是没想清楚。它该进 `## 未决` 并标 `[待澄清：…]`。
- **没有「不做什么」**：这样的计划通常意味着边界没想过。
- **用版本号含糊过关**：写「依据 PRD」不写版本，PRD 一改就全部失效。
- **把过程依据当业务依据**：引用了 `PRD-001` 不代表这份 PRD 描述了你手上这件事。`PRD-001` 管的是会话体系，周报要算哪些数它不管。闸门只能查编号是否真实存在，查不了相关性；所以没有业务 PRD 时必须在计划里明写「业务依据：暂无」，并把任务限制在不靠猜测的部分。

## 五、边界

这个闸门保证的是**过程可见**，不保证**方案正确**。方案对不对仍然要靠独立审查和真实验证——那是 `requesting-code-review` 和 `verification-before-completion` 的事。

skipping：用户明确说「别走流程，直接做」时，可以跳过第 2–5 步，但必须在回复里说一句"这次跳过了规划闸门，因为……"。不许默默跳过。
