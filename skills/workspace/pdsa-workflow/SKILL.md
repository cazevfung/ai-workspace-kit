# PDSA 工作流

本工作区的流程不是拖拽流程图，是一个**受状态约束的推进过程**。判断下一步不靠语言，靠「当前状态 + 是否满足可推进条件」。

## 一、四个阶段

| 阶段 | 产出 | 通过条件 |
| --- | --- | --- |
| **Plan** | 目标、方法、依赖、交付物形状、验收条件 | 验收条件可被独立检验；交付物主题明确 |
| **Do** | 成果 + 自检说明 + 证据 | 成果落在项目目录内，报告了风险 |
| **Study** | 独立验收结论 + 偏差归类 | 由没执行过该工单的会话给出，逐项打勾或打叉并写理由 |
| **Act** | 通过 / 返工 / 重新规划 / 等待决策 | 结论已落库，工单状态随之改变 |

## 二、PDSA 与库里的真实状态

这是最容易出错的地方：**九个概念态里只有七个能在库里表达**（差在哪见 `AGENTS.md` 的「已知未实现」）。照那九个说，会说出一此不存在的状态。

| 九个概念态 | 库里实际 | 差距 |
| --- | --- | --- |
| 待规划 | **无** | 建工单直接进 `ready`；规划产物只能放 `tasks/plan.md`，不进中心 |
| 待执行 | `ready` | ✓ |
| 执行中 | `dispatching` → `running` | 拆得更细：先占位再绑会话 |
| 待验收 | `awaiting_review` | ✓ |
| 验收中 | **无** | 验收是一次原子调用，没有可停留的「进行中」 |
| 待返工 | `rework` | ✓ |
| 受阻或待决策 | **无** | 阻塞原因、解除条件、回到哪一步，都没有字段 |
| 已完成 | `done` | ✓ |
| 已取消 | `cancelled` | ✓ |

**推论：** 遇到「等待决策」「观察中」「暂停但没取消」时，现在只能靠文档记录 + 保持原状态，库里表达不了。不要假装有那个状态，也不要用 `cancelled` 冒充暂停——取消是终止，不能自动恢复。

## 三、可推进条件（每步的闸门）

- `ready → dispatching`：验收条件非空、依赖已满足、已获授权。
- `dispatching → running`：宿主回执里的实际目录与项目 root 一致。不一致就 `recover_ticket`，不许硬绑。
- `running → awaiting_review`：成果在本项目内、有 SHA-256 与大小、PRD 摘要未变。
- `awaiting_review → done`：验收项**全部**打勾，且验收会话不是执行会话。
- `awaiting_review → rework`：至少一项打叉，写明具体缺陷。
- `rework → ready`：重新领取即产生**新的**尝试记录，旧记录保留。

一个执行会话同一时刻只能绑一个活跃尝试（`attempts.session_id` 上有唯一索引）。想并行处理两个项目，就开两个会话，不要在一个会话里来回切。

## 四、Study 阶段的偏差归类

不做归类，返工就会重复同一种错。三类：

| 偏差来自 | 表现 | 动作 |
| --- | --- | --- |
| **实现** | 目标对、方法对、做得不对 | `rework`，指明具体缺陷 |
| **计划** | 目标对，方法或步骤本身不成立 | 重新规划：改 PRD、`revise_ticket`，旧尝试作废 |
| **外部条件** | 资料缺、权限缺、依赖没到位 | 记录阻塞原因与解除条件，保持未完成 |

把「计划错」当「实现错」反复返工，是最常见的浪费。

## 五、暂停与恢复

- 暂停：记下原因、解除条件、恢复时应回到哪一步。**不要只写「卡住了」。**
- 恢复：`recover_ticket` 需要 `expected_revision` 和真原因，它会让旧尝试 `superseded` 并回到 `ready`。
- 恢复**不停止**实际运行的会话，也不替你判断那边有没有产生副作用。先核对产物，再恢复。
- 旧尝试迟到的提交会被 `STALE_ATTEMPT` 拒绝——这是保护，不是故障，不要换个编号绕过。

## 六、workflow 运行记录：已决不建表

PRD-001 v0.5 的 D3 已定：**不建 `workflow_runs` 表**。理由不是省事，是在同一库再造一份步骤状态就会出现两份进度真相，而那正是本体系要消灭的问题。

所以现在请这样做：

- 步骤推进的**权威记录**是工单状态 + 尝试记录，不是任何 Markdown。
- 需要写「为什么停」「等谁」这类信息，写进 `recover_ticket` 的 `reason` 或工单的事件里，不要新建一份 JSON 当进度。
- 不要调用不存在的 workflow 操作，也不要在文档里描述成已具备。

触发再议的条件（写在 `AGENTS.md` 的「已知未实现」里：已裁定不建 `workflow_runs` 表）：出现并行多步骤模板，或需要步骤级审计时，再评估升表。

## 七、项目登记面

`list_projects` 可列出全部登记，`unregister_project` 可撤销误登记（有工单时返回 `PROJECT_HAS_TICKETS`）。全局化之后每个会话都能登记，所以误登记必须能撤；但**不能为了收拾登记去删工单**——工单没了，验收与事件的依据也没了。修正项目路径的做法是「撤销→重新登记」。

## 不要做

- 不根据感觉说「这步差不多完成了」——状态只能由合法操作改变。
- 不同时在两个项目上用一个会话（`CONFLICT` 会直接拒；`tests/test_concurrency.py` 有守护）。
- 不在 `awaiting_review` 阶段改成果（会触发 `ARTIFACT_CHANGED`，必须重新提交）。
- 不把返工上限、预算、时限当成已实现的能力——它们还没有。
