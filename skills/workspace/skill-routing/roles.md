# 三类会话的最小入口表

只列**该角色真的会命中**的节点。节点含义与归口见 `nodes.md`，这里只写「这个角色在这一步先做什么」。
三张表合起来覆盖 N01–N31，任何角色都不需要读另外两张。

## 一、协调会话（开单、派发、收口）

第一条动作：**先跑 `python tools/work_gate.py --list`，再决定这张单要不要开。**

| 编号 | 该角色第一条动作 |
| --- | --- |
| N01 | 用宿主回的 `project_root` 定项目；没有回执就列候选问人 |
| N02 | `python tools/work_gate.py --list`；已有活跃尝试就先问那个会话，不并写同一批文件 |
| N03 | 按「能不能被另一个会话单独判定」切单；切完跨两个项目就是两张单 |
| N04 | 写 PRD 前先读 `PRD/` 最近一份当体例，写不出验收条件就先问人 |
| N05 | PRD 一改，用 `list_tickets` 列在途工单，逐张对 `prd_sha256`，对不上的按 `STALE_PRD` 处理 |
| N06 | 写 `deliverable`（主题+形状+不覆盖什么）与 `criteria`（每条附证据命令） |
| N07 | 每条条件配一个「故意做错」的版本，跑不出差别就重写条件 |
| N08 | 先定任务顺序与每步的完成证据，再决定派几个会话 |
| N09 | 方案有多个时先问人，不替人拍板；不问就要说明为什么只有一个方案可行 |
| N10 | 有计划的单跑 `python tools/doc_gate.py <项目根>/tasks/plan-00N-名称.md`（计划落在服务对象项目里），非零不派发 |
| N11 | `claim_ticket`，然后把 `coordinator_session_id` 写成本会话标识 |
| N12 | 建会话后拿**创建回执里的 id** 当执行者标识，原样转交，不改写不缩写 |
| N13 | 绑定回执的 `project_root` 与派的项目不一致就停下，不发第二次绑定 |
| N18 | 验收必须由没参与执行的会话做；同一个会话验收自己派发的成果等于没验收 |
| N21 | 返工前先归类：实现错 / 计划错 / 外部条件，归类错了会白改一轮 |
| N22 | 验收通过才谈合并；合并前确认 `git status` 干净、用例全绿 |
| N23 | 进度只落中心库（`events`），不另写一份 Markdown 进度当依据 |
| N24 | 用户说「记住」时才写记忆，走 `cindy_memory`，写不出使用场景就不写 |
| N25 | 新增或改 skill 时同步改本目录总表，并重跑校验脚本 |
| N29 | 发消息给执行会话前先 `list_session_queue` 看它在不在跑；要纠错就 `steer_session`，不要只入队 |
| N30 | 开单时把「在哪个资源上、以什么身份」写进 `deliverable` 与 `criteria`；条件里出现共用资源却没写身份读法的，退回改写不派发 |
| N31 | 发现不属于本单的问题当场开一张 `planned` 单（`state=planned`、`deliverable` 一句话），不顺手做、不塞进本单的 `artifacts`；不值一张单的写进收尾包第 4 节 |

## 二、执行会话（绑定、实现、提交）

第一条动作：**取自己的 `session_id`（宿主接口，不从路径拼），再 `bind_session`；状态进 `running` 之前不动文件。**

| 编号 | 该角色第一条动作 |
| --- | --- |
| N01 | 派发消息里的项目根与本次实际目录一致才继续，不一致就发消息问 |
| N02 | `python tools/work_gate.py --list` 看自己有没有活跃尝试 |
| N08 | 按计划顺序做；计划里没有的顺序，先写一句「先做什么、怎么算做完」再动手 |
| N09 | 实施中目标变清楚或变模糊，都停下来回到 N09，不自行换方案 |
| N10 | 被要求出计划时先过 `doc_gate`（路径为 `<项目根>/tasks/plan-00N-名称.md`），非零不写实现 |
| N12 | `get_current_session_id` 取标识；两个 id 都 `list_sessions` 反查到了才绑定 |
| N13 | `bind_session` 成功后看回执 `state` 是不是 `running`，不是就停 |
| N14 | 先写会失败的用例并真跑，再写实现 |
| N15 | 红了先复现再改；改不动就补一条能复现的用例，别猜 |
| N16 | 每条验收条件跑一次，`evidence` 里贴真实输出 |
| N17 | `artifacts` 只写相对 `{{WORKSPACE}}` 的路径；`STALE_PRD` 先 `revise_ticket` |
| N20 | 每条审查意见先验证再答复，写明照改或不改的理由 |
| N23 | 卡住或范围要变时先发消息给派发方，不自己扩范围 |
| N24 | 发现值得长期记住的事实，才写记忆；临时进度不写 |
| N25 | 本单要改 skill 时同步改总表并重跑校验脚本 |
| N26 | 提交说明与回复先改成人话再发，别堆标签 |
| N27 | 并行前确认无共享文件；长任务先写续跑点 |
| N28 | 工作树已被别的活跃尝试占用时先建 worktree |
| N29 | 收到返工或补充指令先看 `list_session_queue`；要改本轮就用 `steer_session` 注入，发完读回执 `wake_kind` |
| N30 | 采集前后各读一次身份，把「资源类型 / 身份值 / 命令与输出」贴进 `evidence`；身份变过就作废重采，用完按归还清单恢复原状 |
| N31 | 干活时发现的缺口当场开 `planned` 单再继续，不扩本单范围；不值一张单的记进 `submit_result` 的 `risks` 与收尾包第 4 节 |

## 三、验收会话（独立判定）

第一条动作：**先确认自己没参与过这张单的执行，再逐条对条件跑命令。**

| 编号 | 该角色第一条动作 |
| --- | --- |
| N01 | 确认自己在正确的项目里验收，不在就别判 |
| N02 | 看这张单的尝试是否真的处于 `awaiting_review`，不是就别判 |
| N16 | 不接受「已验证」四个字，只接受命令与输出；缺输出的条件按不通过 |
| N18 | 逐条打勾或打叉并写理由；判不出来的条件算不通过 |
| N19 | 按维度分块审查，每块至少给一条具体位置 |
| N20 | 返工意见要写清改什么、改到什么程度算过 |
| N21 | 打叉时归类：实现错 / 计划错 / 外部条件，交给协调会话决定返工还是重规划 |
| N23 | 结论落库（`review_result`），不在聊天里给口头通过 |
| N26 | 验收报告的措辞也要能读，别用标签代替句子 |
| N29 | 验收意见要先确认打中了执行会话：回执 `wake_kind=created` 就等于没送达，先停新建的那条再带 `target_session_id` 重发 |
| N30 | 核 `evidence` 里的身份三元组；查不到身份值、或采集前后两次不同的，按不通过处理，不许整体看着对 |
| N31 | 看到越界的改动先问它有没有对应单号；没有就按不通过处理，不许「顺手改的也算在本单里」 |
