# PRD 写作

本工作区的 PRD 不是说明文档，是**派发的依据**：工单绑定它、验收对照它、改一次就让在途成果失效。所以它写的不是"想做什么"，是"什么算做完了"。

**动手前**：读 `PRD/` 下最近一份 PRD 当体例参照，别自己发明结构。

## 一、落笔前必须追问（这一步不能跳）

先扫一遍歧义，再决定问什么。按类别标三种状态，只对 `缺失` 和 `含糊` 的类别发问，**最多 5 个问题**，一次问完，不要一个个挤牙膏：

| 类别 | 要扫什么 |
| --- | --- |
| 目标与边界 | 核心目标是哪个；明确不做什么 |
| 交付物 | **要交出的是什么东西**：文档、脚本、表、清单、还是一句话结论 |
| 验收 | 谁来判断；判断依据是什么；反例长什么样 |
| 依赖与前置 | 缺什么就做不了；谁能提供 |
| 权限与副作用 | 会不会发送、发布、删除、付费、改动生产数据 |
| 已定事项 | 以前定过什么，这次是否仍然有效 |

问完把答案**写回 PRD 正文**，不要只在对话里留一句。对话是线索，文档才是依据。

## 二、必含结构

| 节 | 要求 |
| --- | --- |
| 头部 | 状态、版本、日期、所属项目、当前实施范围（一句话） |
| 要解决什么问题 | 现象 + 为什么现在的做法不行 |
| 边界 | 明确排除项。没有排除项的需求一定会在实施中膨胀 |
| 各类角色分工 | 谁规划、谁执行、谁验收；写明"不得做什么" |
| 需求条目 | 编号，可被工单引用 |
| 验收条件 | 编号 ACxx，见下 |
| 未实现 / 待验证 | 把"还没做"和"做了但没验"分开 |
| 待决策 | 分 `待决` 与 `已决`，见第五节 |
| 变更记录 | 每次改都加一行，写清改了哪条、影响什么 |

## 三、验收条件怎么写

每条 AC 必须通过五个检查，缺一条就是不合格：

1. **能被单独检验。** 实现其中一条，就能单独判断这条过没过。
2. **有可观测的结果。** 写成「给定…，当…，则…」，而不是「体验流畅」「设计合理」。
3. **写明证据形态。** 是测试用例名、文件路径、截图、还是某个接口的返回。
4. **带状态列。** 每条 AC 都是 `待验证 / 部分验证 / 已验证（证据）/ 已作废（原因）` 之一，不许整篇用一句「以上均为待实现」概括——那句话一旦过期就是在撒谎。
5. **必须能写出一条反例。** 写下「什么情况会让这条变红」，写不出反例说明这条本身就不可判定。
6. **涉共用可变资源的条件要写出身份。** 条件是「在身份为 X 的产物上做 Y」：X 是当场读出来的值（真机序列号与包里那一版的 `versionName`、部署回执的 deployment id、共享数据库路径与 `schema` 版本、目录的分支与 head），并附一条读它的命令。只写「在真机上截图」「在共享库上验证」的条件判不了——那张图来自哪一份构建没人知道，这条永远无法被推翻。口径见 `PRD/PRD-012-共用资源的身份与占用.md`。

反例：「系统应稳定可靠」。这不是验收条件，是无法反驳的句子。

**为什么第五条要单独列。** 前四条都能靠措辞满足，第五条不能：反例得说出一件具体会发生的事。写不出反例的验收条件，在验收会话里就退化成一句「检查一下——」于是通过——这正是两次拒收里最常见的形态（「证据不可能失败」）。所以验收条件只有两种合法写法：命令 + 期望输出，或标「判断类」并写出反例。没写反例而只写「判断是否一致」的，本身就不可判定。

第六条与它们不重复：前五条问「这条能不能被推翻」，第六条问「这条说的是不是同一份产物」。写对了前五条的条件，仍可能在别人的构建上被验收通过。

## 四、最容易漏的一条：交付物的主题

**演练实测教训：** 只写验收条件、不写交付物主题时，成果会**合规地跑偏**。曾经一个工单的验收条件是"清单包含迁移步骤与回滚步骤"，执行会话写出了一份数据库迁移清单——完全符合字面要求，但主题根本不是被要求的那个。

所以每份 PRD、每个工单都必须回答：**交付物是什么形状、给谁看、覆盖什么主题、明确不覆盖什么主题。** 验收条件约束"做得对不对"，主题约束"做的是不是这件事"，两者不能互相替代。

## 五、待决策清单

未定的事必须显式存在，不能靠上下文默认。

- 正文里用内联标记：`[待澄清：具体缺什么]`。
- 同时在「待决策」节登记一行：`D1 待决｜问题｜为什么卡住｜谁来决定`。
- 一旦定了，改成 `D1 已决（日期）｜结论｜影响哪些节`，**正文同步改**。只改一处等于没改。
- 禁止裸 `TODO` / `TBD` / `[待定]` / `{{占位}}`——它们无法区分"还没想"和"忘了改"。落笔前清零，或换成带上下文的 `[待澄清：…]`。

## 六、改 PRD 的时候

1. 先回答：这条改动影响哪些在途工单、哪些已通过的验收要重做。
2. 用 `revise_ticket` 显式修订受影响工单的验收条件，写明原因；不要指望执行者自己发现。
3. 版本号加一，变更记录写一行。
4. 旧成果不会自动适配新版——`STALE_PRD` 是设计，不是 bug。

## 七、交出去之前的自检

- [ ] 每条 AC 都能被一个反例推翻
- [ ] 交付物主题、形状、读者写清楚了
- [ ] 没有裸占位符；未定项都在待决策节
- [ ] 排除项写了，且写的是"不做什么"而不是"做得少一点"
- [ ] 「未实现」和「未验证」分开写了
- [ ] 每个数字、日期、路径都能在仓库里指到
- [ ] 条件里出现的每条命令，落进工单前自己先跑一遍；跑不通就改条件——把「期望输出」照字面贴进终端，不只看它读起来对不对。权限不足、`grep` 不认的转义、`…` 或 `<占位>` 这类省略号、只差一行的计数，都算跑不通（AW-083 的两条条件就是用了 `grep` 不认的转义与省略号占位，执行会话为此返工两次）
- [ ] 变更记录加了一行

## 不要做

- 不为了让方案通过而改写验收标准。
- 不把「待决」写成「已决」，也不把「已验证」写成「已实现」。
- 不用「后续优化」「视情况而定」掩盖没想清楚的地方——那属于待决策，请登记。
- 不复制其他项目的 PRD 结构当自己的体例；体例看本仓库现有 PRD。
